Eleven rules for a new storage feature

  1. Start under the deployment media root, then route. Build a normal key under settings.MEDIAFILES_LOCATION and use the appropriate owner helper. Check that the returned key starts with the expected owner root.
  2. Pick the helper by ownership. Use the case, actor, account, jurisdiction, or chat helper as appropriate. An intentionally deployment-wide object can stay bare, with a comment explaining that decision.
  3. Choose saved or built explicitly. Persist the full returned key or URL for a saved file. A built file needs available inputs and a regeneration workflow.
  4. Read a saved file from its saved value. Do not rebuild its address from current IDs. Validate ownership and stored references without assuming the historical name contains the current ID.
  5. Keep writers, readers, and validators consistent. Use the same key-building contract where rebuilding is intended, and preserve compatibility with saved older paths.
  6. Copy, verify, then delete. The guide recommends copy_object_strict; do not delete after the error-hiding copy path.
  7. Route folder prefixes too. A list or delete prefix needs the full correct root. A short prefix can silently search deployment storage.
  8. Keep AI storage behind grants. The AI chooses neither case-data keys nor storage credentials. Add a deliberate grants operation or supported payload field when needed.
  9. Keep credentials out of logs. This includes connection strings, webhook secrets, and signed URLs.
  10. Use the sanitiser’s filename. Raw names can contain traversal-shaped input such as ../. Use the validated result when building the key.
  11. Check customer-root routing in a meaningful test. Use a case whose owning customer has dedicated storage. The guide cites test_index_key_follows_the_cases_owning_account as an example.

Pseudocode · storage and persistence APIs depend on the feature

Illustrative flow, not a drop-in production implementation:

legacy_key = <MEDIAFILES_LOCATION>/<kind>/<case_id>/<safe_filename>
key = key_for_case(case_id, legacy_key)
write_file(key, pdf_bytes)
save_reference(key)

# Later read:
key = read_saved_reference()
read_file(key)

Confirm successful storage before advertising a usable saved file. If a database update and blob write can fail independently, design how the feature detects and repairs incomplete work. The browser simulation does not claim to implement production transaction handling.

Six questions for the pull request

  • Does a new plain string reach put_object, get_object, or generate_signed_*_url without an owner helper?
  • Is the address saved? If so, which table and column? If not, what can rebuild the file?
  • Does a validator compare a saved address against a prefix built from the current ID?
  • Does a copy or move verify the destination before deleting its source?
  • Does a script bypass routing by using the deployment connection directly?
  • Does the feature work both for a customer with dedicated storage and for one using deployment storage?
Predict first: A new list operation uses case-artifacts/9001/. It performs no writes. Can it still be wrong?

Yes. Prefixes are routed like keys. Without the correct owner media root, the list can inspect deployment storage and report no files even though the customer’s blobs exist.

Remember in 30 seconds

  • A successful read/write pair can still put customer data in the wrong storage.
  • Saved addresses, built-address recipes, and ownership checks need a consistent contract.
  • Verify copies before deletion; route prefixes as carefully as full keys.
