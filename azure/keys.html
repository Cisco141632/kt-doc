Read the key; predict the storage

Break a key into five parts, follow the router’s precedence, and choose the owner helper that builds a correctly rooted name.

By the end, you can…

  • Apply the deployment-first, customer-second, fallback-last routing rule.
  • Choose among all seven key helpers.

Five useful parts of one name

Take the guide’s customer-owned derived file. This is one blob name, but its parts explain both routing and purpose:

1 · prefixcrimeos-backend-maha-police-prod
2 · stagemahapolice-prod
3 · fixed wordmedia
4 · what and wherecase-artifacts/9001/run-1/derived
5 · filenamex_pages_1-3.md

The first three parts form the media root. The router matches the stage root <prefix>/<stage>/; media is the next conventional segment. The case ID and filename explain the object but do not independently select the customer’s connection.

The router reads the start, in this order

1 · Deployment root?If it starts with this deployment’s own stage root, use deployment storage
→
2 · Customer root?Otherwise find a matching customer prefix/stage and use its connection
→
3 · No match?Use deployment storage silently

This rule is the guide’s connection_for_key in common/utils/account_storage.py. It chooses storage from the key’s start. It does not query the case ID in the middle of a bare key to discover its owner.

Working does not prove correct routing

A writer and reader can both use a bare key and succeed in deployment storage. That still fails the customer-storage requirement. Check the full key and selected connection rather than only a successful download.

Choose the helper by who owns the file

The helpers begin with a normal key under settings.MEDIAFILES_LOCATION and replace that media-root start with the owner’s media root when required. They build names; the storage adapter then routes and performs the operation.

HelperUse forOwner lookup
key_for_case(case_id, legacy)Case uploads, results, generated lettersCase’s account; actor fallback as described
key_for_actor(user_id, legacy)Profile pictures, signatures, user OSINT uploadsUser’s account
key_for_account(account_id, legacy)Customer templates or account exportsThe given account
key_for_jurisdiction(id, legacy)Bulk tools that already know the stationStation’s account
chat_prefix(chat_session_id)Chat session filesChat’s case account; otherwise chat user’s account
case_ai_key(case_id)Case context bundle ZIPCase’s account
key_under_every_account(legacy)Searching when the owner is unknownCandidates under deployment and every configured customer root

Searching candidate roots does not by itself authorize a user to read everything found. Keep permission checks and owner selection in their respective service layers.

Watch the root replacement

Worked example · illustrative, no Azure request is sent

Deployment MEDIAFILES_LOCATION:
  crimeosbackend-demo/demo/media
Delhi account root:
  delhi/prod/media

Normal legacy key:
  crimeosbackend-demo/demo/media/case_context_data/214.zip
After case_ai_key(214), when case 214 belongs to Delhi:
  delhi/prod/media/case_context_data/214.zip
Router result:
  Delhi connection + environment container + returned key

The helper’s input has to begin with the expected deployment media root. If the input is merely cases/214/ocr_results/a.txt, the guide says the helper returns it unchanged. Calling the right helper with the wrong input shape does not fix a bare key.

Predict first: You call key_for_case(214, "cases/214/a.txt"). Does the helper add Delhi’s root?

No. The input does not start with MEDIAFILES_LOCATION, so the described replacement does not apply. First build the normal media-rooted key, then pass it through the ownership helper.

Two details that affect debugging

The guide describes a 60-second cache for the routing list. Immediately changing a customer’s prefix, stage, or connection can leave a process using cached routing briefly. Check configuration and cache behavior before concluding a new key is ignored.

If two customer accounts claim the same prefix/stage root but different connection strings, the guide says the router logs an error and uses the deployment connection. This is an ambiguous configuration, not a safe way to share customer storage. The deployment-root match also takes precedence over customer matching.

Predict first: Demo knows only acme/prod/, but a saved key starts mh-prefix/prod/media/. Which storage is selected?

Deployment storage. No configured account root matches that saved start. The key is not rewritten merely because the case now belongs to Acme.

Remember in 30 seconds

  • Routing precedence is own deployment root, then customer root, then silent deployment fallback.
  • Helpers replace an expected MEDIAFILES_LOCATION start; bare strings remain bare.
  • Duplicate roots with different credentials cause an error and fallback; routing is cached for 60 seconds.
