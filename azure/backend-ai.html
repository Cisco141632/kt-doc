Lesson 06 / 11 · 20 min

Let the backend grant access to the AI

Follow the storage-grants endpoint: who chooses keys, who signs access, and how an AI-generated file returns to the artifact record.

On this pageOne service chooses storage; another uses grantsThe storage-grants requestThe returned key must make the round tripStrict inputs make integration errors visibleWatch the full document handoffCheck what you understand

By the end, you can…

  • Assign key choice, credentials, and file transfer to the correct service.
  • Compare READ_CASE_BUNDLE and WRITE_DERIVED payloads and results.
  • Avoid confusing AI request identifiers with artifact IDs.

One service chooses storage; another uses grants

ResponsibilityBackendAI service
Choose case-data blob keysYes; resolves ownership and builds keysNo; uses keys returned by the backend
Hold storage connection stringsDeployment configuration and encrypted customer credentialsNo case-data connection string in the described design
Sign a read or write linkYes, with the routed account credentialRequests a grant
Transfer derived text bytesProvides authorized destinationWrites directly with its signed link

The guide reports removal of AZURE_STORAGE_CONNECTION_STRING from the AI’s case-data path. The AI does not need to reimplement customer-storage routing. It uses the destinations and permissions chosen by the backend.

The storage-grants request

Guide endpoint · reference only, no request is executed

POST /api/cases/ai_data/storage_grants/v1/

The request includes the shared webhook secret, case_id, operation, and payload. Use the API’s documented secret-field name in real code; no secret value is included here. The backend checks that the case exists and is not archived, resolves its owner, constructs the key, and signs the permitted access.

OperationPayloadResultKey under the owner’s media root
READ_CASE_BUNDLEEmptyRead link; about 900 secondscase_context_data/<case_id>.zip
WRITE_DERIVEDrun_id and file_namesOne key and write link per filename; about 300 secondscase-artifacts/<case_id>/<run_id>/derived/<file_name>

For example, a customer media root delhi/prod/media produces delhi/prod/media/case_context_data/214.zip. The media root belongs in both the key-building and signing paths.

The returned key must make the round trip

1 · AI requestsOperation, case ID, run ID and sanitized filename inputs
→
2 · Backend grantsAn owner-rooted key and a narrow signed URL
→
3 · AI writesUploads the derived bytes to the granted destination
→
4 · Backend savesReturned key becomes meta_data.extracted_text_key

The AI sends back the same key the backend supplied. The saved artifact points at that exact output. If the AI invents a separate bare key or the callback saves a rebuilt path, the record and stored object can disagree even when the upload itself succeeded.

Predict first: The backend returns a write link under Maharastra’s root. Should the AI prepend the deployment media root before uploading?

No. The signed link already names the destination and the backend’s returned key identifies it. Rewriting either breaks the agreement and can invalidate the signature.

Strict inputs make integration errors visible

The guide says unknown request fields produce a 400 response naming the field. When adding a supported input, update the backend’s allowed-key contract deliberately. A field accepted by an AI client alone is not automatically accepted by the backend.

The AI’s request_id corresponds to the artifact’s backend ai_request_id. It is not the artifact row ID. Use the right identifier when correlating a callback with persisted data.

The guide found its account-specific storage defects on the backend side because the AI followed granted URLs. That is a finding from the reviewed branches, not a claim that AI integrations can never contain bugs. Verify the destination, callback key, and contract when investigating a new failure.

Remember in 30 seconds

  • The backend chooses and signs case-data keys; the AI uses the returned links.
  • READ_CASE_BUNDLE reads a ZIP; WRITE_DERIVED grants per-file output writes.
