Module 09 / 18 · about 25 minutes

Everyday development & real work

Turn shortcuts into a repeatable working habit for coding, testing, observing and recovering context.

By the end, you can…

  • Design a useful project layout.
  • Capture evidence without confusing logs and scrollback.
  • Recognize when a service manager is the better tool.

A workspace with a purpose

You are debugging an API that sometimes returns 500. Give the editor its own window. Put the development server and its recent logs in a second window. Keep tests in a third. Resist splitting everything into unreadable boxes: only show two tasks together when comparing them helps.

Run in your shell
tmux new-session -s api -n editor -c "$HOME/projects/api"
# Run these from a shell inside the new session.
tmux new-window -n server -c "$HOME/projects/api"
tmux split-window -h -c "#{pane_current_path}"
tmux new-window -n tests -c "$HOME/projects/api"
tmux select-window -t api:editor

Replace the path with an existing directory. Run your project’s documented editor, server and test commands in the corresponding panes. A pane is a normal shell; tmux does not install dependencies or configure the application for you.

A practical debugging loop

ReproduceRun one failing request
→
ObserveRead the matching log and time
→
ChangeEdit one hypothesis
→
VerifyRun focused tests, then repeat
  1. Zoom the log pane when you need to read a long stack trace.
  2. Enter copy mode and search backward for the error. Copy only the relevant context.
  3. Return to the editor with the window chooser or the last-window shortcut.
  4. Run a focused test; do not restart every service unnecessarily.
  5. Detach for a break. Reattach by session name and inspect whether the job is still running.

Capture what happened

Run in your shell
tmux capture-pane -p -S -200 -t %3 > ~/tmux-recent-output.txt
# Start recording NEW pane output; inspect its contents before sharing.
tmux pipe-pane -o -t %3 'cat >> "$HOME/tmux-live-output.log"'
# Stop this pipe after collecting enough evidence.
tmux pipe-pane -t %3

Replace %3 with an inspected pane ID. capture-pane captures the rendered pane and available history; it cannot recover output discarded before capture. -S -200 begins 200 lines back; -S - starts at the beginning of retained history.

pipe-pane streams new terminal output to a command; it is not retroactive and can include control sequences. -o opens only if there is no existing pipe. Redirection after capture-pane is performed by the shell running the client command; pipe-pane runs its command on the server host.

Long jobs: know the boundary

Before leaving a long migration, report or model training job, verify that it started in the intended remote pane, has a writable output path, and records useful progress. A tmux status line does not prove the application is healthy. A job can fail while the session remains perfectly alive.

NeedSuitable approach
Interactive work you want to revisittmux with named sessions and persistent application logs.
One detached commandA carefully understood shell job / nohup workflow may suffice; it has different I/O and lifecycle behavior.
Service that should restart after failure or rebootA service manager, such as systemd where available.
Recurring or resource-scheduled batch jobsA scheduler or platform-native job system with retries, limits and durable outputs.
Container applicationLet the platform supervise the application; tmux inside a short-lived container shares that container’s lifetime.

End the day by recording the task status, saving edited files, checking running jobs, and detaching. End a project workspace by stopping applications cleanly, inspecting panes, and then closing only the intended session.

Pause and test your understanding

Remember in 30 seconds

  • Organize by task, not by the maximum number of panes.
  • Capture-pane is a snapshot; pipe-pane records future output.
  • tmux preserves interaction, while applications and supervisors own recovery.
