Module 03 / 18 · about 20 minutes

See the server, sessions, windows & panes

Build a mental model that makes every later command predictable.

By the end, you can…

  • Trace a key from your terminal to a program.
  • Distinguish session, window, pane, client and server.
  • Understand indexes, stable IDs and target syntax.

One workspace, several layers

Think of the server as an office building, a session as a project room, a window as a desk, and a pane as a workstation running a program. Your client is your view into a room. Leaving the room does not demolish the building.

A pane contains a pseudoterminal and a running program—often a shell which launches other programs. A window arranges panes. A session has a list of linked windows and a current window. Windows can be linked into multiple sessions: this is shared state, not a copy.

A window remembers its active pane. A session remembers its current window. Clicking another pane (with mouse support) or selecting one with a shortcut changes where subsequent typing goes. Typing in a log viewer is different from typing in a shell; tmux does not interpret normal keystrokes as shell commands.

Two clients attached to the same session normally see the same current window and active pane. Both may type into the same application. Separate sessions in a session group allow separate current-window selection while sharing windows and the programs inside them.

Names are friendly; IDs are precise

Run in your shell
tmux list-sessions
tmux list-windows -t project
tmux list-panes -a -F '#{session_name}:#{window_index}.#{pane_index} #{pane_id} #{pane_current_command}'
TargetWhat it selects
projectA session name; prefer exact session matching with =project where accepted.
project:1Window index 1 in project.
project:1.0Pane index 0 of window index 1 in project.
%3Pane ID 3, stable for that pane’s lifetime on this server.
@2 / $1Window ID / session ID. Quote dollar-prefixed IDs so your shell does not expand them.

Indexes may change when you move or renumber objects. IDs are unique within one server and last only as long as that object. A session name is not a Linux process ID. A pane’s PID identifies a process, not a tmux target.

Without -t, commands use context and defaults that may surprise scripts. Inspect targets first and pass explicit names or IDs for automation. Quote format strings so the shell sends them unchanged.

The missing layer: a server socket

Clients communicate with the server through a Unix socket, normally under a per-user directory such as /tmp/tmux-UID/. The server belongs to the user who starts it. Running sudo tmux ls typically inspects a different user’s server and will not reveal your ordinary sessions.

Run in your shell
tmux -L training new-session -d -s demo
tmux -L training list-sessions

-L training chooses a named socket and therefore a separate server. -S /path/to/socket chooses an explicit path. A missing session can mean the wrong host, user or socket—not that the session has died.

Pause and test your understanding

Remember in 30 seconds

  • Server → session → window → pane → program.
  • Input goes to the foreground program in the active pane.
  • Use stable pane IDs in scripts, and inspect the correct host, user and socket.
