Module 10 / 18 · about 30 minutes

SSH, nested tmux & collaboration

Keep remote work reachable, diagnose connection layers and share a terminal intentionally.

By the end, you can…

  • Run tmux on the right host and reconnect after an SSH drop.
  • Handle nested prefixes and shared clients.
  • Diagnose user, socket, terminal and environment mismatches.

Persistence belongs on the remote host

Run in your shell
ssh user@server.example
# Now on the server:
tmux new-session -A -s deploy
Laptop terminalCan close or lose the network
→
SSH connectionCarries input and screen updates
→
Remote tmux serverOwns the session
→
Remote jobKeeps running while its host and server survive

Start the job inside the remote tmux session. After a disconnect, reconnect to the same host as the same user, run tmux ls, and attach by name. If you instead run local tmux and then SSH from one pane, local tmux preserves the local SSH client; it does not automatically protect a remote shell when that SSH connection dies.

For a direct interactive attach, ssh -t user@server.example 'tmux new-session -A -s deploy' allocates a terminal for tmux. Noninteractive SSH commands do not always have one. A load-balanced hostname may land you on another machine; check hostname before assuming sessions disappeared.

When there are two prefix layers

Sometimes local tmux contains SSH into a second tmux. With Ctrl+b at both layers, the first prefix is consumed by the outer tmux. Its default send-prefix binding lets a second Ctrl+b pass one literal prefix to the inner layer.

Ctrl+b → Ctrl+b → d

With the default binding, that sequence detaches the inner tmux. Prefix then d detaches the outer one. A distinct outer prefix is another approach. Check list-keys -T prefix if behavior differs.

Nested-session warning

Inside one tmux server, use switch-client to change sessions. The warning about nesting is useful. Unsetting TMUX just to silence it can hide a mistaken workflow; reserve nesting for a deliberate multi-host or separate-server setup.

Attach together, with clear ownership

Run in your shell
tmux list-clients
# Another terminal, same host/user/socket:
tmux attach-session -t api
# Observe with a read-only client:
tmux attach-session -r -t api

Two writable clients can type into the same active pane at the same time. Agree who is driving. A read-only client reduces accidental keystrokes but is not a secrecy boundary: its viewer can still see displayed secrets. attach -d detaches the other clients, so do not use it casually during a shared session.

For separate current-window choices with the same windows, create grouped sessions as shown in the advanced lesson. Pane focus and program state are still shared. For separate users, modern tmux has server-access, but socket path permissions and per-user authorization must both be correct. Do not make a tmux socket world-writable. Use an approved collaboration setup and grant access only to trusted users.

Reconnect does not refresh every existing shell

The server and its sessions hold environment values. On attach, update-environment can refresh selected session variables such as SSH agent or display settings. Existing shell processes keep their inherited environment. A newly created pane may therefore behave differently from an older one.

Run in your shell
tmux show-environment -t api
tmux show-options -g update-environment
printf 'Agent socket: %s\n' "$SSH_AUTH_SOCK"
printf 'Terminal type: %s\n' "$TERM"

A stale SSH_AUTH_SOCK can make an agent-backed Git command fail after reconnecting. Inspect the new connection’s environment, confirm forwarding was intentionally enabled, and open a new pane or carefully update the affected shell. Do not blindly evaluate arbitrary environment output. DISPLAY and Wayland clipboard variables have similar lifetime issues.

If the screen has odd dimensions, inspect list-clients for a small or stale attached client and examine window-size. Modern tmux supports size policies including latest, smallest, largest and manual. Choose intentionally for the team rather than disconnecting someone without explanation.

Pause and test your understanding

Remember in 30 seconds

  • Run remote jobs inside remote tmux.
  • Reconnect to the same host, user and socket.
  • Sharing a session shares programs; reattaching does not rewrite old shells’ environments.
