Module 11 / 18 · about 40 minutes

Script repeatable workspaces

Turn a fragile list of commands into a repeatable project launcher with explicit targets and observable results.

By the end, you can…

  • Create a workspace without duplicate windows.
  • Capture IDs instead of guessing indexes.
  • Understand send-keys, quoting, exit status and synchronization.

Start with an inspectable launcher

A launcher should handle both first run and later runs. Check whether the session exists, create it only if missing, capture the created pane ID, and use that ID for the split. The downloadable workspace script uses a named server and a known config, so it cannot modify your ordinary server.

Illustrative shell script — run outside tmux; directory must exist
#!/bin/sh
set -eu
project_dir="$1"
session="kt-project"
if ! tmux -L kt-tmux has-session -t "=$session" 2>/dev/null; then
  pane=$(tmux -L kt-tmux -f /dev/null new-session -d -P \
    -F '#{pane_id}' -s "$session" -n editor -c "$project_dir")
  tmux -L kt-tmux split-window -h -t "$pane" -c "$project_dir"
  tmux -L kt-tmux new-window -t "$session:" -n tests -c "$project_dir"
  tmux -L kt-tmux select-window -t "$session:editor"
fi
tmux -L kt-tmux attach-session -t "=$session"

-d creates detached; -P -F prints the requested format. Capture that output immediately instead of assuming the first pane is %0. The downloadable version also validates the directory and avoids accidental nesting. Run it from another terminal if you are already attached to a different tmux server.

This is repeatable for sequential runs, not a transactional or race-free deployment system. Two simultaneous launchers can both pass the existence check. Partially created sessions also need inspection before reuse. For concurrency, introduce a lock or synchronize creation explicitly.

Sending text is not a job API

Run in your shell
tmux send-keys -t %3 -l 'printf "hello from tmux\n"'
tmux send-keys -t %3 Enter

-l sends literal text; the separate Enter submits it. Without -l, key names such as Enter and C-c are interpreted as keys. The target might contain an editor, a password prompt or a busy shell. A successful send-keys means input was sent, not that the intended command ran or succeeded.

For deterministic jobs, create a pane with a known command, record its exit status, and use a real completion signal. With remain-on-exit, a finished pane stays visible and can expose pane_dead_status. Validate the workflow on your version before using it for important automation.

Formats give you structured observations

Run in your shell
tmux list-panes -a -F '#{pane_id} | #{pane_current_command} | #{pane_current_path}'
tmux display-message -p -t %3 '#{session_name}:#{window_index}.#{pane_index}'
tmux display-message -p '#{version}'
tmux show-hooks -g

A format expression is expanded by tmux, not your shell. Single-quote it in shell commands. Formats also support conditionals and comparisons; a status example is #{?pane_in_mode,COPY,TYPE}. Inspect actual values before building complex expressions.

if-shell runs a shell test by default. With -F it evaluates a tmux format instead. run-shell executes a command outside a pane; -b runs it in the background. Never interpolate untrusted text into shell commands in status formats, hooks or scripts.

Wait for a signal, not an arbitrary sleep

Run in your shell
# In one shell:
tmux wait-for task-finished
# In another shell using the SAME server:
tmux wait-for -S task-finished

wait-for coordinates commands through a channel; -S signals it, and -L/-U lock and unlock a channel. Waiting does not prove success. Your worker should write an exit code and reliably signal on both success and failure. An absent signal can leave a waiter blocked indefinitely, so use your automation environment’s timeout.

Hooks such as after-new-window run tmux commands after events. They can enforce a layout or notify you, but expensive or recursive hooks create hard-to-explain behavior. Inspect show-hooks while debugging. Command sequences run in order; a launched background job is not automatically finished when the next command runs.

Pause and test your understanding

Remember in 30 seconds

  • Capture IDs and quote paths instead of assuming indexes.
  • A successful send-keys call is not a successful job.
  • Make completion, failure, concurrency and cleanup explicit.
