Module 14 / 18 · about 60 minutes

Eight real-world terminal labs

Use an actual tmux installation to turn recognition into skill. Each lab includes an outcome, commands, predictions, common failures and cleanup.

By the end, you can…

  • Complete the setup, workspace, copy, config and remote labs.
  • Build a repeatable launcher and diagnose intentional faults.
  • Finish a capstone with a clear handoff and cleanup.

Practise with a named lab server

Real terminal, self-reported checklist

These commands run only when you run them in your terminal. Checkboxes record your observations; the website cannot verify your local or remote machine. The browser playground is a separate simulation.

Use -L kt-tmux on outside-shell commands for local labs. Inside its panes, ordinary tmux commands normally use the current server through TMUX. The SSH lab uses a separate remote socket named kt-remote. Existing sessions may carry options from earlier labs; inspect them before assuming clean defaults.

Do not paste an entire lab block without reading its comments: some steps require detaching, switching hosts or stopping a loop first. Example output and predictions are not commands. The full labs take about 3 hours; the 60-minute module estimate is for an initial pass.

Work through the labs

Beginner · 15 min

1 · Prove detach and reattach

Outcome: Keep a visible clock running in a disposable session while its client is detached.

Before you start: Run outside tmux. The named kt-tmux server keeps these exercises separate from your normal sessions. If a lab session already exists, attach and inspect it before reusing it.

Real terminal lab — read the comments between steps
tmux -L kt-tmux -f /dev/null new-session -s kt-clock
# Inside the pane:
while :; do date; sleep 2; done
# Press Ctrl+b, release, then d.
# Back in the outside shell:
tmux -L kt-tmux list-sessions
tmux -L kt-tmux attach-session -t kt-clock

Observe and check off yourself

Predict: Does detaching pause the clock? What happens if the host reboots?

Detach only removes the client, so the loop continues. Reboot ends the server and process. Reattaching cannot restore that live loop.

If it goes wrong: If no session is listed, repeat -L kt-tmux and check host/user. If the loop stopped, verify you did not press Ctrl+c or exit.

Cleanup: After stopping the loop, exit the only shell. Confirm kt-clock is absent from tmux -L kt-tmux ls.

Beginner · 20 min

2 · Build a three-pane workspace

Outcome: Create editor, output and scratch areas, then move focus and zoom without stopping programs.

Before you start: Start a fresh lab session outside tmux. Use a terminal large enough for three readable panes.

Real terminal lab — read the comments between steps
tmux -L kt-tmux -f /dev/null new-session -s kt-layout -n work
# Inside: prefix %, then prefix double quote.
tmux list-panes -F '#{pane_index} #{pane_id} #{pane_current_path}'
tmux select-layout main-vertical
tmux resize-pane -R 5

Observe and check off yourself

Predict: Does zooming close the hidden panes? Does -h create top/bottom panes?

Zoom changes visibility only. -h creates side-by-side panes; -v creates stacked panes.

If it goes wrong: If focus seems wrong, inspect the active border and use prefix q. If splitting fails, enlarge the terminal or use another window.

Cleanup: Exit the three disposable shells, or detach and run tmux -L kt-tmux kill-session -t '=kt-layout' after inspecting it.

Beginner · 20 min

3 · Find and capture a useful log

Outcome: Search a known history, copy a selection and export a snapshot.

Before you start: Start the lab session, then use vi copy-mode keys so the steps are unambiguous.

Real terminal lab — read the comments between steps
tmux -L kt-tmux -f /dev/null new-session -s kt-copy
tmux set-window-option mode-keys vi
seq 1 200
printf 'ERROR request=42: timeout\n'
seq 201 250
# Enter copy mode, then ?ERROR and Enter.
# Space starts selection; move, then Enter copies.
tmux show-buffer
tmux capture-pane -p -S -200 > "$HOME/kt-tmux-capture.txt"

Observe and check off yourself

Predict: Will increasing history-limit recover lines already discarded?

No. It helps panes created afterward retain more future output. A capture is limited to output still available.

If it goes wrong: If Space/Enter fails, inspect mode-keys and the copy-mode-vi table. Test internal buffers before clipboard integration.

Cleanup: Exit the lab shell. Keep or remove only the known ~/kt-tmux-capture.txt exercise file after reviewing it.

Intermediate · 25 min

4 · Diagnose a configuration error

Outcome: Observe partial application and fix a deliberately invalid option on an isolated server.

Before you start: Create ~/kt-tmux-test.conf in your editor with: set -g mouse on, then set -g definitely-not-a-tmux-option on. This is a throwaway file; do not replace your real config.

Real terminal lab — read the comments between steps
tmux -L kt-tmux -f /dev/null new-session -s kt-config
tmux source-file ~/kt-tmux-test.conf
tmux show-options -g mouse
# Fix the invalid line in your editor, then:
tmux source-file ~/kt-tmux-test.conf

Observe and check off yourself

Predict: Is source-file an all-or-nothing transaction?

No. It executes commands and reports failures. Previously applied settings remain; explicitly restore or unset the appropriate value.

If it goes wrong: If changes affect another server, inspect TMUX and -L. Startup -f is ignored when that named server already exists.

Cleanup: Close kt-config and retain/remove only your exercise config. Other lab sessions on kt-tmux may retain this server’s global settings.

Intermediate · 25 min

5 · Recover a remote workspace

Outcome: Reconnect to a running job after closing only its SSH client.

Before you start: Requires an SSH host you are authorized to use and tmux installed there. Replace user@host. Use a disposable job, never a production migration for this exercise.

Real terminal lab — read the comments between steps
ssh user@host
tmux -L kt-remote -f /dev/null new-session -s reconnect
while :; do date; sleep 3; done
# Close this SSH terminal. Reconnect from a new terminal:
ssh user@host
hostname
tmux -L kt-remote list-sessions
tmux -L kt-remote attach-session -t reconnect

Observe and check off yourself

Predict: Would local tmux around an SSH command alone protect a remote process from an SSH drop?

No. Place tmux and the job on the remote host. Host/user policies may still terminate processes on logout, so verify your environment.

If it goes wrong: If the session is missing, check host, user, socket, reboot history and logout policy in that order.

Cleanup: Stop the test loop and exit reconnect. Exit SSH when finished.

Intermediate · 30 min

6 · Launch a repeatable project

Outcome: Run the provided workspace launcher twice and prove it does not duplicate windows.

Before you start: Use an existing project directory. Download examples/workspace.sh or run it from the repository. Start outside tmux.

Real terminal lab — read the comments between steps
sh tmux/examples/workspace.sh "$HOME/projects/my-project"
# Detach, then run the SAME command again.
# From an outside shell, inspect:
tmux -L kt-tmux list-windows -t kt-project
tmux -L kt-tmux list-panes -s -t kt-project

Observe and check off yourself

Predict: Why does the script capture pane_id rather than select pane 0?

Pane indexes and server-global IDs are not guaranteed starting values. Capturing the creation result identifies exactly the pane the launcher made.

If it goes wrong: If the directory is missing, fix the argument. If already inside tmux, detach or use another outside terminal. Inspect partial sessions before retrying after a failure.

Cleanup: Stop any programs you started. Detach and kill only the inspected kt-project session on -L kt-tmux.

Intermediate · 25 min

7 · Troubleshoot a confusing screen

Outcome: Diagnose two intentionally introduced UI problems without losing the workspace.

Before you start: Use a disposable kt-incident session with two shell panes. Do not run important commands while synchronized input is enabled.

Real terminal lab — read the comments between steps
tmux -L kt-tmux -f /dev/null new-session -s kt-incident
tmux split-window -h
tmux set-window-option synchronize-panes on
# Type a harmless comment: # hello
# Then turn broadcasting OFF:
tmux set-window-option synchronize-panes off
tmux resize-pane -Z
tmux list-panes

Observe and check off yourself

Predict: Would restarting tmux be the best first diagnosis?

No. Inspect the specific option and pane list. Restarting can destroy evidence and terminate work when a reversible view/config change is enough.

If it goes wrong: A command entered while synchronization is on may reach both shells. Clear any unfinished harmless input with Ctrl+c before resuming.

Cleanup: Ensure synchronization is off, then close only kt-incident and its disposable panes.

Advanced · 45 min

8 · Capstone: a recoverable development desk

Outcome: Combine project organization, live output, searching, capture, detachment and recovery with a written handoff.

Before you start: Use a harmless project or a scratch directory. The service below is a timestamp loop, so no application installation is required.

Real terminal lab — read the comments between steps
tmux -L kt-tmux -f /dev/null new-session -s kt-capstone -n editor
tmux new-window -n service
while :; do printf 'service alive '; date; sleep 2; done
# Create a tests window with prefix c, rename it with prefix comma.
# There run:
printf 'PASS smoke-check\nERROR simulated timeout\n'
tmux list-panes -a -F '#{pane_id} #{session_name}:#{window_name}'

Observe and check off yourself

Predict: What evidence proves the job is healthy, and what would survive a reboot?

Inspect fresh output and application-specific checks; a session existing is insufficient. Saved files and logs survive only on persistent storage. Live tmux processes do not survive reboot.

If it goes wrong: Use the troubleshooting clinic’s symptom → evidence → fix → verification process. Avoid killing the server to solve an individual window issue.

Cleanup: Stop the service loop with Ctrl+c, save useful files, detach, inspect kt-capstone and kill only that session.

Remember in 30 seconds

  • Explain your prediction before running a command.
  • Check evidence in the actual terminal before ticking a step.
  • End only the inspected lab session; leave unrelated work alone.
