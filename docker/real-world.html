Real-world issues

Tutorials show the happy path. This page collects the problems that teams actually meet when Docker runs real systems: what you see, why it happens, how to fix it, and how to stop it from coming back.

First, a method

Most Docker problems are solved by the same four questions, in this order. Learn the order and you will rarely be stuck.

Exit codes worth knowing

docker ps -a shows a status such as Exited (137). The number tells you a lot.

CodeMeaningUsual cause
0Finished normallyThe main program ended. For a server, that means the wrong command was started.
1Application errorAn exception at startup, a missing variable, a wrong setting. Read the logs.
126Command cannot be executedA script without execute permission
127Command not foundA typo in CMD, or the program is not in the image
137Killed (128 + signal 9)Out of memory, or docker kill
143Terminated (128 + signal 15)A normal docker stop. Usually not a problem.

Disk and logs

The server disk is fullVery common
What you see
no space left on device. Builds fail, the database refuses to write, containers will not start.
Why it happens
Docker never deletes anything by itself. Every deploy leaves the previous image behind. Every build adds cache. After some months this is tens of gigabytes.
Find it
df -h
docker system df
Fix it
# Remove images that no container uses and that are older than 7 days
docker image prune -a --filter "until=168h"

# Remove unused build cache
docker builder prune
Prevent it
Run the image prune above on a schedule (cron or a CI job). Do not schedule anything that prunes volumes.
Container logs eat the diskVery common
What you see
The disk is full, but docker system df does not explain it. One file under /var/lib/docker/containers/ is many gigabytes.
Why it happens
By default Docker writes everything a container prints into one JSON file and never rotates it. A chatty app fills the disk in weeks.
Find it
sudo sh -c 'du -sh /var/lib/docker/containers/*/*-json.log' | sort -h | tail -5
Fix and prevent it
Turn on rotation, per service in Compose: 
services:
  web:
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
or for the whole server in /etc/docker/daemon.json, followed by a restart of Docker. The setting applies only to containers created afterwards. 
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
Images are huge and deploys are slowCommon
What you see
An image of 1.5 GB for a small service. Every deploy and every CI run waits minutes for downloads.
Why it happens
A full base image, build tools left in the final image, no .dockerignore, package caches not cleaned.
Find it
docker images
docker history my-api:1.0
Fix it
Use a -slim or -alpine base. Use a multi-stage build. Add a .dockerignore. Install with pip install --no-cache-dir or npm ci --omit=dev. Clean up in the same RUN line as the install, because a later line cannot shrink an earlier layer.

Crashes and restarts

The app starts before the database is readyVery common
What you see
connection refused in the app logs right after docker compose up. It works when you restart the app by hand a few seconds later.
Why it happens
depends_on in its short form only waits until the database container has started. Postgres itself needs a few more seconds.
Fix it
services:
  web:
    depends_on:
      db:
        condition: service_healthy
  db:
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 10
Prevent it
Also let the app retry its connection for a short time. In production the database can restart at any moment, not only at startup.
A container dies with exit code 137Common
What you see
The service disappears under load. docker ps -a shows Exited (137). The app logs end suddenly, with no error message.
Why it happens
The Linux kernel killed the process because it used more memory than allowed, or more than the server has.
Find it
$ docker inspect -f '{{.State.OOMKilled}}' api
true
$ docker stats
Fix it
Find the memory leak, or give the container what it really needs. Then set a limit on every container, so that one bad service cannot take down the whole server: 
docker run -d --memory 512m --name api my-api:1.0
In Compose the key is mem_limit: 512m.
After a reboot, nothing comes backCommon
What you see
The server was restarted for maintenance. Docker is running, but all containers are stopped.
Why it happens
The default restart policy is no.
Fix it
docker run -d --restart unless-stopped --name api my-api:1.0
In Compose: restart: unless-stopped under the service.
PolicyBehaviour
noNever restart (the default)
on-failureRestart only when the exit code is not 0
unless-stoppedAlways restart, except when you stopped it yourself. The usual choice.
alwaysAlways restart, also after a manual stop once Docker itself restarts
docker stop takes ten seconds and requests are cut offSubtle
What you see
Every deploy has a pause of exactly ten seconds per container. Users get errors during deploys. The container shows Exited (137) after a normal stop.
Why it happens
docker stop sends a polite signal and waits ten seconds. With CMD gunicorn app:app (no brackets) the signal goes to a shell, which does not pass it on. The app never hears it and is killed.
Fix it
Write CMD ["gunicorn", "app:app"] with square brackets. If you start the app from a shell script, the last line of the script must be exec your-program.
The database was empty after the redeployPainful
What you see
After an upgrade or a clean-up, the application starts with no data.
Why it happens
One of three things: the database had no volume at all; the volume was mounted at the wrong path, so the real data stayed inside the container; or someone ran docker compose down -v or docker volume prune -a.
Find it
docker inspect -f '{{json .Mounts}}' db
docker volume ls
Prevent it
Use a named volume at the path the image documents. Take regular backups (pg_dump for Postgres) and store them on another machine. A volume protects against removing a container. It does not protect against a deleted volume or a dead disk.

Security

A secret was baked into an imageSerious
What you see
A security scan, or a stranger, finds an API key or database password in an image that was pushed to a registry.
Why it happens
The secret was written with ENV or ARG, or a .env file was copied in by COPY . .. Deleting it in a later line does not help: the earlier layer still contains it.
Find it
docker history --no-trunc my-api:1.0
docker inspect -f '{{.Config.Env}}' my-api:1.0
Fix it
Change the secret first. Once it was in a pushed image, treat it as public. Then remove it from the Dockerfile and rebuild.
Prevent it
Put .env in .dockerignore. Give secrets to the container when it starts (-e, --env-file, or a secret manager). For secrets needed during the build, use build secrets (RUN --mount=type=secret).
The database port is open to the internetSerious
What you see
Login attempts from unknown addresses in the database logs, although the firewall (ufw) is set to block that port.
Why it happens
-p 5432:5432 listens on every network interface. On Linux, Docker writes its own firewall rules, and they are checked before those of ufw. The port is open even though ufw status says it is closed.
Find it
docker ps --format 'table {{.Names}}\t{{.Ports}}'
Every line that starts with 0.0.0.0: is reachable from other machines.
Fix it
If only other containers need the database, publish no port at all and use a network. If you need it from the server itself, bind it to localhost: -p 127.0.0.1:5432:5432.
The container runs as rootCommon
What you see
A security review flags the image. Or files created through a bind mount belong to root on your machine and you cannot edit them.
Why it happens
Containers run as root unless the image says otherwise.
Find it
$ docker exec api whoami
root
Fix it
RUN useradd --create-home appuser
COPY --chown=appuser:appuser . .
USER appuser
"Permission denied" after switching to a normal userCommon
What you see
You added USER appuser, and now the container stops at once with PermissionError: [Errno 13] Permission denied: '/app/app.py'.
Why it happens
COPY keeps the permissions that the files have on your machine and makes root the owner. If your files are not readable by "others", the new user cannot read them. It works on one laptop and fails on another, depending on how each is set up.
Fix it
Make the user the owner while copying: COPY --chown=appuser:appuser . . This exact problem appeared while the sample app of this course was being built, and that is why its Dockerfile uses --chown.

Builds and deploys

"Nobody changed anything" but today's build is brokenVery common
What you see
The same commit built fine last week. Today the build fails, or the app behaves differently in production.
Why it happens
FROM python:latest, or no tag at all. latest moved to a new major version over the weekend. The same goes for dependencies without a version.
Fix and prevent it
Pin the base image (python:3.13-slim) and pin dependencies (flask==3.1.3, a lock file). Upgrades then happen when you decide, in a commit that can be reviewed and rolled back. The same applies to your own images: deploy my-api:1.4.2 or a commit ID, never my-api:latest.
Works on my Mac, fails on the server: "exec format error"Common
What you see
exec format error when the container starts on the server, or a warning that the image platform linux/arm64 does not match the host linux/amd64.
Why it happens
Apple Silicon Macs build images for ARM processors. Most servers use Intel or AMD processors. An image is built for one processor type.
Fix it
docker build --platform linux/amd64 -t my-api:1.0 .
Prevent it
Do not deploy images built on laptops. Let CI build them on the same processor type as production.
Every CI build takes ten minutesCommon
What you see
A one-line change triggers a full install of all dependencies, every time.
Why it happens
COPY . . comes before the install step, so any change breaks the cache from that line on. Or the CI machine starts empty and has no cache at all.
Fix it
Copy the dependency list, install, and only then copy the code (Module 3). In CI, turn on the build cache feature of your CI system.
CI fails with "toomanyrequests"Occasional
What you see
toomanyrequests: You have reached your pull rate limit while pulling a base image.
Why it happens
Docker Hub limits how many images can be pulled without logging in, counted per IP address. Shared CI machines reach the limit quickly.
Fix it
Run docker login in the CI job, or pull base images through your company registry, which keeps a copy.
I changed the code but the container still runs the old versionVery common
What you see
You saved the file and restarted the container. Nothing changed.
Why it happens
An image is a snapshot taken at build time. Restarting a container starts the same snapshot again.
Fix it
docker compose up -d --build
While developing, use a bind mount so that the container reads your files directly (Module 5).
Docker says a file does not exist, but it is right thereUbuntu
What you see
failed to read dockerfile: open Dockerfile: no such file or directory, or a bind mount that is empty inside the container, although the files exist.
Why it happens
On Ubuntu, Docker installed as a snap package is sandboxed. It can only see folders inside your home directory. It cannot see /tmp or other system folders.
Fix it
Keep projects inside your home directory, or install Docker Engine from Docker's own package repository instead of snap. Check with snap list docker.

Remember

  • Debug in order: docker ps -a → exit code → docker logs → ports → listening address.
  • Docker never cleans up and never rotates logs unless you tell it to.
  • Pin every version: base images, dependencies, and the images you deploy.
  • A secret that was in an image is a leaked secret. Change it.
  • -p opens a port to the network. Use 127.0.0.1: or no port at all for databases.
  • Set a memory limit, a restart policy and a health check on everything that matters.
  • Volumes are not backups.
