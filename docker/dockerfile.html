Build your own image

Until now you ran images that other people made. Here you write a Dockerfile for a small app, build it, and learn the one idea that makes builds fast: layers.

What a Dockerfile is

A Dockerfile is a text file named exactly Dockerfile, with no extension. Each line is one step of a recipe: start from this base, copy these files, run this command. docker build follows the steps from top to bottom and saves the result as an image.

The sample app

This repository contains a small web app in the folder docker/examples/hello-docker. You will use it in this module and the next two. It is one Python file and a list of dependencies:

import os
import socket

from flask import Flask

app = Flask(__name__)


@app.get("/")
def home():
    greeting = os.environ.get("GREETING", "Hello")
    return f"{greeting} from container {socket.gethostname()}!\n"
flask==3.1.3
gunicorn==26.2.0
psycopg[binary]==3.3.6

You do not need Python on your machine. That is the point: Docker brings it.

Your first Dockerfile, line by line

FROM python:3.13-slim

WORKDIR /app

RUN useradd --create-home appuser

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY --chown=appuser:appuser . .

USER appuser

EXPOSE 8000

CMD ["gunicorn", "--bind", "0.0.0.0:8000", "--access-logfile", "-", "app:app"]

RUN or CMD?

RUN happens once, while the image is built, and its result is stored in the image. CMD happens every time a container starts. Install with RUN. Start your app with CMD.

Why 0.0.0.0?

The app must listen on 0.0.0.0 (all addresses), not on 127.0.0.1. Inside a container, 127.0.0.1 means "only this container", so nothing from outside could reach the app, even with -p.

Build it and run it

$ cd docker/examples/hello-docker
$ docker build -t hello-docker:1.0 .
$ docker run -d -p 8000:8000 --name hello hello-docker:1.0
$ curl http://localhost:8000
Hello from container 12b4691b7efd!

You can also open http://localhost:8000 in the browser. The strange name is the ID of the container, which is also its host name.

Same image, different behaviour. This is how one image is used for development, testing and production.

Layers and the build cache

This is the most useful idea in the whole module.

  • Each instruction in a Dockerfile creates one layer. An image is a stack of layers.
  • Docker remembers every layer. If an instruction and its input files are the same as last time, Docker reuses the old layer and prints CACHED.
  • When one layer changes, every layer after it is rebuilt.

So the rule for writing a Dockerfile is: put what changes rarely at the top, and what changes often at the bottom. Your dependencies change once a month. Your code changes every few minutes. That is why the Dockerfile copies requirements.txt and installs before it copies the code.

Build the image a second time without changing anything, and you see it yourself:

$ docker build -t hello-docker:1.0 .
 => CACHED [2/6] WORKDIR /app
 => CACHED [3/6] RUN useradd --create-home appuser
 => CACHED [4/6] COPY requirements.txt .
 => CACHED [5/6] RUN pip install --no-cache-dir -r requirements.txt
 => CACHED [6/6] COPY --chown=appuser:appuser . .

To see the layers of a finished image and how big each one is, use docker history hello-docker:1.0. For this app, the dependencies layer is about 37 MB on top of the Python base image.

.dockerignore: what stays out

COPY . . copies the whole folder. Some files must never go into an image: the Git history, local virtual environments, and above all files with secrets. List them in a file named .dockerignore next to the Dockerfile. It works like .gitignore.

.git
.gitignore
.env
.env.example
.venv/
__pycache__/
*.pyc
Dockerfile
.dockerignore
compose.yaml

You get faster builds, smaller images, and no passwords inside an image by accident.

Why the square brackets in CMD?

CMD ["gunicorn", "app:app"] starts your program directly. When you run docker stop, the program receives the signal and shuts down cleanly, in less than a second for this app. The other spelling, CMD gunicorn app:app, starts a shell that starts your program. The stop signal then often does not reach the app, and Docker waits 10 seconds before killing it. Use the brackets.

Multi-stage builds

To build an app you often need heavy tools: compilers, a full SDK, development dependencies. To run it, you need none of them. A multi-stage build uses two FROM lines in one Dockerfile. The first stage builds. The second stage starts clean and copies only the finished result. Everything else is thrown away.

Node.js

# Stage 1: build (has dev dependencies and build tools)
FROM node:24-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: run (only what production needs)
FROM node:24-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=builder /app/dist ./dist
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]

npm ci installs exactly the versions in package-lock.json and fails if that file is missing. That makes it the right choice for builds. --omit=dev leaves out development dependencies.

Go

# Stage 1: compile one self-contained binary
FROM golang:1.26-alpine AS builder
WORKDIR /app
COPY go.* ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /server .

# Stage 2: tiny runtime image, no Go toolchain inside
FROM alpine:3.23
COPY --from=builder /server /server
USER nobody
EXPOSE 8080
CMD ["/server"]

The Go toolchain image is hundreds of megabytes. The final image is a few megabytes plus your binary. CGO_ENABLED=0 produces a binary that needs no system libraries.

Python

# Stage 1: install dependencies into a virtual environment (compilers allowed here)
FROM python:3.13-slim AS builder
RUN apt-get update \
    && apt-get install -y --no-install-recommends build-essential \
    && rm -rf /var/lib/apt/lists/*
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Stage 2: copy only the finished virtual environment, no compilers
FROM python:3.13-slim
WORKDIR /app
RUN useradd --create-home appuser
COPY --from=builder /opt/venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY --chown=appuser:appuser . .
USER appuser
EXPOSE 8000
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "--access-logfile", "-", "app:app"]

Be honest about when this helps. Our sample app gains nothing from it: its dependencies install without a compiler, and both versions come out at about 155 MB. Use this pattern in Python only when a dependency must be compiled.

Every stage starts fresh

Each FROM begins a new, separate stage from its own base image. Nothing carries over: not the files, not WORKDIR, not ENV. That is why WORKDIR /app appears in both stages, and why you need COPY --from=builder to move files across.

Share your image

To let a server or a teammate run your image, push it to a registry. The image name must start with your account or with the address of your company registry.

docker tag hello-docker:1.0 YOUR_ACCOUNT/hello-docker:1.0
docker login
docker push YOUR_ACCOUNT/hello-docker:1.0

# On any other machine:
docker run -d -p 8000:8000 YOUR_ACCOUNT/hello-docker:1.0

Most companies use a private registry such as Amazon ECR, Google Artifact Registry, GitHub Container Registry or Harbor. The commands are the same; only the name in front changes.

Hands-on lab

  1. Build the image twice in a row. The second build should print CACHED on every step and finish in about a second.
  2. Open app.py and change the word from in the greeting to inside. Build again. Which steps are rebuilt?
    Answer

    Only the last step, COPY --chown=appuser:appuser . .. The pip install step stays CACHED because requirements.txt did not change.

  3. Add a comment line such as # test to requirements.txt and build again. What happens now?
    Answer

    The file changed, so COPY requirements.txt . is rebuilt and so is everything after it, including the slow pip install. Remove the comment afterwards.

  4. Run docker history hello-docker:1.0. Which layer is the largest that you created?
    Answer

    The RUN pip install layer, about 37 MB. Your own code is under 1 kB.

Practice

Remember

  • A Dockerfile is a recipe. docker build -t name:tag . turns it into an image.
  • RUN runs at build time. CMD runs when the container starts.
  • Each instruction is a layer. A changed layer rebuilds everything below it, so put slow, stable steps first.
  • EXPOSE documents a port. Only -p publishes it.
  • Multi-stage builds keep build tools out of the image you ship.
  • Pin versions, use .dockerignore, do not run as root, keep secrets out.
