Change, build, run

You changed something. What do you have to do before the running app shows it? This page answers the questions that everybody asks in their first week with Docker.

Three separate things

The most common confusion in Docker comes from treating three different things as one.

ThingWhat it isChanges when
Your codeFiles on your machineYou save a file
The imageA snapshot of those files, taken at build timeYou run docker build, and something that goes into the image is different
The containerA running copy of one imageNever. You replace it with a new container.
Think of it like this

An image is a photograph of your code. If you repaint the room afterwards, the photograph does not change: you have to take a new one (docker build). A container is a print of that photograph hanging on the wall. Taking a new photograph does not change the print that is already hanging: you have to hang a new print (docker run).

Each button is one action. Watch which of the three boxes changes, and which stay behind.

The questions everybody asks

If I build again, do I get a new container?

No. docker build only ever makes an image. Containers are made by docker run.

You doWhat you get
docker buildA new image, if something changed. No container is created or touched.
docker runA new container, every single time
docker startThe same old container, started again
docker restartThe same old container, stopped and started

If only my code changed, did the image change?

Not yet. An image never changes by itself. Saving a file changes the file and nothing else. The image changes when you build, and only if the file you changed is copied into the image.

Does every build give a different image?

No. If nothing that goes into the image is different, every step says CACHED and you get exactly the same image, with the same ID. These results were measured with the sample app:

What you changed before buildingDifferent image afterwards?Why
NothingSame imageAll steps come from the cache
app.pyNew imageCOPY . . brings in a different file, so that layer is new
requirements.txtNew imageThat COPY layer and the install layer after it are rebuilt
An instruction in the DockerfileNew imageThe recipe itself is different
A comment in the DockerfileSame imageComments are not instructions
A file listed in .dockerignore, such as .envSame imageThe file never reaches the build
compose.yamlSame imageIt describes how to run containers, not what is inside the image

I built a new image. Does my running container use it now?

No. A container keeps the image it was created from, for its whole life. To use the new image you need a new container.

Will docker restart pick up the new image?

No. Restart stops and starts the same container. Same container, same image.

What happens to the old image?

It stays on disk. When you build again with the same name, the name moves to the new image and the old one is left without a name. This is called a dangling image. docker images -a lists it as <untagged> (older Docker versions print <none>). Every rebuild leaves one behind, which is how disks slowly fill up. Remove them with docker image prune.

If I run the same image three times, do I get three containers?

Yes. Each docker run creates one more container. They share the image and do not share anything else.

Prove it yourself

Do not take any of this on trust. Run it in docker/examples/hello-docker. It takes five minutes, and after it you will never be confused by this again.

Step 1. Build and run version 1.

$ docker build -t hello-docker:1.0 .
$ docker run -d -p 8000:8000 --name hello hello-docker:1.0
$ curl http://localhost:8000
Hello from container a074ece336d2!

Step 2. Open app.py and change from container to (version 2) from container. Save. Ask the app again:

$ curl http://localhost:8000
Hello from container a074ece336d2!

Still the old text. You changed a file; the image and the container know nothing about it.

Step 3. Build again, with the same name.

$ docker build -t hello-docker:1.0 .
$ curl http://localhost:8000
Hello from container a074ece336d2!

Still the old text, although a new image exists. Look at what the container is using:

$ docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
NAMES     IMAGE          STATUS
hello     33f44ef87b4a   Up 2 minutes

The IMAGE column no longer shows a name. It shows an ID, because the name hello-docker:1.0 now belongs to the new image and this container still runs the old, nameless one.

Step 4. Try a restart.

$ docker restart hello
$ curl http://localhost:8000
Hello from container a074ece336d2!

The same container ID, the same old text. Restarting did nothing for you.

Step 5. Replace the container.

$ docker rm -f hello
$ docker run -d -p 8000:8000 --name hello hello-docker:1.0
$ curl http://localhost:8000
Hello (version 2) from container 74c919da6197!

A new container ID, and at last the new text. Clean up with docker rm -f hello, and undo your edit in app.py.

The recipe to remember

To make a code change visible, you always need the same three steps:

# 1. Take a new snapshot of the code
docker build -t hello-docker:1.0 .

# 2. Remove the container that runs the old snapshot
docker rm -f hello

# 3. Start a container from the new snapshot
docker run -d -p 8000:8000 --name hello hello-docker:1.0

Docker Compose does all three with one command, docker compose up -d --build, and is smart enough to skip the steps that are not needed. See What picks up my change? in the Compose module.

A better habit: a new tag for every version

Reusing the tag 1.0 is what made step 3 confusing: one name, two different images. Give each build its own tag (hello-docker:1.1, hello-docker:1.2). Then every image keeps its name, you can see at a glance which version a container runs, and going back to the old version is one command. This is how real projects work, and it is the subject of From laptop to production.

While developing

Rebuilding for every saved line is slow. During development you can skip the image completely with a bind mount, so that the container reads your files directly. That is explained in Data & networking and Docker Compose.

Practice

Remember

  • Code, image and container are three separate things. A change moves from one to the next only when you run a command.
  • docker build makes images. docker run makes containers. Neither does the other's job.
  • Code alone never changes an image. A build changes it only if the changed file goes into the image.
  • A container keeps the image it was created from. restart does not change that.
  • New code live = build, remove the old container, run a new one.
  • Rebuilding under the same name leaves a nameless old image behind.
