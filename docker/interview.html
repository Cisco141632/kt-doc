Prepare answers you can explain—not just memorize. Filter questions by level, test yourself before revealing the answer, and use the production checklist to turn theory into good habits.

How to give a strong technical answer

Use this four-part pattern. It keeps a simple question short while giving the interviewer clear paths for a deeper follow-up.

1Define itOne clear sentence without jargon.
2Explain whyName the problem it solves.
3Give an exampleUse a command or real situation.
4Add a trade-offShow where the answer has limits.
Example: “What is the difference between an image and a container?”

Definition: An image is an immutable package; a container is a running or stopped instance created from it. Why: The image gives every environment the same starting point. Example: One nginx:alpine image can create five independent containers. Trade-off: A container's writable layer is disposable, so important data belongs in a volume.

Issues interviewers expect you to diagnose

A strong troubleshooting answer starts with evidence. Say which command you would run, what you expect to see, and how that result changes your next step.

RuntimeThe container starts and immediately exitsOpen →
Start with
docker ps -a, then docker logs <name> and docker inspect <name>.
Likely causes
The main process finished, crashed, cannot find a file, lacks a variable, or has the wrong command. A container lives only while its PID 1 process lives.
Fix
Correct CMD/ENTRYPOINT, configuration or permissions. Do not keep it alive with a fake infinite sleep.
NetworkingThe app runs, but localhost in the browser refuses the connectionOpen →
Start with
docker ps to verify the published ports, then docker logs. Inside the container, confirm which address and port the app listens on.
Likely causes
No -p mapping, the host/container ports are reversed, or the app binds to 127.0.0.1 inside the container.
Fix
Publish HOST:CONTAINER and make the app listen on 0.0.0.0 inside the container.
NetworkingOne container cannot connect to another at localhostOpen →
Key idea
Inside a container, localhost means that same container—not the host and not another service.
Start with
docker network inspect <network> or docker compose ps.
Fix
Attach both containers to the same user-defined network and connect with the other container or Compose service name, such as db:5432.
DataDatabase data disappeared after the container was replacedOpen →
Likely cause
The database wrote to the container's disposable writable layer instead of a named volume or bind mount.
Start with
docker inspect <name> and check Mounts; list volumes with docker volume ls.
Fix
Mount durable storage at the exact directory used by the database, then test replacement—not only restart.
BuildA rebuild still runs old codeOpen →
Separate the objects
Source code, image and container can each be on a different version. A restart does not move an old container to a new image.
Start with
Check the build context and .dockerignore, inspect build output, then compare image IDs with docker image ls and docker inspect.
Fix
Build the intended context and tag, then remove/recreate the container from that new image. Use --no-cache only when evidence points to incorrect cache reuse.
HostBuilds fail with “no space left on device”Open →
Start with
docker system df to see space used by images, containers, local volumes and build cache.
Fix safely
Identify unused objects before pruning. Be especially careful with volumes because they may contain irreplaceable data.
Prevent it
Use multi-stage builds, small contexts and images, CI retention rules, monitoring and intentional cleanup.
Platform“exec format error” appears on deploymentOpen →
Likely causes
The image or binary was built for a different CPU architecture, or a script has an invalid shebang/line ending.
Start with
docker image inspect <image> --format '{{.Os}}/{{.Architecture}}' and compare it with the target host.
Fix
Build for the target platform, or publish a multi-platform image with Buildx. Also check script shebangs and Unix line endings.

Rapid-fire points worth remembering

QuestionShort answer
Does EXPOSE publish a port?No. It documents the intended container port. Use -p or Compose ports to publish it to the host.
Does docker restart use a newly built image?No. It restarts the same container with the image snapshot it was created from.
Is a container a lightweight VM?It is an isolated process, not a machine. Containers share the host kernel; VMs have guest kernels.
Should every container have exactly one process?Prefer one concern and one clear lifecycle. One process is a useful rule of thumb, not an absolute law.
Are tags immutable?No. A tag can be moved to another image. A digest identifies exact image content.
Is the Docker socket harmless inside a container?No. Access to the daemon socket is highly privileged and can usually control the host through Docker.

Interview-day checklist

  • Explain the mental model before listing commands.
  • For troubleshooting, begin with evidence: status, logs, inspect, resources and network state.
  • Mention security, persistence and observability when moving from development to production.
  • If a rule has exceptions, call it a rule of thumb and explain the actual goal.
  • Use one concrete example and one trade-off in every important answer.
