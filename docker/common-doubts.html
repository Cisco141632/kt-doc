Why must the app use 0.0.0.0?

There are three separate settings. Mixing them together causes most of the confusion.

Application listens inside container0.0.0.0:8000
+
Docker publishes host to container127.0.0.1:8080:8000
=
You open on the host127.0.0.1:8080

0.0.0.0 is a server listening setting. You normally do not type it into the browser. 127.0.0.1:8080 is the host address you open.

Why does 127.0.0.1 work in my browser but fail inside the application?

They belong to different network spaces. In your browser, 127.0.0.1 means your host machine. Inside the container, it means the container itself. Docker forwards the host request through the container's network interface, so the server must accept traffic on that interface by listening on 0.0.0.0.

EXPOSE, application port and published port

These three lines do three different jobs. All three may mention ports, but only one creates the host connection.

Metadata

EXPOSE 8000

Documents the intended container port. It does not open a host port by itself.

Application

--bind 0.0.0.0:8000

Makes the server accept traffic arriving at port 8000 inside the container.

Docker runtime

-p 8080:8000

Forwards host port 8080 to container port 8000.

One advanced detail

docker run -P can read the image's EXPOSE metadata and publish those ports to random available host ports. Ordinary docker run still publishes nothing unless you use -p or -P.

If two Dockerfiles use WORKDIR /app, do they conflict?

No. Each image has its own filesystem, and every container gets its own writable layer. The text /app is the same, but the storage behind it is different.

They share files only when you deliberately connect both to the same external storage, such as a bind mount or named volume.

Does docker build update a running container?

No. First predict which box will change, then press the buttons and watch code, image and container versions separately.

The reliable development loop without Compose is: edit → build → remove old container → run new container. With Compose it is usually docker compose up -d --build.

ENTRYPOINT, CMD and docker run arguments

Think of ENTRYPOINT as the program and CMD as its default command or arguments. Arguments after the image replace CMD. The --entrypoint option deliberately replaces ENTRYPOINT.

CMD can also be the whole command

If the image has no ENTRYPOINT, then CMD ["python", "app.py"] is the complete default command. It is still replaced by arguments after the image name.

Why use square brackets?

The JSON-array spelling is called exec form. It normally makes the application the container's main process. Shell form inserts /bin/sh -c in front, and that shell may fail to pass Docker's stop signal to the application.

Shell form is not forbidden—it is useful when you intentionally need shell features such as pipes or variable expansion. For a long-running server, use exec form or make the wrapper script finish with exec your-app.

What happens during docker compose up?

Click through the normal flow. A step happens only when the Compose file requires it; for example, a volume is created only when the project declares or uses one.

1. Read and resolve configuration

Compose reads compose.yaml, loads interpolation values, merges override files, and calculates the desired project configuration. Use docker compose config to see this result.

2. Compare desired and current state

Compose checks existing networks, volumes, images and containers. Objects that already match can be reused.

3. Prepare declared resources

Compose creates the project's default network and any required named volumes that do not already exist.

4. Obtain images

Services using image may pull according to their pull policy. Services using build use a local image; add --build when source changes must produce a new one.

5. Create or replace containers

Compose creates missing containers and replaces containers whose image or configuration changed. Unchanged containers can keep running.

6. Start in dependency order

Short depends_on waits for the dependency to start, not to become ready. condition: service_healthy waits for a configured health check to pass.

Does .env automatically enter the container?

No. A Compose .env file supplies values for interpolation. A value enters the container only when the resolved service configuration passes it through environment or env_file.

ThingJob
.envDefault values used while Compose resolves expressions such as ${HOST_PORT:-8080}.
environment:Places named values into the container environment.
env_file:Loads container environment variables from a specified file.
docker compose configShows the resolved Compose model. Add --environment to inspect interpolation inputs.

Remember

  • Browser address, Docker port mapping and application listening address are three different settings.
  • The same path inside two containers does not mean shared storage.
  • Build creates an image; only a new container can use that new image.
  • Runtime arguments replace CMD; --entrypoint replaces ENTRYPOINT.
  • Compose interpolation and the container's environment are related but not the same thing.
