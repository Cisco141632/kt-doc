Docker Compose

Real applications are several containers that belong together: an app, a database, perhaps a cache. Compose describes all of them in one file and starts them with one command.

Why Compose exists

With what you know from Module 4, you can already run the sample app with a database. It takes five long commands, in the right order, and every teammate has to type them without a mistake:

docker network create hello-net
docker volume create db_data
docker run -d --name db --network hello-net \
  -e POSTGRES_PASSWORD=secret \
  -v db_data:/var/lib/postgresql/data \
  postgres:17-alpine
docker build -t hello-docker:1.0 .
docker run -d --name web --network hello-net -p 8000:8000 \
  -e DATABASE_URL=postgresql://postgres:secret@db:5432/postgres \
  hello-docker:1.0

Compose moves all of that into a file that lives in Git next to the code:

docker compose up -d
Think of it like this

Single docker run commands are like giving a taxi driver directions turn by turn. A Compose file is the address: you say where you want to end up, and Compose works out the steps.

The Compose file

The file is called compose.yaml and sits in the project folder. This is the one from docker/examples/hello-docker:

services:
  web:
    build: .
    ports:
      - "8000:8000" # HOST:CONTAINER
    environment:
      GREETING: Hello
      DATABASE_URL: postgresql://postgres:${POSTGRES_PASSWORD}@db:5432/postgres
    depends_on:
      db:
        condition: service_healthy # wait until the database answers

  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - db_data:/var/lib/postgresql/data # named volume: data survives "down"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  db_data:

Where is the network?

You do not write one. Compose creates a private network for every project and connects all services to it. That is why web can reach the database at the host name db, and why db needs no ports at all.

Run the stack

$ cd docker/examples/hello-docker
$ cp .env.example .env
$ docker compose up -d
$ curl http://localhost:8000
Hello from container fb18acde7e7c!
Visits so far: 1
$ curl http://localhost:8000
Hello from container fb18acde7e7c!
Visits so far: 2

Every request is counted in Postgres. Look at what is running:

$ docker compose ps
NAME                 IMAGE                COMMAND                  SERVICE   CREATED          STATUS                    PORTS
hello-docker-db-1    postgres:17-alpine   "docker-entrypoint.s…"   db        12 seconds ago   Up 12 seconds (healthy)   5432/tcp
hello-docker-web-1   hello-docker-web     "gunicorn --bind 0.0…"   web       12 seconds ago   Up 6 seconds              0.0.0.0:8000->8000/tcp

Notice the PORTS column. web is published on your machine. db shows only 5432/tcp with no arrow: it is reachable inside the project network and nowhere else.

Click through: what "up" does

1. Read compose.yaml and .env

Compose reads the file in the current folder and replaces every ${VARIABLE} with the value from .env. The folder name becomes the project name, here hello-docker.

2. Create the network

A private network named hello-docker_default is created. Every service joins it.

3. Create the volume

The named volume hello-docker_db_data is created, unless it already exists. If it exists, it is reused with all its data.

4. Get the images

db has an image, so it is pulled. web has a build, so its image is built from the Dockerfile, but only the first time. Later you need --build.

5. Start the database

web depends on db, so db starts first.

6. Wait until it is healthy

Compose runs pg_isready every 5 seconds. Only when it succeeds is the service marked healthy. Without this, the app would start while Postgres is still booting, and crash.

7. Start the app

Now web starts, connects to db:5432, and port 8000 is published on your machine.

Compose commands

Run them in the folder that contains compose.yaml. They only touch this project.

CommandWhat it does
docker compose up -dCreate and start everything in the background
docker compose up -d --buildThe same, but rebuild images first. Use it after you change code.
docker compose psShow the services of this project and their health
docker compose logs -fFollow the logs of all services together
docker compose logs -f webFollow the logs of one service
docker compose exec web shOpen a shell in a running service
docker compose exec db psql -U postgresRun a program in a service, here the Postgres command line
docker compose restart webRestart one service
docker compose stopStop the containers but keep them
docker compose downStop and remove containers and network. Volumes are kept.
docker compose down -vAlso delete the named volumes. The data is gone.
docker compose configCheck the file and print it with all variables filled in
docker compose pullDownload newer versions of the images

stop, down, and down -v

Three commands that sound alike and do very different things.

CommandContainersNetworkVolumes (your data)
docker compose stopStopped, keptKeptKept
docker compose downRemovedRemovedKept
docker compose down -vRemovedRemovedDeleted

Prove it with the visit counter:

$ docker compose down
$ docker compose up -d
$ curl http://localhost:8000
Hello from container 64302524246e!
Visits so far: 4
$ docker compose down -v
$ docker compose up -d
$ curl http://localhost:8000
Hello from container bcf3bc1c0112!
Visits so far: 1

After down the container is new (a different ID) but the count continues, because the data is in the volume. After down -v the count starts again at 1.

On a server

Never type down -v on a production machine out of habit. It deletes the database of that project without asking.

Secrets and the .env file

The password is not written in compose.yaml. The file says ${POSTGRES_PASSWORD}, and Compose reads the value from a file named .env in the same folder.

POSTGRES_PASSWORD=change-me
  • compose.yaml goes into Git. It contains no secrets.
  • .env is listed in .gitignore and stays on each machine.
  • .env.example goes into Git with placeholder values, so a new teammate knows which variables to set.
  • Run docker compose config to see the file with the values filled in. If a variable is missing, Compose warns you there.
Forgot to create .env?

Compose prints The "POSTGRES_PASSWORD" variable is not set. Defaulting to a blank string, the database refuses to start without a password, and up ends with dependency failed to start. Run cp .env.example .env and try again.

In production, teams usually go one step further and keep secrets in a secret manager instead of a file on the server.

Live code reload while developing

Rebuilding the image for every code change is slow. During development you can mount your source folder into the container with a bind mount. Put this in a second file named compose.override.yaml. Compose merges it on top of compose.yaml automatically.

services:
  web:
    volumes:
      - .:/app
    command: gunicorn --bind 0.0.0.0:8000 --reload app:app

Now a saved change in app.py is active after a second. Keep this file out of production: there the image must contain the code, so that what you tested is exactly what runs.

"Permission denied: '/app'"?

With a bind mount the container sees your files with the permissions they have on your machine. The app runs as appuser, a different user from you. If your files are readable only by you, run chmod -R a+rX . in the project folder and start again.

Practice

Remember

  • Compose describes a whole application in compose.yaml. docker compose up -d starts it.
  • Services reach each other by service name. No network setup is needed.
  • After a code change: docker compose up -d --build.
  • down keeps your data. down -v deletes it.
  • "Started" is not "ready": use a health check with service_healthy.
  • Secrets go in .env, and .env never goes into Git.
