Data & networking

Two questions every real application has to answer: where does my data live when the container is gone, and how do containers reach each other and the outside world?

Containers forget

In the lab of Everyday commands you changed a file inside a container, removed the container, and the change was gone. That is by design: a container is disposable. For a web server this is fine. For a database it would be a disaster.

Be precise

docker stop does not lose data. The files stay until the container is removed with docker rm. But in real life containers are replaced all the time, for every upgrade and every deploy, so anything important must be in a volume.

Try a named volume

You will write a file from one container and read it from a completely different one. Both containers delete themselves (--rm), and the data still survives.

Visual walkthrough: replace the container, keep the data

Move through the steps and watch the container identity change while the volume and its file stay in place.

$ docker volume create notes
notes
$ docker run --rm -v notes:/data alpine sh -c 'echo "I survive" > /data/note.txt'
$ docker run --rm -v notes:/data alpine cat /data/note.txt
I survive

Anonymous volumes: the ones you did not ask for

Some images, Postgres among them, declare that their data folder must be a volume. If you run such an image without -v, Docker quietly creates a volume with a long random name. That is an anonymous volume. The next container gets a new, empty one, so for you the data is lost, while the old files stay on disk and take space. docker rm leaves them behind. Remove a container together with its anonymous volumes using docker rm -f -v NAME, and find leftovers with docker volume ls -f dangling=true.

Which path?

The path on the right is where that program stores its data, and it is different for every image. Find it under "volumes" or "where to store data" on the image's Docker Hub page. Example: Postgres up to version 17 uses /var/lib/postgresql/data, and the Postgres 18 image moved it to /var/lib/postgresql. A wrong path fails silently: the container works, and the data is lost anyway.

Try a bind mount

Now the opposite direction: show a folder of your machine inside a container. Create a tiny website and let nginx serve it.

Interactive: one file seen from two places

Edit the host file, try a write from the container, switch between read-only and read-write, then replace the container.

$ mkdir site
$ echo "<h1>Hello from my laptop</h1>" > site/index.html
$ docker run -d --name site -p 8080:80 -v "$(pwd)/site:/usr/share/nginx/html:ro" nginx:alpine

Open http://localhost:8080. Then edit site/index.html in your editor and refresh the browser. The change is there at once, with no rebuild and no restart. This is how developers get live reloading in containers.

  • $(pwd) inserts the full path of the current folder. Docker needs a full path for a bind mount. In Windows PowerShell write ${PWD}.
  • :ro at the end means read-only: the container can read your files but cannot change them.
You see "403 Forbidden"?

nginx runs as its own user inside the container. If your files are readable only by you, it is not allowed to read them. Run chmod -R a+rX site and refresh. A bind mount keeps the permissions of your machine: this is the most common bind mount problem on Linux.

Clean up with docker rm -f site.

Ports: reaching a container from your machine

A container has its own private network. Nothing outside can reach it until you publish a port with -p HOST:CONTAINER.

You writeMeaning
-p 8080:80Port 8080 of your machine goes to port 80 of the container. Reachable from other machines too.
-p 127.0.0.1:8080:80The same, but reachable only from your own machine
-p 5433:5432Use host port 5433 because 5432 is already taken on your machine
(no -p)Not reachable from your machine. Other containers on the same network can still reach it.
  • The right number is decided by the app in the image. You cannot choose it.
  • The left number is your choice. Two containers cannot use the same host port.
  • EXPOSE in a Dockerfile does not publish anything.

Networks: containers talking to each other

An app container needs to reach its database container. The rule is simple: put them on the same network that you created, and they can find each other by name.

Trace the request, one hop at a time

Choose where the request starts. The correct address changes because every container has its own network view.

Try it. You start a database with no published port and reach it from a second container by name:

$ docker network create labnet
$ docker run -d --name labdb --network labnet -e POSTGRES_PASSWORD=secret postgres:17-alpine
$ docker run --rm --network labnet postgres:17-alpine pg_isready -h labdb
labdb:5432 - accepting connections

If the answer is no response, wait a few seconds and run the last line again. The database container has started, but Postgres inside it is not ready yet. Remember this: it becomes important in the Docker Compose module.

Clean up:

docker rm -f labdb
docker network rm labnet
Why create a network?

Containers started without --network land on Docker's default network, where finding each other by name does not work. Name lookup is a feature of networks you create yourself. Docker Compose creates one for you automatically.

The localhost trap

This mistake catches almost everyone once. Inside a container, localhost means that container, not your machine and not another container. If your app connects to localhost:5432 and the database is in another container, the connection is refused.

Practice

Remember

  • Data inside a container is gone when the container is removed. Important data goes in a volume.
  • Named volume (name:/path) for data that must survive. Bind mount (/host/path:/path) for live code.
  • -p HOST:CONTAINER. Left is yours to choose, right belongs to the app.
  • Containers on a network you created reach each other by name, without -p.
  • Inside a container, localhost is the container itself.
