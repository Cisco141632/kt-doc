From laptop to production

Your image works on your machine. How does it reach a real server, how do teams ship a new version every day without fear, and how do they go back when a version is bad?

The big picture

In a company nobody copies files to a server by hand. Code travels through a fixed path, and the thing that travels is an image.

StationWhat happens there
GitThe developer pushes code. This starts everything else automatically.
CI serverA machine that runs the same commands on every push: run the tests, docker build, docker push. CI means "continuous integration". GitHub Actions, GitLab CI and Jenkins are examples.
RegistryThe warehouse. It keeps every version of the image, so any server can download any version at any time.
ServersThey never build. They only docker pull a version and run it.
Build once, run everywhere

The image that passed the tests is the same file that runs in production. Not a similar one built again later: the very same one. That is the promise of Docker from the first module, now applied to a whole company.

Every build gets its own version

In Change, build, run you saw the mess that one reused tag creates. In a pipeline the rule is strict: a tag is used once and never moved.

Tag styleExampleGood for
Version numberhello-docker:1.4.2Releases that people talk about
Git commit IDhello-docker:a1b2c3dAutomatic builds: you always know exactly which code is inside
latesthello-docker:latestNothing in production. Nobody can tell which version it is, and you cannot go back.

The full name of an image also says where it lives. To push to a registry other than Docker Hub, the registry address goes in front:

registry.example.com / team / hello-docker : 1.4.2
   where it lives       group    repository    version

Hands-on: your own registry

You do not need an account to try this. A registry is itself just a container. Run one on your machine and send two versions of the sample app through it. Work in docker/examples/hello-docker.

Step 1. Start a registry on port 5000.

docker run -d -p 5000:5000 --name registry registry:3

Step 2. Build version 1.0 and push it. The name starts with the registry address.

docker build -t localhost:5000/hello-docker:1.0 .
docker push localhost:5000/hello-docker:1.0

Step 3. Change the code: in app.py, replace from container with v1.1 from container. Build and push it as a new version.

docker build -t localhost:5000/hello-docker:1.1 .
docker push localhost:5000/hello-docker:1.1

Step 4. Ask the registry what it has.

$ curl http://localhost:5000/v2/hello-docker/tags/list
{"name":"hello-docker","tags":["1.0","1.1"]}

Step 5. Pretend to be a fresh server. Delete your local copies, then pull and run the new version.

$ docker rmi localhost:5000/hello-docker:1.0 localhost:5000/hello-docker:1.1
$ docker pull localhost:5000/hello-docker:1.1
$ docker run -d --name hello -p 8000:8000 localhost:5000/hello-docker:1.1
$ curl http://localhost:8000
Hello v1.1 from container 78606510889f!

That was a deploy. The "server" had no source code and no Dockerfile. It only pulled an image and ran it.

Port 5000 busy?

Use another host port, for example -p 5001:5000, and write localhost:5001 everywhere. A registry on localhost works without a login or HTTPS. A real registry needs both: you run docker login first.

What a deploy really is

However complicated the tooling looks, a deploy to one server is always the same few steps. Click through them.

1. Pull the new image

docker pull registry.example.com/team/hello-docker:1.4.2

The old version keeps running while the new image downloads. Only the layers that changed are downloaded, so this usually takes seconds.

2. Remove the old container

docker rm -f hello

The app is down from this moment. Data is safe, because it lives in a volume and not in the container.

3. Start a container from the new image

docker run -d --name hello --restart unless-stopped -p 8000:8000 --env-file .env registry.example.com/team/hello-docker:1.4.2

The same name, the same ports, the same volume, the same configuration. Only the version at the end is different.

4. Check that it is healthy

docker ps, docker logs hello, and a request to the health address of the app.

A deploy is not finished when the container starts. It is finished when the app answers correctly.

5. Keep the previous image for a while

Do not delete version 1.4.1 at once. If 1.4.2 turns out to be bad in an hour, the old image is your way back.

The same with Compose

On a server, the Compose file uses image instead of build, with the version in a variable:

services:
  web:
    image: localhost:5000/hello-docker:${APP_VERSION}
    ports:
      - "8000:8000"
APP_VERSION=1.1

A deploy is then: change the number in .env, and run two commands.

docker compose pull
docker compose up -d

Compose sees that the image name changed and replaces the container. Services whose image did not change are left running.

Rollback: going back

Version 1.1 is live and something is wrong. Because every version still exists in the registry under its own tag, going back is the same action as going forward, with the older number.

$ docker rm -f hello
$ docker run -d --name hello -p 8000:8000 localhost:5000/hello-docker:1.0
$ curl http://localhost:8000
Hello from container 46e76f9dd4ae!

With Compose: set APP_VERSION=1.0 in .env and run docker compose up -d.

What a rollback does not undo

A rollback changes the code that runs. It does not change the data. If version 1.1 altered the database, for example by renaming a column, the old code now meets a database it does not understand. This is why teams make database changes in small steps that both the old and the new version can live with.

Clean up the lab. The -v also removes the hidden volume in which the registry stored its images.

docker rm -f -v hello registry
docker rmi localhost:5000/hello-docker:1.0 localhost:5000/hello-docker:1.1

Then undo your edit in app.py.

One image, many environments

If the same image runs in testing and in production, how can it talk to a test database in one place and the real database in the other? Configuration comes from outside the image, as environment variables given when the container starts.

DevelopmentStagingProduction
ImageBuilt on your machinehello-docker:1.4.2hello-docker:1.4.2 (the same)
Database addressThe db containerThe staging databaseThe production database
Passwords and keysA local .env with test valuesFrom a secret managerFrom a secret manager
Source codeBind mount, live reloadInside the imageInside the image

The rule: if you have to rebuild the image to move it to another environment, something that should be configuration is baked into the image. Take it out and pass it as a variable.

What the CI server runs

CI sounds complicated, but the Docker part of a CI job is three commands that you already know. The CI system only supplies the password and the version number.

# 1. Log in to the registry. The password comes from the CI system's secret store.
echo "$REGISTRY_PASSWORD" | docker login registry.example.com -u "$REGISTRY_USER" --password-stdin

# 2. Build, tagged with the commit that is being built
docker build -t registry.example.com/team/hello-docker:"$COMMIT_ID" .

# 3. Push
docker push registry.example.com/team/hello-docker:"$COMMIT_ID"

Each CI product has its own file format around these commands. The commands themselves are the same everywhere.

Why not build on your laptop?

An image built by CI comes from code that is in Git, was tested, and was built on the right kind of processor. An image built on a laptop may contain changes that nobody else has, and may be built for the wrong processor. Laptops are for developing. CI is for building what gets shipped.

Beyond one server

Everything so far runs on a single machine. That is enough for many internal tools and small products. It stops being enough when you need one of these:

  • No downtime during deploys. Step 2 above takes the app down for a moment.
  • More than one server, because one is too small or because it must not be a single point of failure.
  • Automatic repair: if a server dies at night, the containers should start somewhere else by themselves.
  • Scaling: ten copies of the app during the day, two at night.

The tools for this are called orchestrators. The best known is Kubernetes; cloud providers also offer simpler ones such as Amazon ECS and Google Cloud Run. They do not replace what you learned. They run the same images and use the same ideas under different names:

Learn Docker and Compose well first. Everything in this course is used unchanged when you move on.

Practice

Remember

  • Code goes to Git, CI builds an image, the registry stores it, servers pull and run it.
  • Build once. The same image moves through every environment.
  • Every build gets its own tag, and a tag is never reused. Never deploy latest.
  • A deploy is: pull, replace the container, check.
  • A rollback is a deploy of the previous tag. It does not roll back data.
  • Configuration and secrets come from outside the image.
