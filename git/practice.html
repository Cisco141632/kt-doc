Lesson 18 / 23 · read at your own pace

Try 12 exercises with real Git

Create new practice folders and try each command in small steps. Some conflicts and rejected pushes are expected parts of the exercise.

Need help with HEAD, index, staging, or diff?
Your file
What you are editing now. Git calls the project files the working tree.
Staging area = index
The file content you chose for the next commit. These are two names for one place.
HEAD
Tells Git which saved commit you are using, usually through your current branch.
Diff
A comparison showing added and removed lines between two versions.
Watch these change with one file →

By the end, you can…

  • Create practice projects without changing an existing project.
  • Read and run one action at a time.
  • Explain the result and check it in your terminal.

Create a new practice area

You need Git 2.28 or later and Python 3. Check git --version and python3 --version. Setup creates small local repositories, including a shared local repository and Alice/Bob copies. It does not need a GitHub login or send anything online.

  1. Choose a new destination

    Run from this learning-documents repository’s root folder. The destination must not exist. On a system without /tmp, choose another new local path.

    Type this in your terminal
    python3 git/examples/create-labs.py /tmp/git-learning-first-run

    What you should see: Twelve exercise folders are created. Existing folders are refused, not replaced.

  2. Enter the first lab

    Use the destination path you chose. Each exercise below names its folder.

    Type this in your terminal
    cd /tmp/git-learning-first-run/01-staging

    What you should see: You are inside the first practice repository. Status shows changes prepared for this exercise.

  3. Run one line and read the result

    Pause at comments asking you to edit or expect a conflict. Do not paste the whole exercise as one script.

    What you should see: You can explain each action before running the next line.

You can also download the setup script and run it with a new local path. Examples use a Linux/macOS shell or Git Bash on Windows. The script gives these projects local identity settings and disables signing/hooks locally for consistent practice.

Check a box after observing the result

The page cannot read your project files. These boxes record what you checked yourself. Browser exercises let you try pictures first.

Practice folder · 01-staging

1 · See the staged snapshot

Your goal: Prove that staged content can differ from the file currently on disk.

Open a terminal in YOUR_LAB_ROOT/01-staging. YOUR_LAB_ROOT means the folder you chose in setup. Read one step, run it, and look at its result before going on.

  1. Type this in your terminal
    git status --short
  2. Type this in your terminal
    git diff
  3. Type this in your terminal
    git diff --staged
  4. Type this in your terminal
    git show :notes.txt
  5. Type this in your terminal
    git commit -m 'Record the first edit'
  6. Type this in your terminal
    git show HEAD:notes.txt
  7. Type this in your terminal
    git diff

Check the results yourself

Why does this happen?

The practice setup staged the first edit, then changed the working file again. Commit records the staging area, not every byte currently on disk.

Final check: HEAD contains the first edit; git diff still shows the second edit.

If your result differs: If you ran git add again, you changed the experiment. Create a fresh practice setup root to repeat it.

Practice folder · 02-fast-forward

2 · Fast-forward without a merge commit

Your goal: Move main to the existing later feature commit and count its parents.

Open a terminal in YOUR_LAB_ROOT/02-fast-forward. YOUR_LAB_ROOT means the folder you chose in setup. Read one step, run it, and look at its result before going on.

  1. Type this in your terminal

  2. Type this in your terminal

  3. Type this in your terminal

Feature continues from main. Moving main’s name to the existing commit is enough.

Final check: git rev-parse main and git rev-parse feature match.

If your result differs: If ff-only fails, check separate new commits on both sides instead of removing the guard.

Practice folder · 04-conflict

4 · Resolve a real three-way conflict

Your goal: Keep the approved timeout budget of 20 and feature’s retry count of 3.

Open a terminal in YOUR_LAB_ROOT/04-conflict. YOUR_LAB_ROOT means the folder you chose in setup. Read one step, run it, and look at its result before going on.

  1. Type this in your terminal
    git merge feature

  2. The conflict is expected. Read status and all stages:

  3. Type this in your terminal
    git status
  4. Type this in your terminal
    git show :1:config.json
  5. Type this in your terminal
    git show :2:config.json
  6. Type this in your terminal
    git show :3:config.json

  7. Edit config.json to valid JSON with timeout 20 and retries 3.

  8. Type this in your terminal
    git add -- config.json
  9. Type this in your terminal
    git diff --cached
  10. Type this in your terminal
    git diff --cached --check
  11. Type this in your terminal
    git merge --continue

Check the results yourself

Why does this happen?

Choosing either entire side loses one requirement. Accepting both may create invalid or duplicate configuration.

Final check: config.json parses to timeout=20, retries=3 and no unresolved paths remain.

If your result differs: Do not run continue before editing/staging. git merge --abort is the matching way to stop this operation.

Practice folder · 05-rebase

5 · Rebase and interpret the reversed sides

Your goal: Apply two feature changes again after main, fixing the configuration conflict when it pauses.

Open a terminal in YOUR_LAB_ROOT/05-rebase. YOUR_LAB_ROOT means the folder you chose in setup. Read one step, run it, and look at its result before going on.

  1. Type this in your terminal
    git branch backup/feature-before-rebase
  2. Type this in your terminal
    git rebase main

  3. Conflict expected: ours is main plus already replayed work.

  4. Type this in your terminal
    git status
  5. Type this in your terminal
    git rebase --show-current-patch
  6. Type this in your terminal
    git show :2:config.json
  7. Type this in your terminal
    git show :3:config.json

  8. Resolve config.json to timeout 20, retries 3, then:

  9. Type this in your terminal
    git add -- config.json
  10. Type this in your terminal
    git rebase --continue
  11. Type this in your terminal
    git log --graph --oneline --all

Check the results yourself

Why does this happen?

The new parents create replacement commits. The second feature change should survive even after resolving the first conflict.

Final check: main is an earlier commit of feature, notes.txt exists, config has 20/3, and the backup keeps old IDs.

If your result differs: Rebase may stop more than once. Do not skip a change just to reach the end.

Practice folder · 06-lease/alice

6 · A teammate races your rewrite

Your goal: See a normal push and an exact-ID lease refused by a shared local repository.

Open a terminal in YOUR_LAB_ROOT/06-lease/alice. YOUR_LAB_ROOT means the folder you chose in setup. Read one step, run it, and look at its result before going on.

  1. Type this in your terminal
    expected=$(cat ../expected-tip.txt)
  2. Type this in your terminal
    git log --graph --oneline --all
  3. Type this in your terminal
    git push origin feature

  4. Non-fast-forward rejection is expected.

  5. Type this in your terminal
    git push --force-with-lease=refs/heads/feature:"$expected" origin HEAD:refs/heads/feature

  6. Lease rejection is expected. Inspect the teammate’s update:

  7. Type this in your terminal
    git fetch origin
  8. Type this in your terminal
    git log --left-right --oneline feature...origin/feature
  9. Type this in your terminal
    git show origin/feature:bob.txt

Check the results yourself

Why does this happen?

The practice setup already includes a later push by Bob. Fetching updates origin/feature but does not change the saved exact expected variable.

Final check: The remote still contains bob.txt after both rejected pushes.

If your result differs: Do not replace the explicit lease with --force. Default leases after background fetch are explored in the browser tool.

Practice folder · 08-stash

8 · Handle a stash-application conflict

Your goal: See a stash kept after conflicts and recover the edits around their original starting point.

Open a terminal in YOUR_LAB_ROOT/08-stash. YOUR_LAB_ROOT means the folder you chose in setup. Read one step, run it, and look at its result before going on.

  1. Type this in your terminal
    git status
  2. Type this in your terminal
    git stash list
  3. Type this in your terminal
    git stash apply 'stash@{0}'

  4. Conflict expected. The fixture was clean before apply.

  5. Type this in your terminal
    git status
  6. Type this in your terminal
    git stash show -p 'stash@{0}'

  7. ONLY for this fixture with no pre-existing edits: discard this attempted application.

  8. Type this in your terminal
    git restore --source=HEAD --staged --worktree -- config.json
  9. Type this in your terminal
    git stash branch rescue/stashed-work 'stash@{0}'
  10. Type this in your terminal
    git diff

Check the results yourself

Why does this happen?

There is no stash --abort. This lab starts with clean files, so the shown targeted restore removes only this attempted application.

Final check: The rescue branch contains the intended stashed edit in its working files.

If your result differs: Never use the targeted restore recipe on pre-existing unsaved work without preserving it.

Practice folder · 09-bisect

Your goal: Find the commit where a file changes from the working value to the failing value.

  6. Type this in your terminal

Why does this happen?

The test gives the same answer each time, so Git can keep narrowing the good-to-bad range.

Final check: The first bad commit is 'Introduce regression'; its parent still contains 0. Regression means a bug that appeared after the project previously worked.

If your result differs: Do not mark a missing command or a setup failure as proof of the product bug.

Practice folder · 12-revert

12 · Undo a shared change with new history

Your goal: Revert a bad feature flag while preserving a later documentation change.

Open a terminal in YOUR_LAB_ROOT/12-revert. YOUR_LAB_ROOT means the folder you chose in setup. Read one step, run it, and look at its result before going on.

  1. Type this in your terminal
    git show bad-change
  2. Type this in your terminal
    git revert bad-change
  3. Type this in your terminal
    git log --graph --oneline --decorate
  4. Type this in your terminal

  5. Type this in your terminal

Why does this happen?

If your result differs: If later edits overlap, resolve the revert conflict and use revert --continue or --abort.

Repeat with a fresh folder

Keep your practice folders to inspect later. To repeat from the beginning, run setup with another new destination. It will not reset an existing exercise. Only delete a practice folder after checking it holds no work you want to keep.

Explain the before and after without looking at the commands. A conflict or expected rejection can be the correct result of an exercise.

What to remember

  • Practise in new folders made for these exercises.
  • Run one action, inspect it, then move on.
  • Check the final files and history, not just a success message.
