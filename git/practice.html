Module 17 / 21 · about 75 minutes

Twelve real Git labs

Practise staging, integration, conflicts, leases and recovery in disposable repositories, with expected failures and concrete verification.

By the end, you can…

  • Create local-only fixtures without touching an existing repository.
  • Complete twelve exercises and explain their state changes.
  • Distinguish observed terminal results from self-reported checklist progress.

Create a fresh practice area

You need Python 3 and Git 2.28+ for the fixture builder. Run it from the documentation repository root, choosing a new destination directory. The builder refuses to overwrite an existing directory. It creates local repositories and one local bare remote; no network credentials or GitHub access are used.

Shell example — read the context before running
python3 git/examples/create-labs.py /tmp/git-learning-first-run

Alternatively download create-labs.py and run it with a new destination path. Each lab below names its subdirectory. Commands contain intentional failure points and editor steps: do not paste an entire lab as an unattended script.

The builder uses local learner identity and isolates inherited Git configuration during setup. Normal commands you run afterward still have your environment; if signing, hooks or editors change behavior, inspect configuration rather than altering your global settings unnecessarily. The generated repos configure signing off and hooks disabled locally for reproducible practice.

Learning checklist, not automatic machine verification

Check a box only after observing the result in your terminal. The site cannot read your filesystem. Browser exercises on the next page are separate, explicitly limited simulations.

Observe, predict, execute, verify

Disposable local repository · 01-staging

1 · See the staged snapshot

Outcome: Prove that staged content can differ from the file currently on disk.

After creating the fixtures, open a terminal in YOUR_LAB_ROOT/01-staging. Read every comment before running the next command.

Real Git lab — expected failures are part of the exercise
git status --short
git diff
git diff --staged
git show :notes.txt
git commit -m 'Record the first edit'
git show HEAD:notes.txt
git diff

Observe and check off yourself

Explain why this happens

The fixture staged the first edit, then changed the working file again. Commit records the index, not every byte currently on disk.

Verify: HEAD contains the first edit; git diff still shows the second edit.

If something differs: If you ran git add again, you changed the experiment. Create a fresh fixture root to repeat it.

Disposable local repository · 02-fast-forward

2 · Fast-forward without a merge commit

Outcome: Advance main to an existing descendant and inspect the parent count.

After creating the fixtures, open a terminal in YOUR_LAB_ROOT/02-fast-forward. Read every comment before running the next command.

Real Git lab — expected failures are part of the exercise
git log --graph --oneline --all
git merge --ff-only feature
git show --no-patch --pretty='%h %p %s' HEAD

Observe and check off yourself

Explain why this happens

All feature commits already descend from main. Moving main’s reference is sufficient.

Verify: git rev-parse main and git rev-parse feature match.

If something differs: If ff-only fails, inspect divergence instead of removing the guard.

Disposable local repository · 03-three-way

3 · Combine independent changes

Outcome: Combine a timeout change on main and a retry change on feature.

After creating the fixtures, open a terminal in YOUR_LAB_ROOT/03-three-way. Read every comment before running the next command.

Real Git lab — expected failures are part of the exercise
git merge-base main feature
git log --graph --oneline --all
git merge feature
git show --no-patch --pretty='%h %p %s' HEAD
cat timeout.txt retries.txt

Observe and check off yourself

Explain why this happens

The two branches changed different parts of the snapshot. A new two-parent commit records the combination.

Verify: timeout.txt is 20 and retries.txt is 3; the merge has two parents.

If something differs: A textually clean merge still needs a behavioral test in a real application.

Disposable local repository · 04-conflict

4 · Resolve a real three-way conflict

Outcome: Keep the approved timeout budget of 20 and feature’s retry count of 3.

After creating the fixtures, open a terminal in YOUR_LAB_ROOT/04-conflict. Read every comment before running the next command.

Real Git lab — expected failures are part of the exercise
git merge feature
# The conflict is expected. Read status and all stages:
git status
git show :1:config.json
git show :2:config.json
git show :3:config.json
# Edit config.json to valid JSON with timeout 20 and retries 3.
git add -- config.json
git diff --cached
git diff --cached --check
git merge --continue

Observe and check off yourself

Explain why this happens

Choosing either entire side loses one requirement. Accepting both may create invalid or duplicate configuration.

Verify: config.json parses to timeout=20, retries=3 and no unresolved paths remain.

If something differs: Do not run continue before editing/staging. git merge --abort is the matching way to stop this operation.

Disposable local repository · 05-rebase

5 · Rebase and interpret the reversed sides

Outcome: Replay two feature commits over main, resolving the same configuration conflict in rebase context.

After creating the fixtures, open a terminal in YOUR_LAB_ROOT/05-rebase. Read every comment before running the next command.

Real Git lab — expected failures are part of the exercise
git branch backup/feature-before-rebase
git rebase main
# Conflict expected: ours is main plus already replayed work.
git status
git rebase --show-current-patch
git show :2:config.json
git show :3:config.json
# Resolve config.json to timeout 20, retries 3, then:
git add -- config.json
git rebase --continue
git log --graph --oneline --all

Observe and check off yourself

Explain why this happens

The new parents create replacement commits. The second feature change should survive even after resolving the first conflict.

Verify: main is an ancestor of feature, notes.txt exists, config has 20/3, and the backup retains old IDs.

If something differs: Rebase may stop more than once. Do not skip a change just to reach the end.

Disposable local repository · 06-lease/alice

6 · A teammate races your rewrite

Outcome: Observe normal-push and explicit-lease rejection against a local bare remote.

After creating the fixtures, open a terminal in YOUR_LAB_ROOT/06-lease/alice. Read every comment before running the next command.

Real Git lab — expected failures are part of the exercise
expected=$(cat ../expected-tip.txt)
git log --graph --oneline --all
git push origin feature
# Non-fast-forward rejection is expected.
git push --force-with-lease=refs/heads/feature:"$expected" origin HEAD:refs/heads/feature
# Lease rejection is expected. Inspect the teammate’s update:
git fetch origin
git log --left-right --oneline feature...origin/feature
git show origin/feature:bob.txt

Observe and check off yourself

Explain why this happens

The fixture already includes a later push by Bob. Fetching updates origin/feature but does not change the pinned expected variable.

Verify: The remote still contains bob.txt after both rejected pushes.

If something differs: Do not replace the explicit lease with --force. Default leases after background fetch are explored in the browser tool.

Disposable local repository · 07-reflog

7 · Recover a lost committed tip

Outcome: Find the commit lost by an intentional fixture reset and name it safely.

After creating the fixtures, open a terminal in YOUR_LAB_ROOT/07-reflog. Read every comment before running the next command.

Real Git lab — expected failures are part of the exercise
git log --oneline
git reflog --date=iso
# Find the commit named 'Record valuable work'; inspect its ID.
git show OLD_TIP
git branch rescue/valuable-work OLD_TIP
git show rescue/valuable-work:valuable.txt

Observe and check off yourself

Explain why this happens

The old commit still exists locally and the reflog helps locate it. A rescue reference protects it before further operations.

Verify: The rescue branch contains valuable.txt; main remains at its current tip.

If something differs: OLD_TIP is a placeholder. Do not assume HEAD@{1} after doing other operations.

Disposable local repository · 08-stash

8 · Handle a stash-application conflict

Outcome: Observe retained stash state and recover around the original base.

After creating the fixtures, open a terminal in YOUR_LAB_ROOT/08-stash. Read every comment before running the next command.

Real Git lab — expected failures are part of the exercise
git status
git stash list
git stash apply 'stash@{0}'
# Conflict expected. The fixture was clean before apply.
git status
git stash show -p 'stash@{0}'
# ONLY for this fixture with no pre-existing edits: discard this attempted application.
git restore --source=HEAD --staged --worktree -- config.json
git stash branch rescue/stashed-work 'stash@{0}'
git diff

Observe and check off yourself

Explain why this happens

There is no stash --abort. This fixture has a known clean starting state, allowing targeted restoration before stash branch.

Verify: The rescue branch contains the intended stashed edit in its working tree.

If something differs: Never use the targeted restore recipe on pre-existing unsaved work without preserving it.

Disposable local repository · 09-bisect

9 · Find a regression with bisect

Outcome: Locate the commit that changed a deterministic value from good to bad.

After creating the fixtures, open a terminal in YOUR_LAB_ROOT/09-bisect. Read every comment before running the next command.

Real Git lab — expected failures are part of the exercise
git bisect start
git bisect bad known-bad
git bisect good known-good
git bisect run sh -c 'test "$(cat value.txt)" = 0'
git bisect log
git show --stat refs/bisect/bad
git bisect reset

Observe and check off yourself

Explain why this happens

The fixture has a stable behavior change, so binary search can narrow the history reproducibly.

Verify: The first bad commit is 'Introduce regression'; its parent still contains 0.

If something differs: A missing command or environment failure in a real test must not be mistaken for the regression.

Disposable local repository · 10-cherry-pick

10 · Backport only the fix

Outcome: Apply one bug fix without copying a later unrelated feature change.

After creating the fixtures, open a terminal in YOUR_LAB_ROOT/10-cherry-pick. Read every comment before running the next command.

Real Git lab — expected failures are part of the exercise
git show fix-to-backport
git cherry-pick -x fix-to-backport
git log -1 --format=full
cat bug.txt
git ls-tree --name-only HEAD

Observe and check off yourself

Explain why this happens

Cherry-pick moves a patch into the current context, not all commits after a branch point.

Verify: bug.txt contains fixed; unrelated-feature.txt is absent.

If something differs: A conflict or missing dependency requires contextual resolution, not blindly accepting one side.

Disposable local repository · 11-worktree

11 · Work on a hotfix without disturbing a feature

Outcome: Use a second checkout while the first has a deliberate uncommitted edit.

After creating the fixtures, open a terminal in YOUR_LAB_ROOT/11-worktree. Read every comment before running the next command.

Real Git lab — expected failures are part of the exercise
git status
git worktree add ../11-hotfix -b hotfix main
git worktree list
# Inspect the hotfix directory; the original dirty file remains unchanged.
git -C ../11-hotfix status
git worktree remove ../11-hotfix
git status

Observe and check off yourself

Explain why this happens

Worktrees share objects and refs while keeping separate index/working-directory state.

Verify: The original notes.txt edit is still present after the hotfix worktree is removed.

If something differs: Commit or save work in the second directory before removing a dirty worktree; do not force removal casually.

Disposable local repository · 12-revert

12 · Undo a shared change with new history

Outcome: Revert a bad feature flag while preserving a later documentation change.

After creating the fixtures, open a terminal in YOUR_LAB_ROOT/12-revert. Read every comment before running the next command.

Real Git lab — expected failures are part of the exercise
git show bad-change
git revert bad-change
git log --graph --oneline --decorate
cat flag.txt docs.txt
git merge-base --is-ancestor bad-change HEAD

Observe and check off yourself

Explain why this happens

A revert records a corrective inverse change in new history. It does not remove the old commit or undo unrelated later work.

Verify: flag.txt is off, docs.txt remains, and the ancestry command exits successfully.

If something differs: If later edits overlap, resolve the revert conflict and use revert --continue or --abort.

Finish without losing work

The repositories live only under your chosen lab root, including the local bare remote and both Alice/Bob clones. Keep the directory if you want to inspect later. To start over, create a different new directory; the builder will not reset an existing exercise in place.

Before deleting a lab root through your normal file manager, confirm it contains only disposable work you created for this course. Never copy the lab’s reset/restore cleanup into an unrelated work repository. The full exercises take several hours; the module estimate covers a first guided pass.

Remember in 30 seconds

  • Use a fresh local fixture for every risky experiment.
  • An expected rejection or conflict is evidence, not a failed lesson.
  • Explain the graph and content after each operation.
