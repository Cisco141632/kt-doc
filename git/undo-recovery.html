Module 10 / 23 · about 40 minutes

Undo, reset, revert & recover

Choose an undo operation based on what must move and whether other people already depend on the history.

By the end, you can…

  • Distinguish restore, reset, revert, amend and clean.
  • Recover a committed tip using reflog and a rescue branch.
  • Understand what Git cannot recover reliably.

Match the tool to the layer

IntentToolWhat changes
Unstage a tracked pathgit restore --staged -- pathIndex is restored from HEAD by default; working files remain.
Discard unstaged tracked editsgit restore -- pathWorking file is overwritten from the index. Save needed edits first.
Undo a public change with new historygit revert COMMITCreates a new inverse change; existing commits remain reachable.
Replace the last private commitgit commit --amendCreates a replacement commit; ID changes.
Move current branch tip, retain index and filesgit reset --soft TARGETHEAD/current branch changes; staged and working content stay.
Move tip and reset index, retain filesgit reset --mixed TARGETDefault reset mode; changes become unstaged.
Move tip and overwrite tracked stategit reset --hard TARGETTracked index/working content is reset; obstructing untracked paths can also be removed.
Remove untracked filesgit cleanSeparate destructive operation. Preview with -n; ignored files need extra flags.

Path-limited reset has different semantics from commit-level reset: git reset HEAD -- path adjusts the index, not the branch. Avoid reasoning about every reset as the same operation. A backup branch protects commits, not unsaved file contents.

Revert shared work without rewriting ancestry

Shell example — read the context before running
git show COMMIT
git revert COMMIT
# Resolve conflicts if necessary, then:
# git revert --continue
# Or stop with git revert --abort

Revert applies the inverse of a selected change in the current context. It does not automatically roll back database changes, deployments, deleted external data or leaked credentials. A rollback plan must cover those systems separately.

For a merge commit, inspect its parents with git show --no-patch --pretty=raw MERGE. git revert -m 1 MERGE chooses parent 1 as the mainline; do not assume that is always the intended parent. The original merge ancestry remains recorded, so merging the same branch again may not reintroduce the reverted changes. Plan new commits or a reviewed revert of the revert as appropriate.

Recover by creating a new reference first

Shell example — read the context before running
git reflog --date=iso
git show OLD_TIP
git branch rescue/before-mistake OLD_TIP
git log --graph --oneline --decorate --all -25

Reflogs record local reference movements such as commits, resets and rebases. Find the event and inspect its commit rather than guessing HEAD@{1}; later commands may have changed that numbering. Create a rescue branch so the commit remains reachable, then decide how to integrate it.

Reflogs are local and expire. A new clone does not download your old local reflog. Garbage collection can eventually remove unreachable objects. Some committed work may be recoverable if objects still exist; discarded untracked or never-staged file content generally is not a Git recovery promise. Editor history, filesystem snapshots and backups may be needed.

Stash is temporary storage, not a backup system

Shell example — read the context before running
git stash push -u -m 'WIP before urgent fix'
git stash list
git stash show -p 'stash@{0}'
git stash apply 'stash@{0}'
# Inspect and test before deliberately dropping a successfully applied stash.

Ordinary stash captures tracked changes. -u includes untracked files; -a also includes ignored files and needs extra care. apply keeps the stash; pop drops it only after a successful application and normally keeps it when conflicts occur. Applying onto changed code can conflict.

A stash apply conflict has no stash-specific abort command. Protect any pre-existing uncommitted work before cleaning the attempted application. Consider git stash branch rescue/wip 'stash@{0}' to apply around its original base; it can remove the stash on successful application, so inspect the result. For long-lived work, prefer a named branch and coherent commits.

Before discarding anything

  1. Inspect status, both diffs, untracked and ignored files relevant to the task.
  2. Identify exactly what is committed, staged, unstaged and outside Git.
  3. Save important files or make a suitable commit/stash before a destructive change.
  4. Preview clean with git clean -nd; adding -x also targets ignored files such as local databases and environments.
  5. Use explicit paths and targets, then verify the remaining state.

Remember in 30 seconds

  • Public correction usually calls for revert; private rewriting is a separate choice.
  • A rescue branch protects a discovered committed tip before further operations.
  • Reflog cannot promise recovery of never-recorded content.
