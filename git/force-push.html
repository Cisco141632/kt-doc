When push is refused, and what force changes

Understand why Git refuses to replace shared commits. Learn the expected-ID check used by force-with-lease and what to do when it fails.

Need help with HEAD, index, staging, or diff?
Your file
What you are editing now. Git calls the project files the working tree.
Staging area = index
The file content you chose for the next commit. These are two names for one place.
HEAD
Tells Git which saved commit you are using, usually through your current branch.
Diff
A comparison showing added and removed lines between two versions.

By the end, you can…

  • Explain what a force push replaces on the server.
  • Read the difference between a normal push and a lease.
  • Keep a teammate’s work when the remote changes.

A push asks to move a branch name

A normal push can move the server branch forward when its current commit is included in your new history. If the proposed history leaves out that current commit, Git normally refuses. This helps protect work already shared.

Before
→Force asks the server to use your new position
After

A force push asks the server to accept this replacement. It changes the server branch position. It does not immediately replace every teammate’s files or erase every old copy. GitHub permissions and branch rules can still block it.

What each push checks

Command choiceCheck before acceptingWhat can still go wrong?
Normal pushThe current server commit must normally be part of the proposed history.You can still send the wrong file or use the wrong branch.
--forceAsks to skip that history check. Server rules still apply.A teammate’s work can fall out of the branch history.
--force-with-leaseBy default, server position must match your local last-known position.An editor may fetch in the background and update that position before you read the new work.
--force-with-lease=refs/heads/feature:EXPECTEDServer feature must still be exactly the commit ID you recorded as EXPECTED.The check detects a changed server position. It does not check whether your replacement keeps all useful work.

Lease here means “only replace the branch if it is still where I expect.” refs/heads/feature is the full Git name for the server branch feature. Never add --force to a lease command; force disables that protection.

Why the expected ID matters

Your expected position is C

A picture to explore. These buttons do not run commands on your computer.

  1. Step 1

    You record C before a rewrite

    You inspect the server work and agree to replace C. You keep the full ID as your expectation.

    Positions
    Expected: C
Server: C
Your replacement: C′

  2. Step 2

    A teammate sends T

    The server moves to T. Your saved expectation stays C, even if another tool fetches T.

    Positions
    Expected: C
Server: T
Your replacement: C′

  3. Step 3

    Your explicit lease is rejected

    The server sees T instead of C. It leaves T in place. Fetch and read the new work before deciding what should happen next.

    Result
    No replacement accepted.
Teammate’s T remains on feature.
Try to answer: If I change EXPECTED to T, have I kept T’s changes?

No. You have only changed the value the server checks. Read and keep the teammate’s needed work before agreeing to replace T.

An agreed rewrite, with checks between actions

Use this only on a branch whose users have agreed to rewrite it. Shared main and release branches usually need new corrective commits instead. These steps assume a real local feature and origin/feature, and a clean working tree.

  1. Fetch and inspect both sides

    Read all server-only changes before rewriting.

    Type this in your terminal
    git status
git fetch origin
git switch feature
git log --left-right --graph --oneline feature...origin/feature

    What you should see: You can explain which changes are local and which are on the server. Stop if any teammate work is not understood.

  2. Record and keep both old positions

    expected is a shell variable holding the full server commit ID seen in your fetch. Choose unused backup branch names.

    Type this in your terminal
    expected=$(git rev-parse refs/remotes/origin/feature)
git branch backup/local-feature
git branch backup/server-feature "$expected"

    What you should see: Your local and server starting commits have backup names. Uncommitted files are not saved by these names.

  3. Make only the agreed change to history

    For example, rebase feature onto a fetched main when that is the agreed task.

    Type this in your terminal
    git rebase origin/main

    What you should see: Check the old/new change lists, final files, and tests. Resolve any paused steps before continuing.

  4. Send to the exact branch with the saved expectation

    Read the destination. HEAD means your current commit; the part after the colon names the server branch to update.

    Type this in your terminal
    git push --force-with-lease=refs/heads/feature:"$expected" origin HEAD:refs/heads/feature

    What you should see: The server accepts only if its feature branch still equals expected and access/rules allow the update. If it rejects, inspect the reason.

When the lease is rejected

Stop and fetch. Read the new commits and agree how to keep both sets of useful work. Do not simply fetch, update expected, and send the same replacement again. That can remove the very work the rejection protected.

After an agreed rewrite, teammates should keep their old local position under a backup branch before moving only their own unpublished changes onto the new history. A broad merge of the old history can bring the replaced commits back. Choose the range carefully; the rebase and cherry-pick lessons explain the options.

If the wrong branch was already replaced

Pause more pushes on that branch and tell the people using it. Find the old commit in a backup branch, a teammate’s copy, or a local reflog. Inspect it and create a rescue branch before doing more changes. Compare it with the current server history so recovery does not remove new work added after the mistake.

A reflog is a local record of branch movements; it is not a lasting server backup. If the purpose was to remove a leaked token, disable that token first. A force push cannot remove it from every other copy.

What to remember

  • A force push replaces a server branch position; it can leave out shared work.
  • An explicit lease checks the exact server commit ID you chose.
  • A rejected lease means inspect new work before changing the expectation.
