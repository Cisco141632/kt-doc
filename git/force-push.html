Module 09 / 23 · about 45 minutes

Force push, leases & shared-history safety

Learn exactly what a force push replaces, why teammates can lose reachability, and what a lease does and does not protect.

By the end, you can…

  • Distinguish normal push, --force and an explicit lease.
  • Inspect and preserve history before a permitted rewrite.
  • Respond safely to a rejected lease or accidental rewrite.

Force push moves a server reference

A force push requests a non-fast-forward reference update. The server may accept it only if permissions, rules and hooks allow it. It does not physically erase every old commit everywhere, and it does not overwrite another developer’s working files immediately. Their clone still has its own state; a later fetch shows the changed server reference and may leave their branch diverged.

The danger is replacing a shared branch tip without retaining commits people expected to remain in that branch’s history. The server’s acceptance is not a semantic approval. Force pushing is not a way to fix authentication, choose a remote, resolve a source conflict or make failing tests pass.

Three push behaviors

Push modeWhat it checksRemaining risk
Ordinary pushThe remote branch tip must normally be an ancestor of the proposed tip.You still need the correct destination and correct content.
--forceAsks to bypass normal ancestry protection for the pushed refs; server rules still apply.Can replace commits you have not incorporated. It also disables lease protection if combined with it.
--force-with-leaseChecks the remote tip against your local tracking expectation by default.An automatic/background fetch can advance that expectation without you reviewing the new commits.
Explicit --force-with-lease=refs/heads/feature:EXPECTEDRequires that exact remote reference to still equal the pinned object ID.Protects against concurrent tip changes, not against deleting known commits or publishing bad content.

Do not combine --force with a lease. A lease does not grant permission and does not override protected-branch rules. Pin the expected value before rewriting so you know precisely which remote state you are agreeing to replace.

A deliberate, coordinated rewrite procedure

Use this only on a branch where rewriting is permitted and collaborators have agreed. These are separate steps to inspect, not an unattended paste-and-run script. Start with a clean working tree, fetch, and understand every remote-only commit before proceeding.

Shell example — read the context before running
git status
git fetch origin
git switch feature
git log --left-right --graph --oneline feature...origin/feature
# Stop if remote work is not understood and preserved.
expected=$(git rev-parse refs/remotes/origin/feature)
git branch backup/feature-before-rewrite
git branch backup/remote-feature-before-rewrite "$expected"
# Perform the agreed rewrite, for example:
git rebase origin/main
# Inspect range-diff, final diff and run tests before this push:
git push --force-with-lease=refs/heads/feature:"$expected" origin HEAD:refs/heads/feature

The explicit destination prevents a vague default from selecting the wrong branch. Backup names must be unused and protect only committed history. If the remote already contains work absent locally, integrate or deliberately account for it first; pinning its ID does not preserve its content by itself.

If the lease is rejected

StopSomeone changed the expected remote tip
→
Fetch and inspectFind the new commits and their owner
→
Preserve intentIntegrate or coordinate the replacement
→
Review againTests, graph and a new intentional expectation

Do not blindly fetch, refresh the expected ID and retry the same destructive update. That merely teaches the lease to accept a state you still have not preserved. Inspect what changed and agree on how both lines of work should survive.

For teammates affected by an intentional rewrite, fetch, preserve their local tip under a new branch, then move only their unpublished work onto the agreed new base. This may require a carefully bounded rebase or selected cherry-picks. A broad pull/merge can reintroduce the old history. A hard reset can discard local work.

If the wrong branch was force-pushed

Stop further updates, communicate the incident, and locate the old tip in a colleague’s clone, a local reflog, a backup reference or other retained evidence. Create a rescue branch at that old commit before doing anything else. Compare old and current server history; another force update can otherwise erase legitimate work added after the incident.

Restoring the old tip is a coordinated server change, subject to policy. A local reflog is not a durable remote backup. If the goal is secret removal, revoke the credential first and follow the dedicated repository-cleanup procedure; a force push cannot clean everybody’s clones or caches.

Pause and test your understanding

Remember in 30 seconds

  • Force updates a reference; it is not secure erasure.
  • An explicit lease checks an exact expected tip, not correctness.
  • A rejected lease means inspect new work, not weaken the protection.
