Who can read, push, and change settings?

Understand account access and tokens through a failed-push example. Check the missing permission without giving everyone admin access.

By the end, you can…

  • Tell account identity, project access, token access, and rules apart.
  • Choose the access a person or job actually needs.
  • Find why the website works while terminal Git fails.

Why “I can open the page” is not enough

You can read a public project without being allowed to push changes to it. You may also be signed into one account in your browser and using another account’s key in your terminal.

Authentication = proving who you are

A sign-in, SSH key, or token tells GitHub which person or app made the request.

Authorization = deciding what you may do

GitHub checks whether that account or app can read, push, merge, or change settings.

Token = a key with limits

A personal access token is a secret used instead of an account password for supported operations. It can allow only certain projects and actions. It cannot give its owner access they do not already have.

Organizations may add sign-in approval, allowed-network rules, or token approval. A private project can appear as “not found” when your terminal account lacks access.

Pick a role for the work

Role in an organization projectCommon useLimit to remember
ReadRead code and join discussions.No direct code pushes.
TriageHelp sort issues and PRs.Does not give code-push access.
WritePush changes and merge when rules allow.Does not give full settings control or automatic rule bypass.
MaintainDo more project upkeep.Some sensitive settings remain restricted.
AdminManage access and sensitive settings.Organization rules and branch rules can still apply.

These are organization repository roles. Personal projects use an owner/collaborator model. Some plans support custom roles. A person may receive access directly, through teams, or through organization defaults; removing one grant may leave another.

A token cannot replace missing project access

Maya needs to send a code change

A picture to explore. These buttons do not run commands on your computer.

  1. Step 1

    Before: Maya has Read

    Her token asks for Contents: write, but her account only has Read on this project. GitHub refuses the push.

    Checks
    Account access: Read → cannot push
Token: Contents write → still cannot add account access

  2. Step 2

    Give the account the needed role

    An authorized owner grants Write for this task. The token also needs this repository selected and Contents: write.

    Checks
    Account access: Write
Token: correct repo + Contents write

  3. Step 3

    Follow the branch rule too

    If main requires PRs, Maya still cannot push directly to main. She can push a feature branch and open a PR.

    Result
    Feature push: allowed if other policies pass
Direct main push: blocked by required PR

Use the right kind of key

MethodWhat it is forWhat to inspect
HTTPS with a credential manager or GitHub CLIA person working from a terminal.The account it is signed in as and the project it can reach. Store credentials in the supported secure store.
SSH keyGit access using a registered public key.Which private key your SSH agent chooses; register only its public part. Organization sign-in approval may also be needed.
Fine-grained personal tokenA user token limited to selected projects and actions.Owner, repository selection, permissions, expiry, and required organization approval. Check current support limits.
Classic personal tokenAn older token type needed for some uses.Its broader scopes and organization restrictions; keep access as small as possible.
GitHub App tokenAn installed service doing project work.Which projects the installation can use, its actions, and when the token expires.
Deploy keyAn SSH key for one repository.Read-only or write-enabled. Anyone holding its private key may keep that access until the key is removed.
GITHUB_TOKENA built-in key for an Actions job.Job/workflow permissions and the event that started the run.

Never paste a token into a remote URL, source file, screenshot, or chat. If you expose it, revoke or replace it. Git commit name/email settings label commits; they do not sign you in.

Check access in a clear order

  1. Check the address

    Confirm the owner and project, without printing any token.

    Type this in your terminal
    git remote -v

    What you should see: The intended address is listed without secrets.

  2. Check which account your terminal uses

    For HTTPS, use your credential manager or gh auth status if GitHub CLI is installed. For SSH, ssh -T git@github.com reports the recognized account; a successful GitHub greeting may still return a nonzero shell status.

    What you should see: The account is the one that has the project access.

  3. Check the project grant and key limits

    Ask the project owner to check the needed role. For a fine-grained token, check the correct owner, selected repository, Contents permission, expiry, and approval.

    What you should see: Both the account and the key allow the intended action.

  4. Read the exact branch-rule error

    A GH006 or GH013 message may say a PR, signature, review, or check is needed.

    What you should see: Use the required route. Increasing token access does not remove branch requirements.

  5. Verify the intended action

    Test in a permitted practice project or branch.

    Type this in your terminal
    git ls-remote origin

    What you should see: A read succeeds. This proves read access only; a permitted feature-branch push separately checks write access.

Common access failures

What happened?What to checkWhat to do, then check
Repository not foundOwner/project spelling and terminal account.Correct the address or account/project selection, then try a read again.
Permission denied (publickey)Chosen SSH key, loaded agent keys, and public-key registration.Use the intended registered key and complete organization approval where needed. Never print the private key.
403 / resource not accessibleToken expiry, selected project, permission, approval, and organization policies.Change only the missing access needed for the task, then retry that action.
Cannot update .github/workflowsOrdinary content-write access plus workflow-file permission.Use the appropriate Workflows permission or classic workflow scope, then satisfy review rules.
Person left, but a job still has accessOther teams, direct grants, deploy keys, apps, and saved tokens.Remove or replace the credentials that should no longer work, then verify the old access fails.

What to remember

  • Check who the terminal signs in as before changing permissions.
  • An account role, a token’s limits, and a branch rule all matter.
  • Give the access needed for the task, then test what should succeed and what should stay blocked.
