Module 13 / 23 · about 40 minutes

GitHub identity, roles & permissions

Understand who you authenticate as, which repository actions that identity can perform, and why a powerful token cannot grant missing access.

By the end, you can…

  • Distinguish authentication, authorization and branch policy.
  • Choose the least repository role and credential scope for a task.
  • Diagnose access failures without escalating everything to admin.

An operation passes several independent gates

IdentityWhich person, app or deploy key?
→
Resource accessCan that identity reach this repo?
→
Credential scopeDoes this credential allow this operation?
→
Organization policyApproval, SSO, network and token restrictions
→
Branch rulesPR, review, checks, signatures, bypass

Authentication proves which identity is making a request. Authorization determines what that identity may do. Branch and repository rules add conditions to otherwise authorized changes. A valid token can still receive a rejection because its repository selection, permission scope or applicable policy does not allow the action.

Public visibility generally permits reading published code without becoming a collaborator. It does not permit direct pushes. A private repository may appear as “not found” when the current credential lacks access. Internal visibility is an enterprise concept, not a synonym for private.

Organization repository roles

RoleTypical responsibilityImportant limit
ReadRead code and participate in discussion/review.No direct code pushes.
TriageManage issue/PR triage without code-writing privileges.Does not grant push access.
WriteContribute code, review and merge when rules permit.Not full administration or automatic rule bypass.
MaintainBroader repository maintenance.Sensitive administration is still restricted.
AdminManage access and sensitive repository settings.Organization constraints and applicable rules still matter.

This table describes organization-owned repositories. Personal repositories use their own owner/collaborator model. Custom roles may exist on eligible plans. An organization owner has broader organization responsibilities; a billing role is not a generic code-write role.

Audit effective access from direct grants, teams and organization base permissions. Removing one team membership may not remove access granted elsewhere. Prefer team-based grants, a small admin group, appropriate base access and periodic review of outside collaborators.

Choose the credential for the job

CredentialTypical useWhat to inspect
HTTPS + supported credential manager / GitHub CLI loginInteractive developer access.Current account and secure credential storage; avoid credentials in remote URLs.
Personal SSH keyGit transport as your account.Public key registration, agent identity and any organization SSO authorization.
Fine-grained PATScoped user automation where supported.Resource owner, selected repositories, permissions, expiry and required approval.
Classic PATWorkflows not supported by fine-grained tokens.Broader scopes, organization restrictions and SSO authorization; minimize exposure.
GitHub App installation tokenInstalled integrations and service automation.Installation repository selection, app permissions and token lifetime.
Deploy keySSH access scoped to one repository.Read-only versus write-enabled; private-key holders may retain access independently of employee membership.
GITHUB_TOKENA workflow job’s built-in GitHub credential.Workflow/job permissions, event trust and organization/repository settings.

A PAT cannot make its owner more privileged than the owner already is. Fine-grained tokens add restrictions on top of that identity. Check current support limitations before choosing them for outside-collaborator or other specialized scenarios. Human offboarding also needs review of deploy keys, apps and automation credentials.

A deliberate access-grant procedure

  1. Identify the specific repository, environment and operation: read, push a feature branch, triage, administer, or deploy.
  2. Grant the least role through an appropriate team or scoped collaborator invitation. Check existing base and inherited access.
  3. Choose a supported credential mechanism. For a fine-grained token, choose the correct resource owner and selected repositories.
  4. Grant the operation’s required permission. Ordinary Git writes need suitable Contents access; modifying workflow files can require Workflows permission (or the classic workflow scope).
  5. Set a suitable expiration and complete organization approval/SSO requirements where applicable.
  6. Test an allowed operation and an intentionally denied operation using a non-admin account.
  7. Record an owner, review date and revocation path for automation credentials.

Do not copy a PAT into shell history, source code, a remote URL, screenshots or chat. Prefer a supported secure credential store. If a credential is exposed, revoke or rotate it promptly; deleting its visible text is not sufficient.

A permission failure is a clue, not a reason for admin

SymptomInspect first
Authentication failed / Permission denied (publickey)Credential validity, transport, selected SSH key and which account it authenticates.
Repository not foundOwner/repo spelling, account identity, private-repo access, selected token repositories.
403 / resource not accessibleToken permission, app installation access, organization approval/SSO/IP rules and endpoint requirements.
Push blocked with GH013/GH006 or policy detailThe named repository/branch rule, required PR/checks/signatures and bypass eligibility.
Cannot update .github/workflowsWorkflow-specific credential permission as well as Contents write and branch rules.
UI can view repo but terminal cannotThe browser session and terminal credential may represent different identities.

Read the server’s specific error. A missing credential permission is different from a branch rule intentionally blocking direct pushes. The visual permission lab lets you vary these gates without changing any actual account.

Pause and test your understanding

Remember in 30 seconds

  • Identity, repository role, credential scope and rules are distinct gates.
  • A token restricts the owner’s access; it does not create extra authority.
  • Grant the narrowest access and verify both allowed and denied actions.
