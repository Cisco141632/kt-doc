Something went wrong: check and fix it

Find the message you see. Learn why it can happen, what to check first, how to fix it, and how to confirm the result.

Need help with HEAD, index, staging, or diff?
Your file
What you are editing now. Git calls the project files the working tree.
Staging area = index
The file content you chose for the next commit. These are two names for one place.
HEAD
Tells Git which saved commit you are using, usually through your current branch.
Diff
A comparison showing added and removed lines between two versions.
Watch these change with one file →

By the end, you can…

  • Read the exact error before choosing a fix.
  • Keep useful files and commits while investigating.
  • Check that the fix kept both your work and your teammate’s work.

Start with these checks

“Rejected” can mean a history problem, a sign-in problem, or a branch rule. The right fix depends on the full message.

  1. Read the current state

    Find the current branch and any paused operation.

    Type this in your terminal
    git status

    What you should see: You know whether Git is waiting for a merge/rebase decision or just showing file changes.

  2. Read changes not yet saved in a commit

    These commands only show differences; they do not replace files.

    Type this in your terminal
    git diff
git diff --staged

    What you should see: You can separate edits in your files from content chosen for the next commit.

  3. Inspect branch links and saved history

    This is a local view. Fetch when you need newer remote information.

    Type this in your terminal
    git branch -vv
git log --graph --oneline --decorate --all -20

    What you should see: You can see branch names and the commits they currently point to.

  4. Choose the matching case below

    If work seems lost, stop cleanup and preserve what you find.

    What you should see: The fix matches the cause. Check the stated final result afterward.

30 problems with checks and fixes

remote Push rejected: non-fast-forward

Why it can happen

The server has work your proposed branch history does not include, or you changed commits already shared.

  1. Check first

    Run git fetch origin, then git log --left-right --graph --oneline HEAD...origin/feature for the relevant branch.

  2. Fix the cause

    Read and combine the needed teammate changes, test, then push normally. For an agreed history replacement, follow the exact-ID lease lesson.

  3. Check that it worked

    Both sets of needed changes are present. The server accepts the intended update.

remote Force-with-lease rejected

Why it can happen

The server branch is no longer at the commit ID you expected.

  1. Check first

    Fetch and compare the new last server commit with your saved expected ID.

  2. Fix the cause

    Read the new commits and agree how to keep them. Do not merely change the expected ID and repeat the same replacement.

  3. Check that it worked

    The final files keep both people’s needed work, and the shared history matches the agreement.

workflow I committed on the wrong branch

Why it can happen

You saved a commit while using a different branch from the one you intended.

  1. Check first

    Read git status, git branch --show-current, and git show HEAD. Check whether you already pushed it.

  2. Fix the cause

    First keep the commit with git branch rescue/my-change. Then plan a private reset or a shared-history revert for the original branch.

  3. Check that it worked

    The wanted commit has a branch name and no shared work was silently replaced.

workflow Detached HEAD

Why it can happen

HEAD points directly to a saved commit instead of naming a branch.

  1. Check first

    Read git status and git log -1. Check whether you made useful new commits here.

  2. Fix the cause

    Before switching away, run git switch -c keep-my-work with an unused branch name.

  3. Check that it worked

    You are on the new branch and the needed commits are still available.

recovery A reset or rebase made commits disappear

Why it can happen

The branch moved away from old commits. Those commits may still be stored locally.

  1. Check first

    Read git reflog --date=iso. Use git show on a possible old ID to check its contents.

  2. Fix the cause

    Give the correct found commit a rescue branch name, then compare before bringing work back.

  3. Check that it worked

    The wanted saved work is available and checked. Reflog cannot promise recovery of never-stored file text.

Why it can happen

The editor labels were read without checking which operation was running.

conflicts Rebase conflicts again in the same file

Why it can happen

More than one commit in the rebase changes the same file.

  1. Check first

    Run git rebase --show-current-patch to see the change being applied at this stop.

  2. Fix the cause

    Resolve this step’s needed change, add, check, test, and continue. Skip only a change checked as already present or unwanted.

  3. Check that it worked

    Rebase finishes and a comparison with the backup shows no accidental missing change.

recovery Stash pop left conflicts and still lists the stash

Why it can happen

Applying the saved edits did not finish cleanly, so the stash was kept.

  1. Check first

    Read status, git stash list, and git stash show. Keep any edits that existed before applying it.

  2. Fix the cause

    Resolve and check the combined edits, or undo only the attempted application after saving earlier work. There is no stash --abort.

  3. Check that it worked

    The wanted edits are present. Drop a saved entry only after checking the result.

files A file in .gitignore still changes in Git

Why it can happen

Git already tracks the file. Ignore rules do not remove tracked files.

  1. Check first

    Use git ls-files -- path for the actual file, and git check-ignore -v -- path where appropriate.

  2. Fix the cause

    If the file should leave tracking but stay on disk, review git rm --cached -- path and commit the removal. Handle any old secret separately.

  3. Check that it worked

    The file is no longer tracked in the new commit; required safe example settings remain.

security A token was committed

Why it can happen

The password or token may still be in old commits or other copies.

  1. Check first

    Find the credential owner, allowed actions, and signs of use without sharing its value further.

  2. Fix the cause

    Disable or replace it first. Then follow the provider’s incident steps and the GitHub old-history cleanup guide.

  3. Check that it worked

    The old credential no longer works. Record the cleanup and how you will avoid repeating it.

remote Current branch has no upstream

Why it can happen

Your local branch has no saved remote branch to follow.

  1. Check first

    Read git branch -vv and git remote -v. Confirm the intended branch and address.

  2. Fix the cause

    For a new feature branch, use git push -u origin feature with the actual branch name. For an existing branch, set the intended tracking link.

  3. Check that it worked

    git branch -vv shows the expected remote branch. No force push is needed.

  3. Check that it worked

access Permission denied (publickey)

Why it can happen

SSH selected a key GitHub does not recognize or does not allow for this project.

  1. Check first

    Check the selected key, SSH agent, registered public key, and any required organization approval. Never print the private key.

  2. Fix the cause

    Load/register the intended key and complete required approval, or use the approved HTTPS login setup.

  3. Check that it worked

    GitHub recognizes the intended account; separately check that account’s repository access.

remote Refusing to merge unrelated histories

Why it can happen

The two histories have no shared starting commit, perhaps because the wrong projects were selected.

  1. Check first

    Check remote addresses and the first commits on both sides.

  2. Fix the cause

    Correct a mistaken address or clone. Use --allow-unrelated-histories only for an intended, reviewed combination of independent projects.

  3. Check that it worked

    The final history contains the projects you meant to combine.

Why it can happen

The test may vary between runs or may classify a setup failure as the product bug.

Revert changed the files but kept the old merge links in history.

workflow index.lock exists

Why it can happen

Another Git process may be writing, or a stopped process may have left the lock behind.

  1. Check first

    Check running Git commands, open commit editors, and repository activity.

  2. Fix the cause

    Let active operations finish. Remove only a confirmed leftover lock when no process uses it; then read status.

  3. Check that it worked

    Git works normally without two processes writing at once or losing staging state.
