Branches and sharing with GitHub

Try work on a branch, send commits to GitHub, and bring a teammate’s changes back. See why fetch, pull, and push do different jobs.

Need help with HEAD, index, staging, or diff?
Your file
What you are editing now. Git calls the project files the working tree.
Staging area = index
The file content you chose for the next commit. These are two names for one place.
HEAD
Tells Git which saved commit you are using, usually through your current branch.
Diff
A comparison showing added and removed lines between two versions.
Watch these change with one file →

By the end, you can…

  • Explain a branch using a small history picture.
  • Connect a local project to the right GitHub repository.
  • Check new shared work before combining it with yours.

Names you will see

Branch

A name pointing to a saved commit. New commits move the name forward. You can work on a branch called add-title while main keeps the agreed project version.

Remote and origin

A remote is the saved address of another repository. origin is the usual name for that address. It is a name you can choose, not another word for GitHub.

origin/main

Your computer’s last known position of main on origin. It can be out of date. git fetch origin asks the other repository for updates.

Upstream

The remote branch your local branch is set to follow. git push -u sets that link. The name upstream is also often used for the original project when someone works from their own GitHub copy, called a fork.

Try an idea away from main

  1. Start from saved work

    In your practice project, finish or save any waiting changes first.

    Type this in your terminal
    git status

    What you should see: A clean working tree means no tracked-file changes are waiting.

  2. Make and enter a branch

    switch -c creates a branch and makes it your current branch.

    Type this in your terminal
    git switch -c add-title

    What you should see: Git reports that you switched to add-title. Both branches start at the same commit.

  3. Make a commit on the new branch

    Edit notes.txt to add a title. Save it, then choose and commit the change.

    Type this in your terminal
    git add -- notes.txt
git commit -m "Add a title"

    What you should see: add-title now points to a new commit. main stays at the earlier commit.

  4. Return to main and compare

    Git changes your tracked files to match the branch you enter.

    Type this in your terminal
    git switch main

    What you should see: The title is absent on main. git switch add-title brings it back. Neither saved version was deleted.

Put the practice project on GitHub

You need a GitHub account and Git installed. To sign in from your terminal, follow GitHub’s credential setup steps. A credential is the key or token that proves which account you are using. The GitHub website password is not used as the password for Git over HTTPS.

  1. Create the shared project on GitHub

    On GitHub, choose New repository. Name it git-notes-practice. Choose the visibility you want. Since you already have local commits, leave README, license, and .gitignore creation off here.

    What you should see: GitHub shows an empty repository with a Code address. Public means other people can read the published files.

  2. Save that address in your local project

    Copy the HTTPS or SSH address shown by GitHub. Replace REPOSITORY_URL below with it; do not type the placeholder or put a token in the address.

    Type this in your terminal
    git remote add origin REPOSITORY_URL

    What you should see: Usually no output. git remote -v should show the intended owner and project name.

  3. Send main

    Run this while main has the saved work you want to share. -u also links your local main to origin/main.

    Type this in your terminal
    git push -u origin main

    What you should see: Refresh the GitHub page. It shows the commits and files sent from main.

  4. Send your idea branch too

    The feature branch is separate from main on GitHub as well.

    Type this in your terminal
    git switch add-title
git push -u origin add-title

    What you should see: GitHub lists add-title. Sending it does not combine it into main.

If the project already exists on GitHub, start by copying it instead: git clone REPOSITORY_URL git-notes-copy, then cd git-notes-copy. Clone means make a local copy with Git history. It also sets origin. Use a new destination folder.

Your branch, your last check, and GitHub

A teammate saves a new commit T on GitHub

A picture to explore. These buttons do not run commands on your computer.

  1. Step 1

    Before you check

    Your local main and origin/main still say B. GitHub main has T. origin/main is a local note, so it does not update itself just because someone else pushed.

  2. Step 2

    Run git fetch origin

    Git downloads new history and updates origin/main to T. Your main and your edited files stay as they were.

  3. Step 3

    Use the new work

    With a clean main at B, run git merge --ff-only origin/main. Because T continues from B, main can move to T.

Choose the command for the job

CommandWhat it doesWhat it leaves alone
git fetch originDownload shared history and update your last-known positions.Your current branch and working files.
git pull --ff-onlyFetch, then move your branch forward only if no separate local commits need combining.It refuses if both sides have new commits.
git pull --no-rebaseFetch, then combine using a merge.It keeps existing commits; a new merge commit may be needed.
git pull --rebaseFetch, then make new versions of your local commits after the fetched work.It does not send the result back; it may pause for conflicts.
git pushAsk the other repository to accept your commits and update its branch.It does not download and combine a teammate’s new work for you.

Plain git pull can behave differently with different settings. While learning, fetch, inspect, and choose the next step. git branch -vv shows branch links and ahead/behind counts based on your last fetch. Ahead means local-only commits; behind means commits seen on the remote side but missing from your branch.

If push or pull is rejected

What happened?What to checkWhat to do, then check
Push says non-fast-forward.Someone may have pushed first. Run git fetch origin, then git log --graph --oneline --all.On a shared branch, inspect and merge the matching remote branch, test, then push normally. See the full fix.
Pull --ff-only refuses.Both sides have commits after their shared starting commit.Use the merge lesson, or use rebase only when suitable for that branch. Do not force a push to fix a local pull.
“No upstream branch.”Read git branch -vv and git remote -v.For add-title, use git push -u origin add-title. Check the destination first.
Remote origin already exists.Read git remote -v.If it is correct, keep it. If it is wrong, use git remote set-url origin REPOSITORY_URL with the address you checked, then inspect again.

Remove old branch names carefully

git fetch --prune origin removes your local records of remote branches that have been deleted. It does not delete a teammate’s live branch on GitHub. After your work is combined and checked, git branch -d add-title deletes your local branch name, with a check that its history is included in its upstream or the current branch. Switch away from that branch first.

-D skips that history check. After a squash merge, the files may be included even though the original commits are not; inspect before deleting. git push origin --delete add-title deletes the server branch. Use that only after the team is finished with it.

What to remember

  • A branch is a name for a saved commit; HEAD tells Git which one you are using.
  • Fetch checks for shared updates. Pull fetches and uses them. Push sends your commits.
  • origin/main is your last-known position, so fetch before relying on it.
