Module 05 / 23 · about 30 minutes

Branches, remotes, fetch, pull & push

Separate your branch, your cached view of the remote and the actual server branch.

By the end, you can…

  • Explain local branches, remote-tracking references and upstreams.
  • Recognize fast-forward and divergence.
  • Choose integration explicitly after fetching.

Three references that people confuse

NameWhere it livesWhen it changes
featureYour local branch, refs/heads/featureWhen you commit, merge, rebase or deliberately move it.
origin/featureA local remote-tracking referenceNormally updated by fetch, and sometimes by successful pushes; it can be stale.
feature on originThe actual branch on the serverWhen an authorized update is accepted there.
Shell example — read the context before running
git branch -vv
git remote -v
git fetch origin
git log --oneline --left-right HEAD...origin/feature

Ahead/behind counts describe ancestry against the local tracking reference, not a live request to GitHub. Fetch first when you need current information. A fork is a hosted repository relationship; a clone is your local copy. A fork workflow commonly names your fork origin and the parent project upstream, but those names are conventions.

Fetch gathers; integration changes your branch

FetchDownload reachable objects and update tracking refs
→
InspectCompare ancestry and intended changes
→
IntegrateFast-forward, merge or rebase deliberately
CommandEffect
git fetch originUpdates remote-tracking information according to refspecs; does not merge into the checked-out branch.
git pull --ff-onlyFetches, then requires a fast-forward integration; refuses divergent history.
git pull --rebaseFetches and rebases local work onto the selected upstream; may replay commits and stop for conflicts.
git pull --no-rebaseFetches and uses merge-based integration; may fast-forward or make a merge commit.

Do not assume every developer’s plain git pull behaves the same: version, branch config and user settings matter. A cautious learning default is git config --local pull.ff only; if it refuses, inspect and choose an explicit operation. Teams may deliberately standardize on another policy.

Why an ordinary push is rejected

When a teammate has pushed C and your local work is D, fetch, inspect and integrate the teammate’s change using the team’s merge or rebase policy. A normal push can then advance to a descendant that includes the shared work. If you intentionally rewrote your own published branch, use the separate force-push procedure after coordination.

Set the tracking relationship with git push -u origin feature, or inspect and set an upstream explicitly using git branch --set-upstream-to=origin/feature feature. Verify the branch exists. Never use force merely to repair a missing upstream or an authentication failure.

Pruning is not deleting teammates’ server branches

Shell example — read the context before running
git fetch --prune origin
git branch --merged main
git branch -d feature/completed

Pruning removes stale local remote-tracking references covered by the fetch refspec; normal branch pruning does not delete live server branches. Deleting a local branch with -d includes a merge-safety check, although “merged” depends on the tracked upstream or current branch. -D bypasses that check. git push origin --delete branch deletes a remote branch and requires an intentional team decision.

Before deleting, confirm the work is integrated as intended, especially after squash merges: patch content may be integrated even though the original commits are not ancestors of main.

Pause and test your understanding

Remember in 30 seconds

  • origin/feature is a local observation, not the live server branch.
  • Fetch first, then choose integration deliberately.
  • A non-fast-forward rejection is a history question, not an invitation to force.
