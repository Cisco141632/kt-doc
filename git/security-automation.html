Secrets, signatures & GitHub automation

Keep credentials out of history, separate trusted automation from untrusted contributions, and understand what verification proves.

By the end, you can…

  • Respond correctly to a committed secret.
  • Scope workflow tokens and protect privileged execution.
  • Distinguish signed commits, successful tests and trustworthy code.

A secret in Git requires credential action

Revoke / rotateInvalidate the exposed credential
→
AssessIdentify usage, scope and exposure
→
Coordinate cleanupHistory, refs, forks, clones and caches
→
Prevent repeatTemplates, scanning and secure stores

Deleting a secret from the latest file does not remove it from earlier commits. Even rewriting and force-pushing history cannot erase copies in other clones, forks, pull-request references or caches. Revoke or rotate first; then follow the provider’s incident process and GitHub’s sensitive-data removal guidance.

History cleanup with tools such as git-filter-repo changes commit IDs and disrupts collaborators. Plan repository backups that do not expose the secret further, coordinate replacement references and downstream clones, and involve GitHub Support where the documented cleanup process requires it. Do not promise that a single reset or force push makes a leaked token safe.

Workflow permissions belong to the job

Least-privilege workflow excerpt
# Excerpt from a GitHub Actions workflow, not a complete workflow.
permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    # Add reviewed checkout and test steps here.

GITHUB_TOKEN is provided for workflow jobs. Its effective permissions depend on repository/organization defaults, explicit workflow or job declarations, and event context. Specify only the permissions needed by each job. Giving the whole workflow write access because one release job needs it widens exposure unnecessarily.

When explicitly declaring permissions, unspecified permissions are generally set to none, with the documented metadata exception. A job that needs issue comments, package publishing or deployments should receive only the corresponding access. Prefer short-lived app or OIDC-based cloud credentials where appropriate rather than a long-lived human PAT stored as a broad automation secret.

Do not execute untrusted code with privileged credentials

Fork pull requests are untrusted input. Normal fork-PR workflows usually have restricted tokens and no ordinary repository secrets; repository settings can affect exceptions. pull_request_target runs in a trusted base-repository context. Fetching or checking out the contributor’s code and then running its tests/install scripts there can expose secrets or write access.

A build step, dependency install, configuration file or downloaded artifact can execute code. The risk is not limited to an obvious shell command in the PR. Keep untrusted validation separate from privileged release or labeling operations, and validate data passed between them. Follow current Actions event policies and security guidance rather than relying on an old template.

Pin third-party actions to reviewed full commit IDs and use a controlled update process. Treat PR titles, branch names and issue bodies as data; do not splice them directly into shell scripts. Use expression-safe environment passing and quoted shell variables. Protect workflow changes with appropriate review.

What a signature proves—and what it does not

A signed commit or tag binds an object to a signing key and allows verification according to the verifier’s trust rules. The author name/email fields alone are not proof of authorship. GitHub’s verification display depends on its supported signature types, identity association and policy.

A verified signature does not prove the code is correct, reviewed, malware-free or approved for deployment. Keep tests and human review. Rebase/amend changes objects, so an old signature cannot remain valid for a different replacement commit; sign replacements if the policy requires it.

Inspection — requires a signed object and correctly configured verification
git log --show-signature -1
git verify-commit COMMIT
git verify-tag TAG

Onboard signing keys and recovery/revocation procedures before enforcing signing across a team. Account 2FA, SSH authentication keys, signing keys and token scopes are related controls but serve different purposes.

Pause and test your understanding

Remember in 30 seconds

  • Rotate exposed credentials before considering history cleanup.
  • Untrusted code must not inherit privileged workflow secrets or write tokens.
  • A valid signature is evidence about an object and key, not proof of correctness.
