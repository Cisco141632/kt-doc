Passwords, job access, and signed commits

See what to do if a secret enters Git, how GitHub Actions gets access, and what a verified signature actually tells you.

If you commit a password or token

A secret is a password, private key, or token that gives access to something. Removing it in the next commit leaves the old value in earlier commits and possibly in other copies.

Revoke means disable the old credential. Rotate means replace it with a new one and stop using the old one. Do this first, then follow the service’s incident process. Removing old history with a tool such as git-filter-repo changes commit IDs and affects teammates. Coordinate all affected branches, tags, forks, clones, and cached views using the official cleanup guide. A force push cannot promise to erase every copy.

What is GitHub Actions?

GitHub Actions runs jobs described in a workflow file under .github/workflows/. A job can test code, build a file, or publish a release. GITHUB_TOKEN is a built-in credential supplied for the job. Its permissions decide which GitHub actions the job may perform.

Part of a workflow — this example is not a complete runnable workflow
permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    # Add reviewed checkout and test steps here.

contents: read allows reading repository content; it does not allow ordinary content writes. Grant write access only to a job that needs it. When you explicitly list permissions, unspecified permissions are generally none, except the basic repository information GitHub always permits. Organization settings and the event can reduce the effective access further.

For cloud access, a short-lived login using OIDC can avoid a long-lived cloud key. OIDC lets the cloud provider check the identity of a particular job before issuing limited access. Configure the accepted project, branch, and job context carefully.

A test job can run someone else’s code

A contribution from a fork may change a build command, package install script, or test. Running it means running the contributor’s code. Normal fork PR jobs usually have restricted tokens and no ordinary repository secrets, though settings can change exceptions.

pull_request_target runs in the trusted base project’s context. Checking out the contributor’s code and running its build there can expose secrets or write access. Keep untrusted tests apart from jobs that can publish or change protected resources.

What does “Verified” mean?

A signature links the exact commit or tag to a signing key. Verification checks that link under the service’s rules. Author name and email fields alone do not prove who made a change.

EvidenceWhat it tells youWhat it does not prove
Verified signatureThe object matches an accepted signing key under the verifier’s rules.That the program is correct or safe.
Passing checkA particular job reported success for a revision.That every possible test passed.
ApprovalA reviewer accepted the change they reviewed.That all automated checks passed or that no later change needs review.
Use a real signed commit/tag and a configured verifier
git log --show-signature -1
git verify-commit COMMIT
git verify-tag TAG

Rebase or amend creates new objects. An old signature cannot verify a different replacement commit; sign replacements when needed. Account two-factor sign-in, SSH access keys, and signing keys serve different jobs.

What to remember

  • Disable an exposed secret first; deleting the latest text is not enough.
  • Give each job only the access it needs, and keep untrusted code away from powerful credentials.
  • A signature, passing test, and human approval are different kinds of evidence.
