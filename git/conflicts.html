Fix a conflict, one file at a time

A conflict means Git needs your help choosing the final file. Read both changes, edit the result, and finish the right operation.

Need help with HEAD, index, staging, or diff?
Your file
What you are editing now. Git calls the project files the working tree.
Staging area = index
The file content you chose for the next commit. These are two names for one place.
HEAD
Tells Git which saved commit you are using, usually through your current branch.
Diff
A comparison showing added and removed lines between two versions.
Watch these change with one file →

By the end, you can…

  • Read conflict markers and the original three versions.
  • Keep the needed changes from both people.
  • Check, continue, or stop a merge or rebase correctly.

First find out what paused

A conflict means Git could not choose some part of the combined result. Your saved commits are still there. It is common when two people edit the same lines differently. It can also happen when one deletes a file and another edits it.

Start with this report
git status

Read whether it says merge, rebase, cherry-pick, or revert. Those operations have different finish and stop commands. List files needing a choice with git diff --name-only --diff-filter=U. Here U means unmerged: Git is waiting for you to resolve the file.

Read the marks in the file

Example text in a conflicted file — do not type this as commands
<<<<<<< HEAD
timeout = 20
||||||| base
timeout = 10
=======
timeout = 30
>>>>>>> feature

In a merge done while on main, the first block is main’s value, 20. The base block shows the old value, 10. The last block is feature’s value, 30. You need to decide the correct value; Git cannot know the project’s rule.

The base block appears when you set git config --local merge.conflictStyle diff3 before a new conflict. Some editors show only the first and last blocks. In all cases, remove the marks after writing the intended result.

Ours and theirs during a merge

Ours means the branch you are on; theirs means the branch you are merging into it.

Ours and theirs during a rebase

Ours means the new starting branch plus changes already copied onto it. Theirs means the original commit being copied now. The labels can feel reversed, so read the actual content.

Git also keeps the conflict versions in numbered index entries. Run git show :1:config.json for the base, git show :2:config.json for ours, and git show :3:config.json for theirs. Some versions may be absent, for example when a file was newly added or deleted. git ls-files -u lists these entries.

Build one correct file

In lab 4, the team requires timeout 20 from main and retries 3 from feature. JSON is a settings format using named values inside braces. Neither whole branch has both required values.

Before
Two sides
Main:    timeout 20, retries 1
Feature: timeout 30, retries 3
→Read the requirement and edit
After
Final config.json
{"timeout": 20, "retries": 3}

  1. Read both changes and the rule

    Use the file versions above, commit messages, and the task description. If two rules disagree, ask the people responsible for the change.

    Type this in your terminal
    git status
git diff

    What you should see: You know what each side tried to change and what the final file should do.

  2. Edit and save the final file

    In your editor, write one valid result. Remove conflict markers and duplicate settings.

    What you should see: config.json has timeout 20 and retries 3, with one of each key.

  3. Tell Git you resolved this file

    Add chooses your edited result and replaces the unresolved entries for this file.

    Type this in your terminal
    git add -- config.json

    What you should see: Status no longer lists config.json as unmerged.

  4. Check the chosen result

    --cached is another name for --staged. --check can catch leftover markers and whitespace errors, but cannot prove the settings are correct.

    Type this in your terminal
    git diff --staged
git diff --staged --check
git diff --name-only --diff-filter=U

    What you should see: The chosen changes are intended. The unresolved-file command prints nothing after all files are fixed. Run the project tests too.

  5. Finish the merge

    Use this only when status says a merge is in progress. For a rebase, use git rebase --continue instead.

    Type this in your terminal
    git merge --continue

    What you should see: The merge completes. Read status and test the final files.

Try to answer: Why can “Accept both” be wrong?

It can keep two incompatible values, duplicate a function, or make invalid JSON. Keep the required behavior, then check the file format.

Other conflicts use the same careful process

ConflictWhat to decideHow to finish the file
Deleted on one side, edited on the otherShould the final project still have this file?Use git rm -- filename for the intended deletion, or keep/edit the file and add it.
Both sides added the same file nameWhich combined contents should exist?Read both complete files, create one result, and add it. A base version may not exist.
File renamed differentlyWhat should the final name be?Check both names and code using them. Keep the intended paths and stage the changes. Git detects renames by comparing content.
Image or other binary fileWhich real file is the correct result?Choose or rebuild it, open it in its program, then add it. Text markers may be unavailable.
Dependency lockfileWhich package changes were intended?Resolve the package list first, then rebuild the lockfile with the project’s required package-manager version. Review and test.
Generated fileWhich source input should produce it?Resolve the input, generate the output again, and review it.
No text conflict, but the program breaksDid the combined changes make different assumptions?Check the failing behavior and both changes. For example, a function rename and an old caller can merge cleanly but fail when run.

Finish or stop the operation named by status

OperationContinue after fixing and addingStop and return
Mergegit merge --continuegit merge --abort
Rebasegit rebase --continuegit rebase --abort
Cherry-pickgit cherry-pick --continuegit cherry-pick --abort
Revertgit revert --continuegit revert --abort
Stash apply or popResolve, add, and decide when to commit.There is no stash --abort. Preserve earlier edits before undoing the attempted application.

--skip in a rebase or cherry-pick leaves out a commit’s change. Use it only when you have checked that the change is already present or should be dropped. A whole-file command such as git restore --ours -- config.json can drop useful content from the other side.

What to remember

  • A conflict asks you to choose the correct final content.
  • Check whether you are merging or rebasing before using ours and theirs.
  • Edit, add, check, test, then use the matching continue command.
