Module 06 / 21 · about 45 minutes

Resolve conflicts without losing intent

Follow a repeatable conflict-resolution procedure and learn what the editor’s buttons actually choose.

By the end, you can…

  • Identify the operation and conflict stages.
  • Build the intended combined result and validate it.
  • Handle text, delete/modify, rename, binary and generated-file conflicts.

Stop and identify the operation

Shell example — read the context before running
git status
git diff --name-only --diff-filter=U
git ls-files -u
git diff

A conflict means the operation paused because Git could not finish some decisions automatically. It does not mean your repository is corrupted. First read whether this is a merge, rebase, cherry-pick, revert or stash application. Their continue and abort commands are different.

List all unresolved paths, then read each branch’s intent: issue, commit message, surrounding code and tests. If two changes encode incompatible requirements, talk to the owners. A merge tool can edit text; it cannot decide which business behavior is correct.

Read all three versions

Example diff3 conflict markers — not a shell command
<<<<<<< HEAD
timeout = 20
||||||| base
timeout = 10
=======
timeout = 30
>>>>>>> feature

The marker labels depend on the operation. For a normal merge, HEAD/current is your checked-out branch and incoming is the branch being merged. git config --local merge.conflictStyle diff3 includes the base in newly produced conflict markers. zdiff3 is another useful style on supported Git versions.

Inspect unmerged index stages for this path
git show :1:settings.txt
git show :2:settings.txt
git show :3:settings.txt

Stage 1 is the base, 2 is ours and 3 is theirs. Some stages are absent for add/add or delete/modify conflicts. During a rebase, ours is the new base plus already replayed commits; theirs is the commit currently being replayed. Do not equate ours with “my original feature branch” in every operation.

“Accept current,” “Accept incoming,” and “Accept both” usually choose text mechanically. Accepting both may duplicate functions, create invalid JSON or combine two mutually exclusive values. Inspect the labels and construct the intended final content.

The resolution loop

UnderstandRead base, both changes and requirements
→
EditProduce one correct final result
→
StageMark each resolved path with add or rm
→
ValidateInspect the staged diff and test behavior
→
ContinueUse the operation-specific command
Shell example — read the context before running
git add -- settings.txt
git diff --cached
git diff --cached --check
git diff --name-only --diff-filter=U
# Run the relevant tests, then use ONE matching operation:
# git merge --continue
# git rebase --continue
# git cherry-pick --continue
# git revert --continue

Staging says “this is my resolution,” not “this is correct.” Removing conflict markers is only one check. The unresolved-path list must be empty before continuing, and the staged diff must preserve the intended changes. A rebase can stop again at the next replayed commit; resolve each stop in context.

Be precise with ours/theirs shortcuts

git restore --ours -- path or --theirs chooses an entire side from the unmerged index for that path. It can discard useful changes from the other side. During rebase the labels are particularly easy to misread. Prefer manual intent-based editing when both changes matter.

Conflicts beyond a few lines

TypeA careful resolution
Delete/modifyDecide whether deletion or continued existence matches the feature. Use git rm for the intended deletion, or restore/edit and git add the retained file.
Add/addBoth sides introduced the path. Compare complete contents and build one valid file; there may be no base stage.
Rename/rename or rename/deleteInspect old/new paths and callers. Decide the final name and update references; Git rename detection is inferred from content.
BinaryA text merge is not available. Choose or regenerate a known correct artifact, verify it in its application and stage it.
LockfileResolve source manifests, use the project’s pinned package-manager version to regenerate the lockfile as documented, inspect and test. Do not blindly choose one side or delete the lockfile.
Generated codeResolve source-of-truth inputs, regenerate consistently, review the generated diff and test.
Whitespace / line endingsCheck .gitattributes and normalization policy. Avoid mixing a mass normalization with a functional conflict fix.
Semantic conflictText merged cleanly but APIs or assumptions disagree. Only review and behavioral tests reveal it.

Know how to stop safely

OperationStop / recover
Merge in progressgit merge --abort.
Rebase in progressgit rebase --abort; --quit has different semantics and leaves current state.
Cherry-pick / revertgit cherry-pick --abort or git revert --abort.
Stash apply/pop conflictThere is no git stash --abort. Preserve existing work, inspect status and the retained stash, then restore only the intended tracked paths or use a clean worktree.
Need to skip a rebase/cherry-pick step--skip drops that commit’s replay from the sequence. Use only when you have verified the change is already present or deliberately unnecessary.

Do not respond to conflict fatigue with reset --hard. Copy important uncommitted files outside the repository if necessary, record the operation state, and prefer the matching abort command. Reuse resolutions with rerere only after understanding and reviewing what it reapplies.

Pause and test your understanding

Remember in 30 seconds

  • Identify the operation before interpreting current/incoming.
  • Resolve intended behavior, not just the visible markers.
  • Inspect the staged result, test, then continue or abort deliberately.
