What is a pull request?

A pull request, often shortened to PR, is a page asking to put one branch’s changes into another branch. It shows the changed files, discussion, and test results. Opening it does not put the changes into main.

Base branch

The branch you want to receive the changes, often main.

Head branch

The branch holding the proposed changes, such as add-title. This GitHub label is different from the all-capitals Git name HEAD.

Review

A person reads the change and may approve it or ask for fixes.

Check

A reported result from an automated job, such as tests. A passing check only covers what that job actually tested.

Open and finish a small pull request

  1. Send your idea branch

    Use the add-title branch from the sharing lesson. Check its saved changes first.

    Type this in your terminal
    git switch add-title
git push -u origin add-title

    What you should see: GitHub now has that branch.

  2. Choose the correct branches on GitHub

    Open Pull requests → New pull request. Set base to main and compare/head to add-title.

    What you should see: Files changed shows just the title change you meant to propose.

  3. Explain the change

    Use a clear title such as “Add a title to the notes.” In the description, say what was wrong, what changed, and how you checked it. Use Draft if it is still unfinished.

    What you should see: A reviewer can understand the change without reading your private chat.

  4. Read feedback and checks

    Open the Files changed and Checks views. If a test fails, open that job and read the first useful error. Confirm it ran for your latest commit.

    What you should see: You know what needs fixing and what already passed.

  5. Make follow-up commits on the same branch

    Edit, test, add, commit, and push. The existing PR updates automatically.

    Type this in your terminal
    git push origin add-title

    What you should see: The new commit appears in the same PR. Rules may ask for fresh approval.

  6. Merge when the required work is complete

    Use the method your team chose. Review approvals, required checks, and unresolved concerns before merging.

    What you should see: The PR says Merged. Main contains the accepted result.

  7. Update your local main

    Start with saved work. Fetch the accepted result and move your clean main forward.

    Type this in your terminal
    git fetch origin
git switch main
git merge --ff-only origin/main

    What you should see: Your local main contains the change. Start the next task from a fresh branch here.

Try to answer: A reviewer approved, but a required test failed. Is review complete?

The human review and automated check are separate. Under a rule requiring that check, the failure must be fixed before a normal merge.

If you cannot push to the original project

A fork is your own GitHub copy of a project, where the project allows it. A clone is a local copy on your computer. Clone your fork, and keep origin pointing to it. Save the original project address under a name such as upstream.

Replace the URL with the original project address; use its actual default branch
git remote add upstream PARENT_REPOSITORY_URL
git fetch upstream
git switch -c my-fix upstream/main

Make your commits, push my-fix to origin, then open a PR with the original project as base and your fork/my-fix as head. Proposing a PR does not give you permission to merge it.

How to make a review useful

Keep unrelated changes separate. Include screenshots for a visible change and test results for program changes. If you rewrote the PR branch, give reviewers a range-diff comparison so they can see what changed during the rewrite.

An issue tracks a task or problem. A tag names a saved version. A GitHub release adds notes and downloads around a tag. Merging, releasing, and deploying a running program are separate actions.

CODEOWNERS is a file telling GitHub which people or teams should review certain paths. Rules decide whether that approval is required. A merge queue tests several approved changes in the order they will enter main. Its workflows may need the merge_group event to report the required results.

What to remember

  • A PR asks to combine a head branch into a base branch.
  • A push, an approval, a passing check, a merge, and a deployment are separate steps.
  • After merging, update main and start the next task on a fresh branch.
