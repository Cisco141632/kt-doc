Module 11 / 21 · about 30 minutes

GitHub pull requests & team integration

Connect local Git habits to reviews, checks, merge methods and clear collaboration.

By the end, you can…

  • Understand repositories, forks, pull requests and review roles.
  • Choose a consistent integration method.
  • Write a useful handoff and improve practical skills.

From issue to reviewed integration

A pull request is a discussion and proposed integration between a head branch and a base branch. Opening one does not merge it. A draft signals that feedback is welcome but review is not yet ready. A fork lets a contributor propose changes without direct write access to the parent repository, subject to visibility and forking policies.

Issues track work; branches hold references; pull requests review changes; releases describe published versions. A Git tag and a GitHub release are related but separate objects. GitHub Actions can run checks or deployments, but merging alone does not guarantee a deployment happened.

Open, update and finish a pull request

  1. Fetch the intended base. With a clean working tree, create your feature branch from the inspected base, for example git switch -c feature/login-fix origin/main.
  2. Make a focused change, test it, inspect staged content and commit. Push with git push -u origin feature/login-fix.
  3. On GitHub, use the proposed Compare & pull request link, or Pull requests → New pull request. Verify both base repository/branch and head repository/branch.
  4. Read Files changed and Commits before creating the PR. Select Draft if the work is still in progress. Add the problem, resulting behavior and validation, then request appropriate reviewers.
  5. Push follow-up commits to the same head branch to update the PR. Inspect checks, resolve review threads with evidence, and obtain fresh review when required.
  6. Resolve any base-branch conflicts using the team’s merge/rebase policy. Re-test the result and follow the published-history rules if a rewrite is involved.
  7. Merge using the approved method once required gates pass. Fetch the result locally, update your clean main with git merge --ff-only origin/main, and verify before cleaning up the completed feature branch.
Fork contribution

If you cannot push to the parent project, create a permitted fork, clone your fork, and add the inspected parent URL as a remote named upstream. Fetch upstream, branch from upstream/main (or the actual base), push your feature to origin, and open a PR with the parent as base and your fork as head. Permission to propose a PR is different from permission to merge it.

Fork workflow — assumes origin is your fork and main is the intended parent base
git remote add upstream APPROVED_PARENT_URL
git fetch upstream
git switch -c feature/contribution upstream/main
# Edit, test, stage and commit, then:
git push -u origin feature/contribution

GitHub’s Files changed, commit pages, and file History/Blame views complement local investigation. Preserve an exact commit link when discussing evidence: a branch URL can show different content after the branch moves. GitHub Actions shows job logs and the tested commit; a green check on a different revision is not proof that the latest change passed.

Give the reviewer useful evidence

Describe the concrete problem and resulting behavior. Include the relevant tests, screenshots for UI changes, migrations, compatibility effects and a rollback plan when appropriate. Keep unrelated cleanup separate. A good review asks whether the change fulfills its requirements, handles failures and remains maintainable.

Respond to comments with the implemented result or your reasoning. Do not mark unresolved behavioral concerns as solved merely to enable the merge button. New commits can invalidate approvals under team rules. Required checks may run against a commit or proposed merge result; inspect which revision was tested.

Merge optionWhat reaches the base branchTeam consideration
Create a merge commitRetains branch ancestry with a merge boundary.Useful when individual commits and the integration event matter.
Squash and mergeOne combined commit with a single parent.Good for one feature per PR; old feature commits are not ancestors of the squash commit.
Rebase and mergeLinear replay of the commits onto the base.GitHub creates new commit IDs and updates committer information; do not equate it with every local fast-forward scenario.

After a squash or GitHub rebase merge, start new work from updated main instead of extending the old feature branch indefinitely. Otherwise later PRs can contain surprising comparisons or require careful retargeting. The best merge method is the one your team can review, audit and recover consistently.

Rules are part of the workflow

Agree who may rewrite a feature branch, who reviews sensitive code, how emergency fixes proceed, and what “done” means. Preserve shared main/release history and use reviewed corrective commits. If a contributor needs to rewrite a published personal PR branch, notify reviewers and retain enough evidence to compare the patch series.

CODEOWNERS can request domain reviewers; enforcement requires a corresponding rule. A maintainer or bot’s permission is not an automatic bypass of all applicable controls. A merge queue, where available, tests integration combinations under busy traffic; required workflows need the appropriate merge-group trigger to provide checks for queue commits.

Practise a short incident, then explain the graph before and after without looking at the commands. Review one real PR’s history with a teammate. Prefer small frequent changes, early integration, testable commits and a shared glossary over memorizing a long alias list.
