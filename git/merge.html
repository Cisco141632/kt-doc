Merge: put two sets of work together

See how Git uses the shared starting version to combine changes. Learn what to check when the merge finishes.

Need help with HEAD, index, staging, or diff?
Your file
What you are editing now. Git calls the project files the working tree.
Staging area = index
The file content you chose for the next commit. These are two names for one place.
HEAD
Tells Git which saved commit you are using, usually through your current branch.
Diff
A comparison showing added and removed lines between two versions.

  • Explain a simple merge with before and after pictures.

One project, two useful changes

Your settings file starts with timeout 10 and retries 1. Timeout is how long a request waits; retries is how many times it tries again. On main, you increase timeout to 20. On feature, your friend increases retries to 3. You want both changes.

Base

The saved version both branches started from. It tells Git what each person changed.

Parent

An earlier commit recorded by a commit. Most commits have one parent; a normal merge commit records two.

Fast-forward

Git can move a branch name to an existing later commit when there is no separate work on that branch to combine.

VersionTimeoutRetriesWhat changed?
Base B101Starting values.
Main C201Only timeout changed.
Feature D103Only retries changed.
Merge M203Both changes kept.

This is called a three-way merge because Git reads the base and the two branch versions. Reading only the last two files would not show who changed which value.

Try a real merge in lab 3

Create the practice folders first. Open a terminal in its 03-three-way folder. This setup already has the two changes.

  1. Read the starting state

    Finish or save unrelated edits before merging.

    Type this in your terminal
    git status
git log --graph --oneline --all

    What you should see: Main and feature have separate commits. The tracked files are clean.

  2. Find the starting commit

    This prints the commit ID Git uses as their common starting point.

    Type this in your terminal
    git merge-base main feature

    What you should see: One ID. In a complicated history there can be more than one suitable common base.

  3. Combine feature into your current branch

    In this lab you are on main. If an editor opens for the merge message, save and close it.

    Type this in your terminal
    git merge feature

    What you should see: Git reports a merge. If it reports conflicts, use the next lesson before continuing.

  4. Read both values and the history

    Check content as well as the new commit links.

    Type this in your terminal
    cat timeout.txt retries.txt
git show --no-patch --pretty="%h %p %s" HEAD

    What you should see: The values are 20 and 3. The line from show has the new ID, two parent IDs, and the message.

For a real program, also run tests covering both changes together. A merge can combine text successfully while combining behavior incorrectly, such as a renamed function whose callers still use its old name.

When no new merge commit is needed

Before
→On main: git merge --ff-only feature
After

--ff-only means “only do this if moving the branch name is enough.” A later date alone is not enough. The old main commit must be in the earlier history of feature.

Three ways to keep the result

MethodSaved resultWhat to remember
Normal mergeKeeps both histories; may fast-forward or add a two-parent commit.--no-ff asks for a merge commit even when a simple move would work.
Squashgit merge --squash feature chooses the combined changes. You inspect and commit them separately.The new commit has one parent. It does not link the feature commits as a second parent.
Rebase, then combineMakes new copies of the feature changes after a newer base.Commit IDs change. Read the rebase lesson before using this on work others have seen.
Try to answer: Does a squash mean Git remembers feature as a merged parent?

No. It saves combined file changes in one new commit, with one parent. The files can match while the history links differ.

When the merge needs help

What happened?What to checkWhat to do, then check
Merge paused with conflicts.Run git status. It names the files needing a choice.Edit the correct final content, add each resolved file, test, then run git merge --continue.
You want to stop the merge.Check that a merge is still in progress.Use git merge --abort. Starting with unsaved unrelated changes can make an exact return harder.
“Already up to date.”Look at the branch names and git log --graph --oneline --all.Git already has that branch’s commits in your current history. If a previous revert removed their effect, see the reverted merge example.

What to remember

  • Merge uses the shared starting files to understand both changes.
  • Fast-forward moves a name; a normal two-sided merge adds a commit with two parents.
  • A successful text merge still needs a check of the final behavior.
