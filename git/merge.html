Merge and the three-way comparison

See how Git combines two lines of development and why the common ancestor matters.

By the end, you can…

  • Distinguish fast-forward, merge commit and squash.
  • Explain base, ours and theirs during a merge.
  • Understand what an automatic merge does not guarantee.

Fast-forward moves a pointer

The diagram draws a separate line for feature only to show the label; C’s parent is B. A fast-forward does not combine independent edits because there is no divergent main-side work to combine. --ff-only fails if moving the pointer would not be enough.

A three-way merge uses three snapshots

SnapshottimeoutretriesInterpretation
Base B101Common starting point.
Ours C201Main changed timeout.
Theirs D103Feature changed retries.
Combined M203Independent edits can be combined.

Comparing only the two tips would not tell you which side changed each value. The base supplies that context. Git can usually combine independent edits; overlapping changes with incompatible textual resolutions may cause conflicts. Two branches changing the same file does not necessarily conflict, and two branches changing different files can still introduce a semantic bug.

For a single merge base, inspect it with git merge-base main feature. In more complex criss-cross histories, there may be multiple best bases; the merge strategy may synthesize a base tree. The three-snapshot mental model remains useful, but the base need not be one simple hand-picked commit.

Choose the history you want to record

MethodNew history shapeUse and tradeoff
Fast-forwardMoves the receiving branch to an existing descendant.Simple when no divergence; no merge boundary is recorded.
git merge --no-ff featureA merge commit with two parents, even when fast-forward is possible.Records integration ancestry; more graph structure.
git merge --squash feature, then commitPrepares a combined change; the later commit has one parent.One integration commit, but no parent link to the feature tip; repeated integration from a long-lived branch needs care.
Rebase, then fast-forwardReplays commits onto a new base, then moves a ref.Linear history with rewritten identities; coordination is needed if old identities were shared.

During a normal merge, existing commits stay unchanged. A merge commit records both parent lines, and its tree can include manual conflict-resolution changes that were in neither parent. A squash is not a record that all source commits became ancestors. That difference affects future merges, history analysis and branch-deletion checks.

Perform and verify a merge

Shell example — read the context before running
git status
git fetch origin
git switch feature
git branch backup/feature-before-merge
git merge origin/main
# If conflicts occur, follow the conflicts module before continuing.
git log --graph --oneline --decorate -12
git diff HEAD^1 HEAD
# Run relevant tests before pushing.

Use a unique backup-branch name; it protects the current committed tip, not uncommitted files. A backup branch does not replace checking a clean working tree. If you need to stop an in-progress merge, git merge --abort attempts to restore the pre-merge state. Starting with unrelated dirty work makes restoration harder and can prevent exact recovery.

Automatic textual success means Git found a mechanically mergeable result. Verify API compatibility, imports, database assumptions and generated artifacts. Run tests that exercise the interaction between both changes, not just each branch independently.

Remember in 30 seconds

  • Fast-forward moves a reference; a true merge combines divergent histories.
  • Three-way means base + current side + incoming side.
  • A conflict-free merge can still contain a functional bug.
