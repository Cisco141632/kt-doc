Module 13 / 21 · about 40 minutes

Set team rules and enforce them

Turn team expectations into repository controls that can be tested, explained and maintained.

By the end, you can…

  • Define a practical branch and review policy.
  • Create and verify a ruleset with intentional bypass behavior.
  • Avoid configurations that block every legitimate merge or silently allow direct updates.

Write the human agreement first

AreaExample baselineWhy it matters
main and release branchesChanges arrive through reviewed PRs; no ordinary force pushes or deletion.Keeps shared history and release references dependable.
ReviewsRequire an appropriate reviewer count and domain review for sensitive paths.Distributes knowledge and checks intent.
ChecksRequire named, relevant CI checks for the exact revision/integration being merged.Prevents a green result for the wrong work from being mistaken for validation.
Merge methodChoose squash, rebase or merge commit consistently with history rules.Makes debugging and recovery predictable.
Feature historyRewriting only with branch-owner coordination; explicit lease for published rewrites.Protects collaborators’ unreviewed work.
Emergency changesA small named bypass group, recorded reason, rapid follow-up review.Makes an exception accountable instead of routine.
Secrets and automationLeast-privilege credentials, no secrets in Git, trusted workflows for privileged actions.Limits the impact of mistakes and untrusted contributions.

These are a sample team policy, not Git defaults. Store the agreed expectations in CONTRIBUTING or an equivalent handbook. Local aliases and hooks can help developers, but enforcement of a shared branch belongs on the server because local hooks can be absent or bypassed.

Configure a branch ruleset on GitHub

  1. Use a repository where you have admin or an applicable custom rule-management permission. Confirm the feature is available for its visibility and plan.
  2. Open repository Settings, locate Rulesets, and choose a new branch ruleset. Interface grouping may vary.
  3. Name the policy, choose its enforcement status and target the actual default/release branches. Inspect the matching branches.
  4. Specify bypass actors and whether bypass is restricted to pull requests, where supported. Avoid a broad, undocumented escape route.
  5. Choose PR requirements, review/check requirements, blocked force pushes and protected deletion as your policy requires.
  6. Save, inspect the effective rules, and test with an ordinary contributor rather than only an admin/bypass account.

Rulesets can overlap with other rulesets and existing branch protection. Applicable restrictions are evaluated together; a permissive rule does not necessarily cancel a stricter one. Active rules enforce; disabled rules do not. Evaluation modes, where offered, report impact without enforcing. Confirm the actual mode rather than assuming a saved policy is blocking updates.

Settings with easy-to-miss consequences

SettingConsequence to think through
Require linear historyMerge commits are disallowed on the target; allow squash/rebase integration methods instead.
Require branch to be up to dateA base-branch update can require integration and fresh checks; consider a merge queue for busy repositories where available.
Dismiss stale approvals / require latest-push approvalNew changes can require fresh human review; understand whose approval counts.
Require code-owner reviewNeeds valid owners with appropriate access and a matching CODEOWNERS file on the PR base branch.
Restrict updatesCan block updates except for bypass actors; it is not merely another name for requiring PRs.
Required checksChoose stable, unambiguous job/check names and appropriate trusted sources. A check that never runs can leave merges pending.
Require signed commitsOnboard developers and bots, and check the selected merge workflow’s signature behavior.
Branch patternsPattern syntax is not a shell glob copied blindly: a single * does not cross / in GitHub’s fnmatch matching. Verify actual branch matches.

CODEOWNERS routes review; it does not grant access

Example .github/CODEOWNERS — not installed by this course
# Example only: replace these with real teams that have repository access.
* @example-org/maintainers
/src/auth/ @example-org/security
/.github/ @example-org/platform
/.github/CODEOWNERS @example-org/maintainers

GitHub uses the CODEOWNERS file from the pull request’s base branch. Later matching patterns take precedence, so order matters. Valid owners need the necessary repository access. The file requests ownership review; required code-owner approval must be enabled through the relevant rule. Ownership is not filesystem protection and does not make someone an administrator.

Protect changes to the ownership file and workflow definitions themselves. Check GitHub’s displayed errors and requested reviewers with a sample PR rather than trusting that a text file is syntactically correct.

Test the policy as a product feature

  1. Attempt a direct update to the protected test branch as an ordinary contributor; verify the intended rejection.
  2. Open a small PR and observe required reviews, checks and ownership requests.
  3. Push another change and confirm the approval/check freshness behavior.
  4. Make a required check fail, then pass, and confirm the merge gate follows the correct revision.
  5. Test the documented emergency path in a safe repository and record who can use it.
  6. Review inherited organization rules, service-account access and policy drift periodically.

The course includes an adaptable policy checklist. It is a planning document; no GitHub settings are changed by opening it.

Pause and test your understanding

Remember in 30 seconds

  • Write the team agreement, then enforce and test it.
  • Ruleset mode, branch targets and bypass actors are part of the policy.
  • Local hooks and CODEOWNERS alone do not enforce every required rule.
