Team rules that GitHub can check

Turn “review before merge” into a working rule. Check the target branches, required tests, and exceptions with a small practice change.

Need help with HEAD, index, staging, or diff?
Your file
What you are editing now. Git calls the project files the working tree.
Staging area = index
The file content you chose for the next commit. These are two names for one place.
HEAD
Tells Git which saved commit you are using, usually through your current branch.

A comparison showing added and removed lines between two versions.

By the end, you can…

  • Write a clear rule before changing settings.
  • Understand a ruleset and who can use an exception.
  • Find why a rule blocks too much or fails to block a direct push.

Start with a rule people understand

Example: “To change main, open a PR, get one other person’s approval, and pass the tests. Do not force-push or delete main.” A ruleset is a saved group of GitHub rules for selected branches or tags. A bypass is an explicitly allowed exception for selected people, teams, or apps.

→Require a PR, approval, and tests

Named exceptions: follow their allowed route

Write the agreement in CONTRIBUTING or your team guide. Include who handles urgent fixes and how those fixes are reviewed afterward. Local Git hooks are scripts that help check changes on a computer; they can be missing or skipped, so shared enforcement belongs on the server.

Set up and test a branch ruleset

  1. Choose a safe project and check availability

    You need Admin or the appropriate custom rule-management access. Available settings depend on plan, visibility, and organization policy.

    What you should see: You can see the applicable Rulesets settings.

  2. Create a branch ruleset

    Open repository Settings and find Rulesets. Choose the branch-ruleset option; menu grouping can vary.

    What you should see: You can name the rule and select its target branches.

  3. Check the matching branches and mode

    Select the actual default branch, such as main. Active means enforce. Disabled does not enforce. Evaluate, where available, reports what would happen without blocking.

    What you should see: The displayed matching branches and enforcement mode are the ones you meant.

  4. Set the requirements and exceptions

    Require the agreed PR reviews and named checks. Block force pushes and deletion if that is the policy. Give exceptions only to the intended accounts or apps.

    What you should see: The saved rule describes the team agreement.

  5. Test a normal contributor’s direct push

    Use a harmless practice branch covered by the test rule. Use an account that has no exception.

    What you should see: The direct update is refused with the expected rule message.

  6. Test the approved route

    Open a small PR. Observe missing review and failing-check blocks, then obtain review and pass the actual required checks.

    What you should see: The PR becomes mergeable when the intended requirements pass.

More than one ruleset and older branch protection can apply. Read the combined effective rules: one permissive rule does not cancel a stricter one. Testing only as an admin or bypass account can hide a problem that normal contributors will face.

Ask the right people to review

CODEOWNERS is a text file mapping paths to reviewers. Use real teams with the required repository access. For example:

Example .github/CODEOWNERS — replace these team names
* @example-org/maintainers
/src/auth/ @example-org/security
/.github/ @example-org/platform
/.github/CODEOWNERS @example-org/maintainers

GitHub reads this file from the PR’s base branch. The last matching pattern wins. The file requests review; the rule requiring code-owner approval makes that review a merge condition. The file does not grant access. Check errors and requested reviewers on an actual small PR.

If the rule behaves differently

What happened?What to checkWhat to do, then check
Direct push is allowed unexpectedly.Matching branch, Active mode, inherited rules, and bypass list.Correct the actual mismatch, then retry as a normal writer.
A required check never appears.Exact check name, workflow event, path/branch filters, and trusted source.Make the job report on the revision being evaluated. For a merge queue, check merge_group.
A correct PR cannot merge.Conflicting history requirements, Restrict updates, missing approval, or another ruleset.Read the named blocker and fix the inconsistent setting or unmet requirement.
CODEOWNERS asks nobody.File location on the base branch, matching path, team visibility/access, and syntax errors.Fix the example and check the requested reviewers again.

What to remember

  • A rule needs the correct branch targets, enforcement mode, and exceptions.
  • CODEOWNERS chooses reviewers; a separate rule requires their approval.
  • Test both a blocked direct update and a successful approved PR as a normal contributor.
