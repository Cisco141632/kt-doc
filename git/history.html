Find what changed and why something broke

Read saved changes, search a file’s history, and use a repeatable test to find when a bug first appeared.

Need help with HEAD, index, staging, or diff?
Your file
What you are editing now. Git calls the project files the working tree.
Staging area = index
The file content you chose for the next commit. These are two names for one place.
HEAD
Tells Git which saved commit you are using, usually through your current branch.
Diff
A comparison showing added and removed lines between two versions.
Watch these change with one file →

By the end, you can…

  • Choose log, show, and diff for a specific question.
  • Read two-dot and three-dot comparisons.
  • Find a first bad commit with bisect and check the result.

Ask one question at a time

Log

A list of saved commits. With --graph, lines show which commits follow which.

Show

Read a particular saved commit or file without replacing your current file.

Regression

Something that worked before but fails now. You need a test that can tell the two results apart.

  1. See a small history picture

    --oneline gives a short ID and message. --decorate shows names such as main. --all includes histories reached by local branch and other saved names.

    Type this in your terminal
    git log --graph --oneline --decorate --all -20

    What you should see: Up to 20 commits with their links. Fetch first if you need current remote history.

  2. Read one change

    Replace COMMIT with an ID from log.

    Type this in your terminal
    git show COMMIT

    What you should see: The commit message and the added/removed lines.

  3. Read an old file without switching branches

    Use a real file path in place of notes.txt if needed.

    Type this in your terminal
    git show COMMIT:notes.txt

    What you should see: The file’s contents in that saved commit. Your current file is not changed.

  4. Search the history of a file

    --follow tries to follow earlier names of this one file.

    Type this in your terminal
    git log --follow -- notes.txt

    What you should see: Commits that affected the file, including detected renames.

Commit links are more useful than sorting only by time. A commit can record an original author time and a later time when it was applied. git log --first-parent --oneline main follows the first parent at merges, useful for seeing how changes entered main.

Two dots and three dots: read them with the command

CommandMeaning hereResult
git log main..featureCommits in feature’s history but not main’s history.D and E.
git log main...featureCommits on either side but not in both histories.C, D, and E.
git diff main..featureCompare the files at the two named commits.C’s files → E’s files. Same as git diff main feature.
git diff main...featureCompare the shared starting files with feature’s files.B’s files → E’s files. This shows feature’s changes since the split.
Try to answer: Does git diff feature...main show the same change in reverse?

No. It compares the base B to main C. The branch after the three dots decides the ending version.

Find the reason behind a line

Use files and line numbers that exist in your project
git blame -L 1,10 -- notes.txt
git log -S 'timeout' -- config.json
git log -G 'timeout.*' -- config.json

Blame is the Git command name for showing the commit that last changed each selected line. Use it to find the commit and read its reason. Formatting and moved lines can affect the result; it is not a measure of who caused a bug. -w can ignore whitespace when calculating blame.

-S finds commits where the number of occurrences of a text changed. -G searches added and removed lines for a pattern. The pattern above means timeout followed by any text. Both need you to inspect the matching commits.

Let Git narrow down the first bad commit

Bisect tests a commit near the middle of a known good-to-bad range, then keeps narrowing the range based on your answer. Start with a clean working tree because it changes the checked-out files.

A test passes before C and fails from C onward

A picture to explore. These buttons do not run commands on your computer.

  1. Step 1

    Choose known results

    A works and E fails. Keep the same test and setup when checking older commits.

  2. Step 2

    Test a middle commit

    Git chooses C. The test fails. Tell Git “bad.” The first failure is now between A and C.

  3. Step 3

    Test B and inspect C

    B passes, so C is the first bad commit in this example. Reproduce both B and C and read C’s change.

Replace the two placeholders with tested commit IDs
git bisect start
git bisect bad BAD_COMMIT
git bisect good GOOD_COMMIT

Run your test at the revision Git selects. Say git bisect good if the behavior works, git bisect bad if this bug occurs, or git bisect skip if you cannot test that revision. Repeat until Git reports the first bad commit. Save the report with git bisect log. Finish with git bisect reset to return to your original branch.

For a reliable test script, git bisect run ./test-regression.sh automates the answers. Exit 0 means good, exit 125 means cannot test, and normal nonzero failures mean bad. Special error codes are described in the manual. A missing dependency is not proof this product bug happened.

Compare changes after a rebase

git range-diff OLD_BASE..old-tip NEW_BASE..new-tip compares two lists of commit changes. Replace the four names with checked starting points and endings. It helps spot a dropped change or a changed conflict resolution. Matching patches do not prove identical behavior; the new surrounding code matters too.

Bisect points to an unlikely commit.Test that commit and its parent with the same setup. Read git bisect log.Fix unreliable tests or mark untestable revisions as skip before repeating.
A date suggests the wrong order.Read the parent links in the graph.Use the saved history links and actual changes to explain the result.

What to remember

  • Ask a specific question, then choose the history command.
  • Log chooses commits; diff compares file versions. Dot notation depends on which command you use.
  • Bisect needs a reliable test, known starting results, and a final check of the reported commit.
