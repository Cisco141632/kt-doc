Module 11 / 23 · about 40 minutes

Trace history, explain changes & find regressions

Turn commit history into evidence with log, diff, show, blame, range-diff and bisect.

By the end, you can…

  • Read ancestry rather than relying on timestamps.
  • Find when and why code changed.
  • Use a reliable test to locate a regression.

Start with the shape and the question

Shell example — read the context before running
git log --graph --oneline --decorate --all -30
git log --first-parent --oneline main
git show --stat COMMIT
git show COMMIT -- path/to/file
git show COMMIT:path/to/file

--all walks commits reachable from local refs; it does not mean all commits ever created or everything still on the server. Fetch when remote history matters. --first-parent follows the integration line and is useful for release history when merges are preserved. Author and committer dates can differ and do not replace parent relationships.

Ask a specific question: “What introduced this timeout?”, “Which feature landed in this release?”, “Was this patch preserved after rebase?” Different commands provide different evidence. Start with a small relevant range instead of reading thousands of unrelated commits.

Two dots and three dots depend on the command

ExpressionFor git logFor git diff
A..BCommits reachable from B but not from A.Compare endpoint trees A and B, like git diff A B.
A...BCommits reachable from either side but not both (symmetric difference).Compare the merge base with B: what the B side changed since the common base. This is asymmetric.
HEAD^1 / HEAD^2First / second parent of HEAD; second requires a merge commit.Use those revisions to compare chosen parents or snapshots.
HEAD~3Follow the first-parent chain three times.A revision selector, not “three commits in date order.”
Shell example — read the context before running
git log --left-right --oneline main...feature
git diff main...feature
git log --oneline origin/main..HEAD

A pull-request diff commonly focuses on head-side changes since a merge base. A direct tip-to-tip diff answers another question. Always say which comparison you mean when discussing “the diff.”

Find the change behind a line

Shell example — read the context before running
git log --follow -- path/to/file
git log -p -- path/to/file
git log -S 'timeout_seconds' --all -- path/to/file
git log -G 'timeout.*=' --all -- path/to/file
git blame -L 20,45 -- path/to/file
git show COMMIT

--follow follows one file across detected renames; rename tracking is heuristic, not a stored rename event. -S finds changes to the number of occurrences of a string. -G finds patches whose added/removed lines match a regular expression.

Blame shows the last modifying commit for lines in the selected revision. Use it to find context and read the whole commit, its parent and linked review. It is not a measure of responsibility or code quality: formatting, generated changes and moves can change attribution. -w can ignore whitespace in the blame calculation when that helps.

Find the first bad commit with a repeatable test

Shell example — read the context before running
git status
git bisect start
git bisect bad BAD_COMMIT
git bisect good GOOD_COMMIT
# Test the checked-out revision and say git bisect good or bad.
# Or automate with a verified test script:
git bisect run ./test-regression.sh
git bisect log
git bisect reset

A clean working tree protects unrelated work while bisect checks out revisions. The test must detect the same regression across the range. Exit 0 means good; exit 125 means skip because this revision cannot be tested; ordinary nonzero test failures mark bad (the manual documents special statuses). A missing dependency is not proof the product regression exists there.

A nonmonotonic or flaky test can mislead bisect. Reproduce the identified commit and its parent, read the patch, and check environmental changes. End with git bisect reset to return to the original checkout.

Audit a rewritten patch series

Shell example — read the context before running
git range-diff OLD_BASE..backup/feature NEW_BASE..feature
git log --cherry-mark --left-right --oneline old-tip...new-tip

Patch equivalence can help recognize changes that have new IDs after rebase or cherry-pick. It is not identical to ancestry or functional equivalence. range-diff compares patch series and helps reviewers inspect conflict-resolution edits, missing patches and unexpected reordering. Use the correct base boundaries and read unmatched entries.

Pause and test your understanding

Remember in 30 seconds

  • Ancestry, date order, patch equivalence and content equality are different.
  • log A...B is symmetric; diff A...B compares the base to B.
  • A reproducible test turns bisect into evidence.
