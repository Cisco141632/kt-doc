Module 16 / 23 · about 35 minutes

Advanced workflows you will encounter

Recognize the tools for moving selected changes, parallel work, large repositories and repeated conflict resolution.

By the end, you can…

  • Choose cherry-pick, worktree, tags and rerere deliberately.
  • Understand submodules, LFS, shallow clones and sparse checkouts.
  • Know which advanced operations need extra coordination.

Cherry-pick one change, not a whole branch

Shell example — read the context before running
git show COMMIT
git switch release/maintenance
git cherry-pick -x COMMIT
# Resolve and stage conflicts, then git cherry-pick --continue.
# Or git cherry-pick --abort to stop.

Cherry-pick applies a selected commit’s change to the current branch and generally creates a new commit ID. -x records the source commit reference for traceability. Verify dependencies: a fix may rely on earlier refactoring, a schema change or a test helper absent from the release branch.

Cherry-picking a merge commit requires a chosen mainline and careful interpretation. Repeatedly cherry-picking a whole development stream creates duplicated patch identities and confusing ancestry. Use it for focused backports with tests rather than as a substitute for an integration policy.

Parallel checkouts without a stash shuffle

Shell example — read the context before running
git worktree add ../project-hotfix -b hotfix/login origin/main
git worktree list
# Work, commit and review in the separate directory.
# After it is clean and no longer needed:
git worktree remove ../project-hotfix

Linked worktrees share one repository’s object database and references while having separate working directories and index/HEAD state. They are useful for an urgent fix while a feature checkout is dirty. Git normally prevents checking out the same branch in two worktrees to avoid competing updates.

Each directory may need its own dependencies, build outputs and environment. Remove a worktree through Git when possible; do not assume deleting a directory also cleans its metadata. Inspect worktree list when branch deletion or checkout reports that a branch is in use.

Reuse a resolution, then verify it

Shell example — read the context before running
git config --local rerere.enabled true
git rerere status
git rerere diff

Rerere records how a conflict was resolved and can reuse that resolution when a similar conflict reappears. This helps repeated integrations and rebases, but it can repeat a bad decision too. Inspect the result, decide when it should be staged, and run tests. rerere.autoupdate changes whether the index is updated automatically; understand that extra behavior before enabling it.

git merge -X ours favors our side for conflicting hunks while retaining nonconflicting changes from the other side. git merge -s ours records ancestry while keeping the current tree and ignoring the other tree’s content. They are very different. Neither should be a habitual way to avoid understanding conflicts.

Repository size and dependency boundaries

FeatureWhat it doesCommon pitfall
SubmoduleThe parent records a commit ID for another repository plus configuration.Changing parent pointers does not automatically publish the submodule commit. Use documented initialization/update steps and ensure the referenced commit is reachable.
Git LFSGit records pointers while large objects are stored separately.A clone may have pointer text if LFS objects were not fetched; access and quota are separate concerns.
Shallow cloneDownloads limited history depth.Blame, merge-base and range operations may lack needed ancestors; fetch deeper or unshallow when appropriate.
Partial cloneDefers some objects until needed.Some operations need network access to retrieve missing objects.
Sparse checkoutLimits which tracked paths appear in a working directory.Hidden paths are not deleted from the repository; tooling must handle the selected view.
AttributesDefine line endings, merge/diff handling and other path behavior.Mass renormalization can create noisy diffs; coordinate and separate it from functional changes.
Small .gitattributes example — adapt and review before normalizing existing files
* text=auto
*.sh text eol=lf
*.png binary

For a repository with existing line-ending policy, do not introduce git add --renormalize . casually. Preview, review the full diff and coordinate platform/tool behavior. Case-only filename changes can also require special care on case-insensitive filesystems.

Release references and maintenance

Example release workflow — use only the team-approved version and release commit
git tag -a v1.2.0 -m 'Release 1.2.0'
git show v1.2.0
git push origin v1.2.0

Tags are not sent by every ordinary branch push; push the intended release tag explicitly. Avoid moving published tags: build systems and people may have cached the old value. A GitHub release adds release notes and assets around a tag; it does not itself prove that an artifact was built from that exact commit.

For large history cleanup, use supported dedicated tooling and a coordinated migration. For an “unrelated histories” error, first check repository identity and remote selection; --allow-unrelated-histories is for an intentional combination of independent projects, not a routine push fix.

Remember in 30 seconds

  • Cherry-pick moves a selected patch; worktree gives another checkout.
  • Reused resolutions still need review and testing.
  • Large-repo and dependency features introduce their own fetch and ownership boundaries.
