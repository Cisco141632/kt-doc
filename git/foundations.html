Your file, staging, and HEAD

Use one small text file to see what Git saves. Learn HEAD, index, staging, and diff by watching the file change.

Need help with HEAD, index, staging, or diff?
Your file
What you are editing now. Git calls the project files the working tree.
Staging area = index
The file content you chose for the next commit. These are two names for one place.
HEAD
Tells Git which saved commit you are using, usually through your current branch.
Diff
A comparison showing added and removed lines between two versions.
Watch these change with one file →

By the end, you can…

  • Make your first local project and commit.
  • Explain the three places using the actual text in a file.
  • Read each diff and predict what the next commit will save.

Start with these five meanings

Commit = a saved project version

You choose when Git saves a version. Each saved version has a message and an ID, such as 7ac19d2. A commit stays on your computer until you send it elsewhere.

Staging = choosing content for the next commit

Think of a tray marked “save these changes next.” git add notes.txt puts the file’s current content on that tray. Editing the file later does not change what is already on the tray.

Index = Git’s name for that staging area

These are two names for the same thing. You do not need to learn two separate places. The index records the file versions you have chosen for the next commit.

HEAD = where you are in saved history

HEAD tells Git which commit you are using. Usually it does this through your current branch. For example: HEAD → main → commit A. Before the first commit, main has no saved commit yet.

Diff = a view of what changed

A diff compares two versions. A line starting with - was removed; a line starting with + was added. The command you choose decides which two versions Git compares.

Make a tiny practice project

A terminal is a window where you type commands. Run one step at a time. These examples use a Linux or macOS shell; on Windows, use Git Bash. A repository is your project plus its Git history.

  1. Check that Git is installed

    Type the command and press Enter. If it is missing, install Git from the official download page, reopen your terminal, and try again. These lessons use Git 2.28 or later.

    Type this in your terminal
    git --version

    What you should see: A version number, such as git version 2.43.0. Your number may differ.

  2. Make a new folder and go into it

    mkdir makes a folder. cd enters it. Choose a new name if this folder already exists.

    Type this in your terminal
    mkdir git-notes-practice
cd git-notes-practice

    What you should see: You are now inside your new, empty folder.

  3. Ask Git to keep history here

    init starts Git in this folder. -b main names your first branch main. Nothing is uploaded to GitHub.

    Type this in your terminal
    git init -b main

    What you should see: Git reports that it created a repository. It also makes a hidden .git folder. Leave that folder alone.

  4. Set the name shown on your practice commits

    These settings apply only to this project. Replace the example name and email with the ones you want on your commits. They label commits; they do not sign you into GitHub.

    Type this in your terminal
    git config user.name "Your Name"
git config user.email "you@example.com"

    What you should see: Usually no output. git config user.name lets you check the saved name.

  5. Create one text file

    printf writes text. > replaces the named file, so use it only for this new practice file.

    Type this in your terminal
    printf 'Hello\n' > notes.txt

    What you should see: Open notes.txt in your editor. It contains one line: Hello.

  6. Ask Git what it sees

    Status is a report about the current project. It does not save or discard anything.

    Type this in your terminal
    git status

    What you should see: notes.txt appears under “Untracked files.” This means Git has not yet chosen it for a commit.

  7. Choose this file for the next commit

    This is the staging step. It chooses the content currently in notes.txt.

    Type this in your terminal
    git add -- notes.txt

    What you should see: Run git status. The file is under “Changes to be committed.” The -- separates options from file names.

  8. Look at what you are about to save

    --staged means “show the changes already chosen for the next commit.”

    Type this in your terminal
    git diff --staged

    What you should see: The new line appears as +Hello. With no earlier commit, Git compares it with an empty starting point.

  9. Save the first version

    -m gives this saved version a short message.

    Type this in your terminal
    git commit -m "Write my first note"

    What you should see: Git reports one new commit. git log --oneline shows its ID and message. git status reports a clean working tree: no changes to the tracked file are waiting.

Try to answer: At step 4, what will git commit save?

Hi. That is what you chose at step 3. The later edit, Good morning, has not been chosen yet.

Which two versions does each diff compare?

At step 4 above, your file says Good morning, your staging area holds Hi, and HEAD still leads to Hello.

CommandComparesThe change you see
git diffChosen content → your file-Hi
+Good morning
git diff --stagedCurrent saved commit → chosen content-Hello
+Hi
git diff HEADCurrent saved commit → your file-Hello
+Good morning

A plain diff does not show the contents of a new, untracked file. Start with git status to find it. In diff output, --- and +++ label the two files. A heading such as @@ -1 +1 @@ gives the line numbers around the change.

A shorter status report
git status --short

If you see MM notes.txt, the first M means the chosen content differs from the saved commit. The second M means your file differs from the chosen content. M means “modified.” ?? means untracked. You can always use the longer git status while learning.

How Git keeps these versions

Inside .git, Git stores saved file content and the information needed to rebuild each saved project. Git calls a stored file’s content a blob. A tree records file names, folders, and which stored contents belong there. A commit points to the project tree, its earlier commit or commits, the name and time recorded, and the message.

A branch is a name that points to one commit. HEAD usually names the current branch. When you commit on main, main moves to the new commit, and HEAD still names main. These links let Git find your current saved files without copying the whole project for every branch.

HEADYou are using main
→
mainPoints to saved commit B
→
Commit BPoints to saved files and earlier commit A

git add stores the chosen file content and updates the index entries for it. git commit records a project version from those entries. Git gives stored objects IDs calculated from their contents. Changing a commit message or its earlier-commit link creates a different commit ID, even if the files are the same.

Read the saved file, then the staged file; these commands do not edit either one
git show HEAD:notes.txt
git show :notes.txt

HEAD:notes.txt means “notes.txt in the current commit.” :notes.txt means “notes.txt in the staging area.” These work after the file has been added; the HEAD form needs a first commit.

If you see “detached HEAD”

You are using a saved commit directly, rather than working through a branch name. To keep new work there, run git switch -c keep-my-work before switching away. Choose a branch name that does not already exist.

What to remember

  • Your file is what you edit. Staging holds what you chose for the next commit.
  • Index means staging area. HEAD tells Git which saved commit you are using.
  • git diff shows changes still in your file; git diff --staged shows changes chosen for the next commit.
