Module 03 / 23 · about 25 minutes

Snapshots, the index, HEAD & objects

Understand what Git stores, what a branch actually is, and why staged and unstaged changes are different.

By the end, you can…

  • Distinguish the working tree, index and commits.
  • Explain commit IDs, parents, branches, tags and HEAD.
  • Configure identity without confusing it with authentication.

Start with a clone or a new local repository

For an existing project, copy its approved HTTPS or SSH clone URL from GitHub’s Code menu. Replace APPROVED_REPOSITORY_URL below; never insert a token into the URL. Cloning creates a local repository, downloads available history, configures a remote normally named origin, and checks out a branch. It does not copy another developer’s uncommitted files.

Existing project — choose an unused destination directory
git clone APPROVED_REPOSITORY_URL project
cd project
git status
git remote -v

For a genuinely new project, start in a fresh directory instead. git init creates local Git metadata; it neither creates a GitHub repository nor uploads files. Keep the two starting routes separate.

New local project — use a fresh directory
mkdir my-first-git-project
cd my-first-git-project
git init -b main
# Set repository-local identity if needed:
git config user.name 'Your Name'
git config user.email 'your-approved-address@example.com'
printf 'A small first project.\n' > README.md
git add -- README.md
git diff --staged
git commit -m 'Describe the project'
git log --oneline

To publish that new repository, first create the intended empty GitHub repository with the correct owner and visibility. If you already created its files locally, avoid independently initializing a second README/history on GitHub. Add the inspected remote with git remote add origin APPROVED_REPOSITORY_URL, verify git remote -v, then git push -u origin main when its access and rules permit. For a repository that already has history, clone and integrate that history instead of reflexively forcing an unrelated branch over it.

The hidden .git directory contains the ordinary repository’s metadata and objects. Do not delete or edit it to “fix” a confusing status. Git does not track empty directories, and a newly created file is untracked until you add it.

Three places where your content can exist

Working treeFiles currently on disk
→
Index / staging areaThe snapshot prepared for the next commit
→
Local historyCommits stored in the object database

Editing changes your working tree. git add records the selected content in the index. git commit creates a commit from the index. If you edit a file again after staging it, the staged version and the current file can differ. A clean working tree means it matches the index and current commit for tracked paths; it does not mean every file on disk is tracked.

Shell example — read the context before running
git status --short
git diff
git diff --staged
git ls-files
ObservationMeaning
git diffWorking tree compared with index: unstaged changes.
git diff --stagedIndex compared with HEAD: what the next ordinary commit would include.
git diff HEADWorking-tree tracked content compared with the current commit; does not include untracked file contents.
?? fileUntracked file; it is not in a commit merely because it exists in the directory.
MM fileThe file has both staged changes and additional unstaged changes.

A commit is a snapshot with history

A blob stores file content, a tree maps names to blobs or other trees, and a commit points to a tree plus its parent commit(s), author/committer metadata and message. Git identifies objects by a content-derived object ID. Reusing file content reuses objects; a commit need not store another full copy of every unchanged file.

A normal commit has one parent, a root commit has none, and a merge commit usually has two. Changing content, parents, metadata or the message changes the commit object and normally its ID. Rebase and amend create replacement commits; they do not edit an existing immutable commit in place.

Shell example — read the context before running
git show --no-patch --pretty=raw HEAD
git cat-file -p HEAD
git ls-tree HEAD

Most repositories you encounter use SHA-1 object IDs; Git also supports SHA-256 repository formats. Do not build tooling that assumes all identifiers are exactly 40 characters. Short prefixes are convenient only when unambiguous in that repository.

HEAD, branches and tags

On a branch, HEAD normally names a branch reference such as refs/heads/main. A new commit moves that branch forward. A branch is not a separate directory or a complete copied project. Switching branches updates the index and working tree; Git may refuse if doing so would overwrite local changes.

Detached HEAD points directly to a commit, often when inspecting a tag or bisecting. You can commit there, but create a branch to retain new work before switching away. A tag normally marks a release point. Annotated tags have their own metadata and can be signed; lightweight tags are simple references. Tags can technically be moved, but published release tags should be treated as stable.

Shell example — read the context before running
git branch --show-current
git symbolic-ref --short HEAD
# If you deliberately created useful commits while detached:
git switch -c rescue/detached-work

The symbolic-ref command returns a nonzero status when HEAD is detached. That is an observation, not necessarily a broken repository.

Install, identify and inspect

Shell example — read the context before running
git --version
git config --global user.name 'Your Name'
git config --global user.email 'your-approved-address@example.com'
git config --show-origin --get user.email
git config --show-origin --get-regexp '^(user|pull|push|merge)\.'

Use your operating system’s supported installer or package manager. Configure an approved work or GitHub noreply email if appropriate. user.name and user.email are commit metadata; they do not authenticate you or grant GitHub permissions. Repository-local settings can override global settings. Inspect origin and scope when an unexpected identity is used.

Pause and test your understanding

Remember in 30 seconds

  • add selects content; commit records the index.
  • Branches move; existing commit objects do not change.
  • Author identity, cryptographic signatures and GitHub authentication are different.
