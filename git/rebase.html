Module 07 / 21 · about 40 minutes

Rebase: replay changes onto a new base

Understand which commits are recreated, how conflicts are replayed, and what collaborators see after a rewrite.

By the end, you can…

  • Predict commit IDs and parent changes after rebase.
  • Perform and inspect a private-branch rebase.
  • Use interactive rebase and --onto with a recovery point.

What actually changes

Rebase selects commits not already integrated into the target history and replays their changes onto a new base. In the simple case D and E become D′ and E′. The resulting files may look familiar, but different parents or metadata mean different commit IDs. Git may skip changes already upstream or handle newly empty commits according to its options.

Rebase does not move main merely because you rebased onto it. It moves the branch you are rebasing. Ordinary rebase generally flattens merge structure; --rebase-merges attempts to recreate it and requires extra review. Do not treat every history shape as the simple two-commit example.

A private branch rebase you can inspect

Shell example — read the context before running
git status
git fetch origin
git switch feature
# Choose a fresh backup name and start from a clean working tree.
git branch backup/feature-before-rebase
git merge-base feature origin/main
# Record that output as OLD_BASE for the later comparison.
git rebase origin/main
git log --graph --oneline --decorate -15
git range-diff OLD_BASE..backup/feature-before-rebase origin/main..feature

The backup retains the old committed tip. Record the old merge base before rewriting, because comparing the wrong ranges can hide a dropped patch. range-diff helps map the old patch series to the new one; it is a review aid, not a proof that behavior is identical. Inspect meaningful differences and run tests.

If the branch was never pushed, an ordinary push publishes the new history. If its old IDs are already on the server, a normal push will usually be rejected as non-fast-forward. That is when the force-push lesson and your team’s shared-history policy matter.

Why the same file can conflict more than once

Rebase works through individual commits. A resolution while replaying D can be followed by another conflict when replaying E. During each pause, the new base and successfully replayed commits are the “ours” side. The original commit currently being replayed is “theirs.” Read the content, not just the editor’s button names.

Shell example — read the context before running
git status
git rebase --show-current-patch
# Edit and test the intended combined result.
git add -- path/to/resolved-file
git rebase --continue
# To return to the original branch state instead:
# git rebase --abort

--skip omits the current replayed change; it is not a generic “fix this conflict” operation. --abort restores the pre-rebase branch state when possible. --quit stops rebase bookkeeping while leaving HEAD, index and working-tree state where they are. Those choices have different consequences.

Clean up a private patch series

Interactive rebase — review every todo action before saving
git rebase -i origin/main
ActionEffect
pickReplay the commit.
rewordReplay but edit its message.
editPause to amend or split a change; continue when ready.
squashCombine with the previous picked commit and edit the message.
fixupCombine while discarding this commit’s message by default.
dropOmit the change from the replayed series. This is a deliberate content decision.

The todo list normally runs oldest first. Reordering can break dependencies; combining commits can hide useful review boundaries. git commit --fixup COMMIT with git rebase -i --autosquash BASE helps organize review fixes. Review the resulting patch series rather than assuming a prettier graph means better code.

Move a specific range with --onto

This is useful for retargeting dependent work after a base branch changes, but the boundary is easy to choose incorrectly. Inspect git log old-base..feature first. A wrong boundary can replay unrelated changes or omit required ones. For shared branches, agree on the migration and keep old tips available to collaborators.

Remember in 30 seconds

  • Rebase recreates selected commits and changes their IDs.
  • Conflicts happen per replay; ours is the new-base side.
  • Review ranges and coordinate before rewriting published history.
