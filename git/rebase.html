Rebase: put your changes after newer work

Follow each change as Git applies it again after a newer starting commit. See why commit IDs change and how to recover from a stopped rebase.

Need help with HEAD, index, staging, or diff?
Your file
What you are editing now. Git calls the project files the working tree.
Staging area = index
The file content you chose for the next commit. These are two names for one place.
HEAD
Tells Git which saved commit you are using, usually through your current branch.
Diff
A comparison showing added and removed lines between two versions.
Watch these change with one file →

By the end, you can…

  • Predict which branch and commit IDs change.
  • Rebase a private practice branch with a way back.
  • Fix a paused step and check that no useful change was lost.

Start with the reason

You made two commits on feature. Meanwhile main gained another commit. You want your feature changes to appear after that newer main. Rebase takes your selected changes and applies them again, one at a time, after a new starting commit.

Same intended work, new commit IDs

A picture to explore. These buttons do not run commands on your computer.

  1. Step 1

    Before: work split after B

    Main has C. Feature has D and E. Keep a backup name for the old feature before changing it.

  2. Step 2

    Apply the change from D after C

    Git compares B with D to get D’s change, then tries that change after C. The new commit is D′. A conflict pauses this step.

  3. Step 3

    Apply E’s change next

    E’s change is applied after D′, making E′. Feature moves to E′. Main stays at C.

Git does not edit D and E in place. Parent links are part of each commit, so new parents mean new IDs. Git may leave out a change already present on the new base. Review the result rather than assuming the number of commits stays the same.

Try it on a private branch first

A private branch here means work you have not shared with others. If someone already uses the old commits, changing the branch history needs agreement. In a team project, fetch first and use the intended remote base such as origin/main.

  1. Start with saved, clean work

    Read status. Save unrelated edits first. Switch to the branch whose changes you want to reapply.

    Type this in your terminal
    git status
git switch feature

    What you should see: Feature is current and there are no waiting tracked-file changes.

  2. Keep the old feature under another name

    Choose a new backup name. This keeps committed work, not uncommitted edits.

    Type this in your terminal
    git branch backup/feature-before-rebase

    What you should see: Both names point to the old feature commit.

  3. Record the old starting point

    Copy the printed ID into your notes. Later it will be OLD_BASE in the comparison command.

    Type this in your terminal
    git merge-base feature main

    What you should see: The common starting commit ID, B in the picture.

  4. Reapply feature after main

    This local practice uses main. In a shared project, use the fetched and checked base, often origin/main.

    Type this in your terminal
    git rebase main

    What you should see: Git reports success, or pauses at a conflict with instructions.

  5. Check the result

    Inspect commit order, final files, and the project’s tests. Replace OLD_BASE with the ID you recorded.

    Type this in your terminal
    git log --graph --oneline --all
git range-diff OLD_BASE..backup/feature-before-rebase main..feature

    What you should see: Range-diff compares the old list of changes with the new list. Read changed or missing entries; it is a review aid, not proof the program still works.

If rebase stops

  1. Read the current step

    Rebase is applying one original commit at a time.

    Type this in your terminal
    git status
git rebase --show-current-patch

    What you should see: You can see the change being applied now. A patch is the list of added and removed lines.

  2. Edit the intended combined file

    During rebase, ours is the newer starting work plus changes already reapplied. Theirs is the original commit being applied now.

    What you should see: The final file keeps the required behavior from both sides.

  3. Choose the resolved file, check it, and test

    Use the actual conflicted file name. This example uses config.json.

    Type this in your terminal
    git add -- config.json
git diff --staged

    What you should see: The right result is chosen. Run tests before continuing.

  4. Continue with the next change

    The next commit can conflict in the same file again. Check each stop on its own.

    Type this in your terminal
    git rebase --continue

    What you should see: The next step runs, or the rebase finishes.

To return to the pre-rebase branch, use git rebase --abort while rebase is in progress. --quit stops managing the rebase but leaves the current files and commit position. --skip drops the current change from the copied list. These three commands do different jobs.

Change the list of commits deliberately

git rebase -i main opens a list of commits not on main, oldest first. The -i means interactive: you edit what Git should do. Use this only with a clear starting point and backup.

Word in the listWhat Git does
pickApply that commit’s change.
rewordApply it, but ask you to change its message.
editPause so you can change or split the commit.
squashCombine it with the previous kept commit and let you edit the message.
fixupCombine it with the previous kept commit, usually leaving out this message.
dropLeave that change out.

Changing order can break a change that needs an earlier one. git commit --fixup COMMIT marks a small correction for a specific commit. git rebase -i --autosquash BASE can place that correction beside it. Replace COMMIT and BASE with checked IDs. Review the edited list before saving.

Move only a chosen set of changes

Advanced example — these three names must be real branches or checked commit IDs
git log old-base..feature
git rebase --onto new-base old-base feature

Read it as: “Take feature’s commits that are not in old-base, and apply them after new-base.” The first command lets you inspect that selected set. Choosing the wrong old-base can include unrelated work or leave out a needed change.

A normal rebase usually turns merge history into a single line. --rebase-merges tries to build the merge structure again. That needs extra review, including earlier conflict decisions.

What to remember

  • Rebase applies selected changes again and usually makes new commit IDs.
  • Only the branch being rebased moves; main stays at its starting position.
  • Keep the old branch, check each conflict, compare the result, and agree before replacing shared history.
