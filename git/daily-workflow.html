Module 04 / 23 · about 25 minutes

A reliable daily development loop

Move from an issue to a coherent commit, with intentional staging, useful messages and a reviewable diff.

By the end, you can…

  • Stage only intended changes and verify the commit.
  • Keep generated files, secrets and unrelated edits out.
  • Choose a clean starting point for integration.

Start by establishing context

Shell example — read the context before running
git rev-parse --show-toplevel
git status
git branch --show-current
git remote -v
git fetch origin
git log --oneline --decorate -8

Check that you are inside the intended clone, on the intended branch, talking to the expected remote. Remote URLs should not contain tokens. Fetch updates your knowledge of the remote without merging into your current branch. Inspect uncommitted work before switching or integrating.

On a clean working tree, a common feature start is git switch main, git merge --ff-only origin/main, then git switch -c feature/login-timeout. If fast-forward fails, inspect divergence; do not make the failure disappear with a hard reset.

Build one reviewable change

Shell example — read the context before running
git diff -- src/login.py
git add -p -- src/login.py
git diff --staged
git diff --staged --check
# Run the project’s relevant tests here.
git commit -m 'Handle expired login challenges'
git show --stat HEAD
git status

Partial staging lets you separate unrelated changes within one file. The patch shown by git diff --staged is the proposed snapshot. Review it for missing files, debug output, accidental formatting, credentials and generated artifacts. A commit should answer one understandable question, not merely capture everything that happened since lunch.

A useful message describes behavior and why it changed. Use a short summary and, for a complex change, a body explaining the problem, constraints and tradeoff. Follow the team’s conventions; a naming scheme cannot replace a coherent diff.

Staged content can be stale

After staging, later edits are not automatically included. Recheck both git diff and git diff --staged before committing. Avoid a broad git add . when other work is mixed into the directory.

Ignore rules are not deletion or secret protection

Repository ignore patterns — adapt to your project
# .gitignore example
.env
.venv/
__pycache__/
*.log

.gitignore affects untracked-file discovery; it does not remove a file already tracked in history. For a tracked file that should stay on disk but leave the next snapshot, inspect and use git rm --cached -- path, then commit that removal. Old commits still contain the file. Use git check-ignore -v -- path to locate the matching ignore rule.

Track a sanitized example configuration rather than an actual secret. Lockfiles are often intentionally tracked for reproducibility; do not ignore them reflexively. Large binaries may need Git LFS or artifact storage, not repeated ordinary Git snapshots.

Before pushing and asking for review

  1. Read the exact diff and confirm the branch and remote.
  2. Run relevant tests, checks and a build where required.
  3. Confirm the base branch is appropriate and no private data is included.
  4. Push the feature branch with an explicit upstream.
  5. Open a pull request that explains the problem, behavior, validation and rollout implications.
Shell example — read the context before running
git push -u origin feature/login-timeout

A successful push only means the server accepted the update. It does not prove CI passed or the change was merged. Read the pull request checks and review comments. Save local work with a commit, a reviewed stash, or a separate worktree before taking on a different urgent task.

Pause and test your understanding

Remember in 30 seconds

  • Inspect before staging; inspect staged content before committing.
  • One commit should have one coherent purpose.
  • Ignore rules neither untrack existing files nor remove secrets from history.
