Save a change, one step at a time

Follow a small change from editing to a saved commit. Check exactly what will be included before you save it.

Need help with HEAD, index, staging, or diff?
Your file
What you are editing now. Git calls the project files the working tree.
Staging area = index
The file content you chose for the next commit. These are two names for one place.
HEAD
Tells Git which saved commit you are using, usually through your current branch.
Diff
A comparison showing added and removed lines between two versions.
Watch these change with one file →

By the end, you can…

  • Read status before changing anything.
  • Save only the change you meant to save.
  • Keep temporary files and private settings out of new commits.

Begin in the right place

Use the practice project from the previous lesson. A tracked file is a file Git already knows about through staging or a commit. An untracked file has not been added yet.

  1. Read the current state

    Status says which branch you are using and whether any changes are waiting.

    Type this in your terminal
    git status

    What you should see: In a finished practice project, the branch is main and the working tree is clean.

  2. Make one small change

    Open notes.txt. Add the line “I can save a change.” Save the file in your editor.

    What you should see: Status now lists notes.txt as modified, under “Changes not staged for commit.”

  3. Read what changed

    Check that the added sentence is the change you meant to make.

    Type this in your terminal
    git diff -- notes.txt

    What you should see: A + line shows the new sentence.

  4. Choose that file

    Git chooses its current content for the next commit.

    Type this in your terminal
    git add -- notes.txt

    What you should see: Status puts notes.txt under “Changes to be committed.”

  5. Read the chosen change

    This is your last content check before saving the commit.

    Type this in your terminal
    git diff --staged

    What you should see: Only the sentence you intended to add is included.

  6. Save with a useful message

    Say what you changed. A message such as “Add a practice note” is more useful than “stuff.”

    Type this in your terminal
    git commit -m "Add a practice note"

    What you should see: Git shows the new commit ID and the number of changed files.

  7. Check the saved result

    show displays the latest saved change. --stat gives a short file list.

    Type this in your terminal
    git show --stat HEAD
git status

    What you should see: The new commit contains notes.txt. Status shows whether anything remains unsaved in Git.

If your file changes after add, stop and read both diffs. Commit saves the chosen content. It does not automatically choose your newest edit.

For two unrelated changes in the same file, git add -p -- notes.txt lets you choose small groups of changed lines. Git calls each group a hunk. Read each group and answer the prompt. If this feels difficult, make and save one small change at a time first.

Try to answer: Does changing the commit message remove a file you chose by mistake?

No. The message describes the change. Use git restore --staged -- filename to remove a tracked file’s changes from the next commit, then check the staged diff.

Tell Git which new files to leave out

.gitignore is a text file listing new files Git should usually leave out. For example, a log file is a record of a program running. A local settings file may hold private passwords.

Example .gitignore file — edit this in your text editor
.env
*.log
.venv/

.env matches a file with that name. *.log matches names ending in .log. .venv/ matches that folder. Save and commit .gitignore so teammates get the rules too.

These rules do not remove a file Git already tracks. To stop tracking an existing file while keeping your local copy, first inspect git ls-files -- .env, then use git rm --cached -- .env and commit the removal. Earlier commits still contain the old file. If it held a password or token, disable or replace that secret first.

git check-ignore -v -- debug.log tells you which rule ignores debug.log. Do not ignore files just because they are generated: your project may need dependency lockfiles, which record exact package versions.

When you work with a team

A remote is a saved name and address for another Git repository. A push sends your commits there. You will set this up in the next lesson. A commit by itself stays local.

For program changes, run the project’s tests before pushing. Tests are commands the project provides to check behavior; Git does not run them automatically. Before asking a teammate to review, say what changed and which checks you ran.

If something goes wrong

What happened?What to checkWhat to do, then check
Switching branches says it would overwrite your changes.Read git status and both diffs.Save useful work with a commit, or use the temporary-save steps in the stash lesson. Then retry the switch.
The commit includes unrelated changes.Before committing, read git diff --staged.Remove unwanted changes from staging with restore --staged, then check again. If already shared, make a new correction instead of silently changing shared history.
Git says index.lock exists.Another Git command or editor may still be running.Let it finish. Remove the lock only after confirming it is left over from a stopped process. Run status afterward.

What to remember

  • Read status, read the change, choose it, check it, then commit.
  • Saving a file in your editor and making a Git commit are separate actions.
  • Ignore rules only help with files that are not already tracked.
