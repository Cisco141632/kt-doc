Hands-on: commit to container registry

You will run a Dockerized application, test its health, write a GitHub Actions workflow, publish an immutable image and walk through a release decision.

Your mission

Prerequisites: Git, Docker, a GitHub repository with Actions enabled, and permission to publish packages. The sample commands use this repository's docker/examples/hello-docker application.

Work in a branch

Create a practice branch. The workflow will first run as a pull request without publishing. Merge only after you understand every permission and command.

Part 1 — prove the application locally

$ cd docker/examples/hello-docker
$ docker build -t hello-ci:local .
[+] Building ...
$ docker run -d --name hello-ci -p 8000:8000 hello-ci:local
$ curl --fail http://localhost:8000/health
ok
$ docker inspect --format='{{.Config.User}}' hello-ci:local
appuser
$ docker rm -f hello-ci

The health request is a smoke test. The inspect command proves the final image does not run as root. If port 8000 is busy, use -p 8001:8000 and curl port 8001.

The image built successfully. Can the pipeline publish it immediately?

Part 2 — create the workflow

Create .github/workflows/container.yml at the repository root. This workflow gives all jobs read-only access by default. Only the main-branch publish job receives package-write permission.

name: Container pipeline

on:
  pull_request:
    paths:
      - "docker/examples/hello-docker/**"
      - ".github/workflows/container.yml"
  push:
    branches: [main]
    paths:
      - "docker/examples/hello-docker/**"
      - ".github/workflows/container.yml"

permissions:
  contents: read

env:
  CONTEXT: docker/examples/hello-docker

jobs:
  verify:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - name: Check out the tested commit
        uses: actions/checkout@v7

      - name: Build pull-request image
        run: docker build --tag hello-ci:verify "$CONTEXT"

      - name: Smoke test image
        run: |
          set -eu
          docker run -d --name hello-ci -p 8000:8000 hello-ci:verify
          trap 'docker rm -f hello-ci' EXIT
          curl --fail --retry 10 --retry-delay 1 \
            --retry-all-errors http://localhost:8000/health
          test "$(docker inspect --format='{{.Config.User}}' hello-ci:verify)" = appuser

  publish:
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    outputs:
      digest: ${{ steps.push.outputs.digest }}
    steps:
      - uses: actions/checkout@v7

      - name: Define the lowercase image name
        run: echo "IMAGE=ghcr.io/${GITHUB_REPOSITORY_OWNER,,}/hello-docker" >> "$GITHUB_ENV"

      - name: Log in to GitHub Container Registry
        run: printf '%s' "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io \
          --username "$GITHUB_ACTOR" --password-stdin

      - name: Build the release image once
        run: docker build --tag "$IMAGE:$GITHUB_SHA" "$CONTEXT"

      - name: Smoke test the release image
        run: |
          set -eu
          docker run -d --name release-smoke -p 8000:8000 "$IMAGE:$GITHUB_SHA"
          trap 'docker rm -f release-smoke' EXIT
          curl --fail --retry 10 --retry-delay 1 \
            --retry-all-errors http://localhost:8000/health

      - name: Push the tested image
        id: push
        run: |
          output="$(docker push "$IMAGE:$GITHUB_SHA")"
          printf '%s\n' "$output"
          digest="$(printf '%s\n' "$output" | awk '/digest: sha256:/{for (i=1;i<=NF;i++) if ($i=="digest:") print $(i+1)}' | tail -1)"
          test -n "$digest"
          echo "digest=$digest" >> "$GITHUB_OUTPUT"
          echo "Published $IMAGE@$digest" >> "$GITHUB_STEP_SUMMARY"

This example deliberately uses normal Docker commands so you can reproduce every important step locally. Larger pipelines commonly use Docker's official Buildx actions for cache, multi-platform images, metadata and attestations.

Production hardening

Major tags such as actions/checkout@v7 are readable for learning. Production workflows should pin third-party actions to reviewed full commit SHAs and use an updater to propose future versions.

Part 4 — run it and inspect evidence

  1. Create a branch: git switch -c learn/container-pipeline.
  2. Add the workflow, commit it and push the branch.
  3. Open a pull request. Confirm that only verify runs.
  4. Open each step log. Find the health response and the non-root user check.
  5. Intentionally change /health to a missing path. Push and observe the failure.
  6. Restore the path, push and confirm recovery.
  7. Merge when approved. Confirm the publish job writes a digest to the summary.
  8. Open the repository package and locate the commit-SHA tag.

If package publication is not permitted, keep the pull request unmerged. You still completed the CI portion without external writes.

Part 5 — promote by digest

Copy the published digest from the job summary. A deployment manifest should reference the exact content:

spec:
  template:
    spec:
      containers:
        - name: hello
          image: ghcr.io/OWNER/hello-docker@sha256:PASTE_DIGEST_HERE
          readinessProbe:
            httpGet:
              path: /health
              port: 8000

For a Docker server, pull and run the same digest. The deployment system should record commit, digest, environment, actor, time and result.

Interactive release rehearsal

A release is ready. Perform the decisions in their safe order.

Begin with the evidence that makes this commit releasable.

Optional extensions

  • Add a Python unit test and run it before the Docker build.
  • Add a dependency or container vulnerability scan with an explicit severity policy.
  • Generate an SBOM and attach it to the release evidence.
  • Add a protected staging environment and a deploy job that references it.
  • Add a concurrency group so production deployments cannot overlap.
  • Pin every action to its full commit SHA.

Definition of done

  • You can explain every trigger, permission, dependency and command.
  • A deliberately broken health check blocks the pipeline.
  • The published image is tagged with its commit and recorded by digest.
  • You know how that same digest would be promoted and rolled back.
