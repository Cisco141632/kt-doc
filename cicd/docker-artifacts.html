Docker and immutable artifacts

CI should turn source into one identifiable output. For a containerized service, that output is an OCI image addressed by a tag and, precisely, by a content digest.

Docker is the delivery contract

This is build once, promote many. Rebuilding for production can silently change packages or base layers, so production would no longer run what staging verified.

Which value most precisely proves which image bytes are running?

Prepare the application for containers

  • Read configuration from environment variables or mounted configuration.
  • Keep secrets out of source, build arguments, layers and image history.
  • Write logs to standard output/error.
  • Expose readiness and liveness endpoints with meaningful checks.
  • Handle termination signals and stop within the platform grace period.
  • Store durable data outside the writable container layer.
  • Run as a non-root user and use a small, maintained base image.

app:1.4.2Human release versionNever move the tag to different content
app:a81f29cDirect link to a Git commitUse enough characters to avoid collisions
app@sha256:…Exact content identityLess readable, strongest deployment reference
app:latestConvenience for local explorationNot a reliable production release identity

$ docker push ghcr.io/acme/payments:a81f29c

The registry is the promotion boundary

A registry stores versioned images and metadata. CI authenticates with write permission to publish. Runtime identities normally need read-only permission. Record the digest returned by the push; deployment consumes that digest.

Promotion does not mean copying source

Promotion changes which verified digest an environment references. Some organizations copy the same manifest between registry namespaces, but they still preserve its content identity.

Attach evidence to the artifact

A mature build produces more than an image:

  • Test and coverage reports
  • Vulnerability scan result
  • Software Bill of Materials (SBOM)
  • Provenance/attestation describing how it was built
  • OCI labels linking source repository, commit and license
Recall: why should CI build production images instead of a developer laptop?

CI starts from committed code in a controlled environment, records the logs and identity, applies policy, and avoids uncommitted files or a mismatched processor architecture.

Remember

  • Build once, verify once, and promote the same digest.
  • Tags are names; a digest is the immutable content identity.
  • Container readiness begins in the application: external config, stdout logs, health checks, signals and statelessness.
