Continuous integration

CI is a team practice before it is a server: integrate small changes often, verify each change automatically, and keep the main branch releasable.

The developer feedback loop

A pull request should show the code difference and the machine evidence together. Require important checks before merge and prevent direct, unreviewed changes to the protected branch.

Use several test layers

LayerQuestionTypical speedPipeline position
Static checksIs the code well-formed and free of obvious defects?SecondsFirst
UnitDoes one function/class behave correctly?Seconds–minutesEvery change
IntegrationDo our components, database and queue work together?MinutesBefore publishing
ContractDo service interfaces remain compatible?MinutesBefore merge/release
End-to-endCan a user complete a critical journey?SlowestSelected paths, staging
SmokeDid the deployed service start and answer?SecondsAfter deployment

A database migration changes a column type. Which test is most likely to catch an incompatibility?

Quality gates need policy

Useful gates reject known risk. Examples: tests pass, coverage on changed code does not fall below an agreed threshold, no critical exploitable vulnerability is introduced, and required reviewers approve sensitive paths.

Healthy gate

  • Has a documented purpose
  • Produces an actionable message
  • Has an owner and exception process
  • Blocks real risk consistently

Unhealthy gate

  • Was copied without context
  • Fails intermittently
  • Nobody knows how to fix it
  • Teams routinely bypass it

Make CI reliable and fast

  • Pin dependencies and commit lock files.
  • Use clean runners so undeclared machine state cannot make a test pass.
  • Cache dependencies, not truth. Cache package downloads; never reuse stale test output.
  • Quarantine only with ownership. A flaky test gets a ticket, owner and deadline.
  • Cancel obsolete runs. If a new commit replaces an older pull-request run, stop wasted work.
  • Make local reproduction easy. One script or container should run the same checks.
#!/usr/bin/env sh
set -eu
./scripts/lint.sh
./scripts/unit-test.sh
./scripts/integration-test.sh

Branching without long-lived divergence

Short-lived feature branches and frequent merges expose integration problems early. Long-lived branches postpone integration, creating a large, risky merge at the end. Release branches can still be appropriate when multiple supported versions require separate maintenance.

Recall: why does “merge small changes often” reduce risk?

Each review contains less code, failures have fewer possible causes, conflicts are smaller, and rollback affects less behavior.

Remember

  • CI keeps the main branch releasable through small integrations and automatic evidence.
  • Different tests answer different questions; no single test layer is sufficient.
  • A noisy, flaky gate trains people to ignore safety signals.
