Deployment strategies

Deployment places code in an environment. Release exposes behavior to users. Choosing how traffic moves determines downtime, infrastructure cost, detection speed and rollback complexity.

Choose the simplest strategy that meets the risk

StrategyHow it worksStrengthTrade-off
RecreateStop old, start newSimple and cheapDowntime; no overlap
RollingReplace instances graduallyContinuous availabilityOld and new coexist
Blue-greenBuild a complete parallel environment, then switch trafficFast traffic rollbackTemporary duplicate capacity
CanarySend a small traffic percentage to the new version, then increaseLimits initial blast radiusNeeds traffic control and version-aware metrics
Feature flagDeploy code disabled, then enable behavior separatelySeparates deploy from releaseFlag cleanup and interaction complexity

Hands-on: make the deployment decision

A payment service requires near-instant traffic rollback and can temporarily afford double capacity. Which is the best initial choice?

A recommendation change may affect conversion in ways tests cannot predict. You want 2% exposure first.

A canary is a controlled experiment

1. Establish the baseline

Record current error rate, latency, saturation and business success for the stable version.

2. Deploy without meaningful traffic

Confirm readiness, configuration and dependency access.

3. Send a small cohort

Compare canary and stable by version. Aggregate metrics can hide canary failure.

4. Increase in timed steps

Continue only while technical and business guardrails pass.

5. Complete or abort

Move to 100% and retire old instances, or send traffic back and preserve evidence for diagnosis.

Rolling update and rollback in Kubernetes

$ kubectl set image deployment/api api=ghcr.io/acme/api:a81f29c
$ kubectl rollout status deployment/api
deployment "api" successfully rolled out
$ kubectl rollout history deployment/api
$ kubectl rollout undo deployment/api
$ kubectl rollout status deployment/api

A readiness probe prevents traffic reaching an instance before it is ready. maxUnavailable limits lost capacity; maxSurge limits extra capacity. The commands do not solve database compatibility or confirm business health by themselves.

Rollback is one recovery tool

  • Rollback: deploy the previous artifact when it remains compatible.
  • Roll forward: release a small corrective change when rollback is unsafe.
  • Disable a feature: use a flag or kill switch to reduce impact quickly.
  • Shift traffic: return traffic to blue/stable while keeping the failed version available for inspection.
Practice before the incident

A rollback runbook that nobody has exercised is a hypothesis. Regularly prove artifact retention, access, commands, database compatibility and decision ownership.

Remember

  • Recreate is simplest; rolling preserves capacity; blue-green switches environments; canary limits exposure.
  • Feature flags separate deployment from behavior release, but they create code paths that must be cleaned up.
  • A successful rollout command is not enough—verify user-facing health.
