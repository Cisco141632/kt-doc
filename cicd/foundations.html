Pipeline foundations

A pipeline is executable release policy: which event starts work, where it runs, what evidence it produces and which conditions allow the release to continue.

The six building blocks

PartMeaningExample
TriggerThe event that starts a runPull request, merge, release tag, manual request, schedule
WorkflowThe complete automated process.github/workflows/ci.yml
JobA group of steps on one runnerTest, build image, deploy staging
RunnerThe machine or container executing a jobHosted Ubuntu VM or controlled self-hosted agent
ArtifactA versioned output retained after the jobTest report, binary, Docker image, SBOM
GateA condition that must passTests green, scan accepted, approval granted

Design for fast, useful failure

  1. Run formatting, linting and unit tests early because they are fast.
  2. Run independent checks in parallel.
  3. Build once after cheap checks pass.
  4. Run integration, security and end-to-end checks against the built result.
  5. Publish only verified artifacts.
  6. Deploy with explicit concurrency and rollback rules.
A long pipeline is not automatically a strong pipeline

A 50-minute pipeline that fails for unrelated flaky tests teaches developers to ignore it. Optimize for trustworthy feedback: stable tests, clear ownership, useful logs and a short critical path.

Read a small workflow

name: CI

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - run: ./scripts/ci-test.sh

on defines triggers, jobs defines parallel work, runs-on chooses a runner, and steps run in order inside that job. Keeping commands in scripts/ci-test.sh lets developers run the same test locally.

The test job creates app.tar. A separate deploy job expects that file. What must the workflow do?

Hands-on: assemble the safe path

Select the stages in the order that gives fast feedback and preserves one verified artifact.

Start with the fastest feedback that can reject a bad change.

Pipeline ownership

The platform team may provide templates, but the team shipping the service owns whether its tests describe reality. Treat a broken main branch or failed production deployment as a product incident, not as “the CI team's problem.”

  • Every failed step should say what failed and how to reproduce it.
  • Every gate should have an owner and a reason.
  • Every exception should expire rather than silently becoming permanent.

Remember

  • Triggers start workflows; jobs run on isolated runners; artifacts carry outputs; gates control progression.
  • Parallelize independent work and put fast checks first.
  • The pipeline is shared production code: review, test and maintain it.
