What is CI/CD?

CI/CD is the repeatable path that turns a code change into a verified release. It combines team habits, automated checks, immutable artifacts, controlled deployment and production feedback.

The complete picture

A healthy delivery system answers four questions in order: Is the change understandable? Is it correct? Is the exact release safe to deploy? Is it healthy after deployment?

Think of a pipeline as an airport

Git identifies the passenger, CI performs security checks, the artifact is sealed luggage, deployment moves it to the aircraft, and monitoring confirms the flight is healthy. Skipping a gate may feel faster until something goes wrong.

CI, delivery and deployment

TermMeaningDecision it automates
Continuous integrationDevelopers merge small changes frequently. Every change is automatically built and tested.“Is this change safe to merge?”
Continuous deliveryEvery successful change becomes a deployable release. Production still has a deliberate approval or business decision.“Could we release this now?”
Continuous deploymentEvery change that passes the pipeline automatically reaches production.“All evidence passed, so release it.”

Continuous deployment is not the first goal. Start with reliable continuous integration, then make releases repeatable, then automate production only when tests, observability and rollback are trustworthy.

Predict before revealing

Every merge is tested, packaged and deployed to staging. A release manager approves production. What is this?

How it helps

SpeedShort feedbackA developer learns about a failure in minutes while the change is still fresh.
SafetySmall releasesSmall batches are easier to review, test, diagnose and reverse.
ConsistencyOne repeatable processThe pipeline performs the same steps for every release instead of relying on memory.
EvidenceTraceable releasesA commit, test run, artifact digest and deployment record explain exactly what is running.

CI/CD does not mean “deploy quickly at any cost.” It means reducing release risk through small changes, automated evidence and fast recovery.

Do not learn a shopping list

Learn the responsibilities first. A Jenkins stage and a GitHub Actions job use different syntax, but both execute work on a runner and pass evidence to the next gate.

Remember

  • CI verifies changes; continuous delivery keeps a verified release ready; continuous deployment releases it automatically.
  • The artifact that passed the tests—not freshly rebuilt code—should move between environments.
  • A pipeline is complete only when production health is verified and recovery is possible.
