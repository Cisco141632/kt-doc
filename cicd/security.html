Pipeline security

A delivery pipeline can modify production, publish trusted software and access secrets. Treat it as a high-value production system with a software supply-chain threat model.

What can go wrong?

Least privilege by job

permissions:
  contents: read

jobs:
  test:
    permissions:
      contents: read
    # no package or production permission

  publish:
    permissions:
      contents: read
      packages: write
      id-token: write

Separate build and deployment identities. A pull request from untrusted code must not receive production secrets. Protect environment secrets behind the production gate and prefer short-lived credentials.

A forked pull request needs to run unit tests. Which permission is appropriate?

Protect the software supply chain

  • Pin package dependencies with lock files.
  • Pin third-party CI actions to full commit SHAs; use an updater to propose reviewed changes.
  • Use trusted, ephemeral runners for sensitive builds.
  • Generate an SBOM and build provenance.
  • Sign or attest artifacts and verify policy before deployment.
  • Restrict registry writes and prevent production tags from being overwritten.
  • Patch/rebuild images when the base receives security updates, even if application code did not change.
Scanning is not patching

A scanner reports evidence. The remediation loop still needs ownership, severity policy, a deadline, a rebuilt artifact and verification that the vulnerable version is no longer deployed.

When a secret leaks

  1. Revoke or rotate the credential immediately.
  2. Determine its scope, lifetime and access logs.
  3. Remove the secret from current source and artifacts.
  4. Rewrite history only when required, understanding that existing clones remain.
  5. Find the control failure and add prevention/detection.
Recall: why is deleting the secret in a new commit insufficient?

The previous commit, CI logs, caches, images and developer clones may still contain it. The credential must be assumed compromised and rotated.

Remember

  • Give every job only the permissions it needs, for only as long as it needs them.
  • Never expose privileged secrets to untrusted pull-request code.
  • Evidence—scans, SBOMs and provenance—needs enforcement and a remediation owner.
