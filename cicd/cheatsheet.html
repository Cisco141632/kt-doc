CI/CD cheat sheet

Use this during pipeline reviews and releases. It summarizes sequence, evidence, commands, ownership and recovery.

Safe pipeline blueprint

  1. Change: small commit, pull request, review.
  2. Verify: lint, unit, integration, contract and security checks.
  3. Build once: produce an immutable versioned artifact.
  4. Identify: record source commit, image tag and digest.
  5. Publish: push to a controlled registry with evidence.
  6. Stage: deploy the same digest and run smoke/end-to-end checks.
  7. Gate: satisfy policy, approval, SLO and change-window requirements.
  8. Release: roll out with controlled exposure.
  9. Verify: compare technical and business health by version.
  10. Recover: pause, shift traffic, disable, roll back or roll forward.

Docker artifact commands

$ git rev-parse --short HEAD
a81f29c
$ docker build -t ghcr.io/acme/api:a81f29c .
$ docker run -d --name smoke -p 8000:8000 ghcr.io/acme/api:a81f29c
$ curl --fail http://localhost:8000/health
ok
$ docker push ghcr.io/acme/api:a81f29c
$ docker inspect --format='{{index .RepoDigests 0}}' ghcr.io/acme/api:a81f29c
ghcr.io/acme/api@sha256:…
$ docker rm -f smoke

Use the resulting digest for environment promotion. Do not rebuild between staging and production.

Pull-request pipeline checklist

QuestionHealthy answer
Can untrusted code access privileged secrets?No; fork/PR jobs are read-only and isolated
Can developers reproduce checks?Yes; repository scripts or containers run the same commands
Are dependencies deterministic?Lock files and pinned tool/action versions are reviewed
Are important checks required?Branch policy blocks merge when trustworthy checks fail
Are failures actionable?Logs identify the failing test, input and reproduction path
Is obsolete work cancelled?New commits cancel superseded safe-to-cancel runs

Production release checklist

  • Required tests, reviews and policy checks passed.
  • Artifact digest and source commit are recorded.
  • SBOM, scan and provenance meet policy.
  • Configuration and secret references are correct for the environment.
  • Database migration is backward-compatible and separately recoverable.
  • Previous working digest is retained and rollback was rehearsed.
  • Readiness, smoke and version-specific monitoring are ready.
  • Only one production deployment can run at a time.
  • Owner, communication path and stop conditions are known.
  • Release is observed for the defined verification window.

One rule to carry forward

Build once, identify precisely, promote the same artifact, verify real health, and keep recovery simpler than deployment.
