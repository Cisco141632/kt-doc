Continuous delivery and environments

Delivery makes every accepted change release-ready. Environments provide increasing confidence, but they should not create different application builds.

Perfectly identical environments are rarely practical. Aim for parity in the behavior being tested: runtime version, deployment mechanism, networking and managed-service class should reveal production-relevant failures.

Use gates where risk changes

1. Verify the commit

Code review, automated tests and security checks create evidence. No deployment credential is needed.

2. Publish the artifact

Push an immutable image and record its digest, SBOM and provenance.

3. Validate in staging

Deploy the same digest, run smoke/contract/end-to-end checks, and examine signals.

4. Satisfy production policy

Risk may require a human reviewer, change window, automated SLO check or segregation of duties.

5. Release and verify

Control traffic, watch the new version and automatically stop or roll back on failure.

When should a production deployment job receive production secrets?

Separate code, configuration and secrets

Configuration

  • Feature limits
  • Service URLs
  • Log level
  • Replica count

Secrets

  • Database password
  • Signing key
  • API credential
  • Private certificate

Configuration can usually be versioned. Secrets require encrypted storage, access policy, auditing and rotation. Prefer short-lived identity federation (for example OIDC to a cloud role) over permanent cloud keys stored in CI.

Database changes cross release boundaries

An application rollback does not roll back data. Use backward-compatible expand and contract changes:

  1. Expand: add the new column/table/API without removing the old one.
  2. Migrate: release code that can work with both shapes and backfill data safely.
  3. Switch: make the new path authoritative after verification.
  4. Contract: remove the old path in a later release.
Avoid a dangerous coupling

Do not deploy code that requires a destructive schema change at the exact same instant. During rolling or canary deployment, old and new instances coexist.

Scenario: version 2 renames customer_name to name. What is the safe first migration?

Add name while keeping customer_name. Update code to tolerate/write both, migrate existing values, and remove the old column only after no deployed version uses it.

Control concurrent deployments

Two production deployments running at once can finish out of order. Configure a production concurrency group so only one release changes the environment at a time. Decide whether a newer queued release cancels or waits for the older one; migrations often require waiting.

Remember

  • Promote one artifact; inject environment-specific configuration at runtime.
  • Put approval and secret access at the boundary where risk increases.
  • Use backward-compatible database migrations because application rollback cannot reverse data automatically.
